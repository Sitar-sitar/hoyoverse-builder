## 2. 重大な指摘（E着手前に解消が必須）

### R-01【重大 / §5.7・§5.8 E】Pages の CDN キャッシュ（max-age=600）で descriptor が最大10分古いまま読まれる

- **該当**: §5.8「Pages deploy成功後に…伝播待ちの再試行は全体120秒以内・10秒間隔」、§5.8「cache no-store」
- **事実**: GitHub Pages は `Cache-Control: max-age=600` を返し CDN 経由で配信される。リクエスト側の `cache: "no-store"` は fetch 実装のローカルキャッシュを抑止するだけで、CDN エッジのキャッシュは迂回しない。
- **指摘**: deploy 直後のエッジが旧 `release.json` を返し続けると、公開後検査の120秒窓を使い切って job が失敗し得る。定期監視も最大10分間 `release_transition`／不一致で失敗し得る。どちらも実害のない誤失敗だが、「失敗＝要対応」という監視の意味を損なう。
- **推奨対応**: descriptor 取得 URL へ毎回変わる cache-busting クエリ（例: `release.json?run=<GITHUB_RUN_ID>-<attempt>` または時刻）を付けることを §5.8 に明記する。固定 Origin・固定パスの許可先判定はクエリを除いたパスで行う。§8.1 の monitor 試験に「旧 descriptor を返す CDN fixture が cache-busting で解消する」ケースを足す。CDN 挙動は観測でしか確かめられないため、G-05 に「初回公開時に descriptor の伝播時間を実測して記録」を加える。

### R-02【重大 / §5.8 E-2】通常リリースの「API先行・Pages未公開」窓の扱いが未定義

- **該当**: §5.1「通常更新はPR検証→API自動配備→health対象SHA一致→Pages配備」、§5.8「開始・終了でSHAやdescriptorが変わった場合は`release_transition`」
- **指摘**: 通常更新では API が先に新 SHA へ切り替わり、Pages の build（`pnpm test`・`content:check`・`check`・`build:api`）を経て deploy されるまで、**API=新 SHA、descriptor=旧 SHA** の状態が数分続く。この間の定期 run は開始・終了で値が変わらないため `release_transition` に当たらず、分類が未定義のまま非合格になる。結果として **すべての通常リリースで定期監視の失敗が1回以上出る** ことが仕様上確定する。また §5.8 の期待 digest は descriptor 由来のため、API が新 SHA の時点で digest 比較は必ず不一致になり、`payload_mismatch`（同一 SHA で digest だけ違う）とも区別できない。
- **推奨対応**: 次のどちらかを設計で選び、理由とともに §5.8 に固定する。
  1. **(推奨)** `api_ahead`（health の revision ≠ descriptor の revision、かつ開始・終了で不変）を固定理由として追加し、非合格（終了1）のまま `release_transition` と同様「次 run で自然回復を確認」と扱う。誤報ではなく「公開途中」と読めるようにする。digest 比較は revision 一致時だけ行い、不一致時は `api_ahead` を優先して記録する。
  2. API 先行窓を許容（PASS 扱い）する。ただし API だけ更新されて Pages が失敗したまま放置される状態を検出できなくなるため、許容時間の上限（例: 30分）と超過時の失敗理由を合わせて定義する必要がある。
- §8.1 monitor 行・AC-E2 に、この窓の分類試験と「通常リリース1回で発生した失敗理由を記録する」受入を加える。

### R-03【重大 / §5.7 E-1】forward 以外のモードでの `mode_unsupported` の終了コードが未定義

- **該当**: §5.7「legacy/parallel/rollbackでは`mode_unsupported`とする」、§5.8「終了0/1を維持」、§10「descriptor付き直前artifactと対応APIへ戻す」
- **指摘**: `mode_unsupported` が終了1なら、rollback モードで復旧している間、定期監視が5分ごとに失敗し続ける（復旧手段を取るほど監視が赤くなる）。終了0なら、誤って forward 以外へ切り替わった公開を見逃す。どちらかで運用が変わるのに決まっていない。あわせて、rollback モードの artifact にも descriptor を生成するのか（§5.7 は `mode:"forward"` 固定）が読み取れない。
- **推奨対応**: `mode_unsupported` は **終了1・固定理由記録** とし、rollback 中は監視失敗が続くことを運用ガイドの切戻し手順（A）へ明記する、のように決めて §5.7 に書く。descriptor の `mode` は「forward のときだけ生成、他モードは生成しない（→ `release_descriptor_missing`）」か「各モードで生成し monitor が mode で分岐」かを決め、§8.1 release 行の「mode不正」試験の期待値をそれに合わせる。

## 3. 中程度の指摘（該当段階の着手前に反映）

### R-04【中 / §5.5 C・§11 G-02】Job の NODE_ENV は image で確定済み。開発時の URL 検証条件が曖昧

- **該当**: §5.5 表「本番JobのDrizzle実行…JobのNODE_ENV=productionを運用ゲートで確認」、「URL不正、mysql以外のscheme、host/database欠落」行
- **事実**: `Dockerfile.northflank:11` が `NODE_ENV=production` を固定しており、Job は同 image を使う（運用ガイド §Migration）。一方、Northflank 側の環境変数で上書きされていないかはコードからは分からない。
- **指摘**: (1) G-02 の確認対象を「image 既定は production。Northflank の Job 環境変数による上書きの有無」に絞れる。(2) 表の「URL不正…起動拒否」行が production 限定か全環境かが書かれていない。development でも DATABASE_URL が設定されていれば拒否するのか、従来どおり `getDb` の catch で null に落とすのかで、ローカル検証の挙動が変わる。(3) `drizzle.config.ts` は `drizzle-kit generate`（`db:push` の前段）でも評価される。ローカルの generate で production 検証が走らない条件（NODE_ENV 未設定）を明記しておくと安全。
- **推奨対応**: 表の該当行に適用環境（推奨: DATABASE_URL が設定されていれば全環境で URL 形式を検証、CA 必須は production のみ）を追記し、§8.1「本番設定」行に development の不正 URL ケースを足す。G-02 の文言を上記 (1) に更新する。
- **補足（設計の妥当性を補強する事実）**: 現行 `drizzle.config.ts` は CA ありのとき URL を host/user 等へ分解するため **query を捨てる** が、API は `uri` をそのまま mysql2 へ渡すため **query が効く**。つまり現状でも API と Job で URL query の扱いが非対称であり、§5.5 の「本番URLにqueryオプションあり→起動拒否」はこの非対称を解消する点でも正しい。この根拠を §5.5 に一文残すとよい。

### R-05【中 / §5.2 B-1】容量拒否でも UID 回数制限を消費する影響を利用者側から書いていない

- **該当**: §5.2「routerのIP/UID回数制限は従来どおり先に評価される。これを回避するためのカウント返却は行わない」、`server/routers.ts:107-111`
- **指摘**: 設計判断自体は妥当（返却は回数制限の迂回経路になる）。ただし「混雑で `public.busy` を受けた利用者が再試行すると、上流取得が一度も行われていないのに UID 制限へ近づく」という利用者影響が §10 リスク表に無い。上流 429 は `TOO_MANY_REQUESTS`（`server/gameProviders.ts:86`）、容量拒否は `SERVICE_UNAVAILABLE` と code は分かれるが、文言は同じ `public.busy` のため利用者からは区別できない。
- **推奨対応**: §10 に「容量拒否の再試行が UID 制限を消費する」行を追加し、検出手段（固定理由の拒否件数）と許容理由を書く。文言を分けない理由（新規文言は翻訳基盤の対象になり D/翻訳の範囲を広げる）も一言残す。

### R-06【中 / §5.4 B-3・§6】プール非待機化で、公開表示設定が瞬間的に legacy 表示へ戻り得る

- **該当**: §5.4「公開設定の既存fallback…を維持」、§6 非破壊条件、`server/displaySettings.ts:23-38`
- **事実**: `readPublicDisplaySettings` は成功時だけ60秒キャッシュし、DB 取得失敗時は **全キー legacy（`variants:{}`）** を返す。失敗時のキャッシュは無い。
- **指摘**: `waitForConnections=false` 導入後は、キャッシュ切れの瞬間に接続10本が埋まっていると（照会の analytics 記録はリクエストごとに接続を使う）、その要求は待たずに失敗し、**管理者が選んだ表示 variant ではなく legacy 表示が配信される**。これは既存 fallback の「維持」ではあるが、従来は待機で吸収されていた事象が利用者に見える表示切替として現れる新しい挙動であり、§6 の「3ゲームの…実装前後で一致する（負荷制限による新しい拒否とOAuth期限切れ以外）」の例外にも入っていない。
- **推奨対応**: 次のいずれかを §5.4 に明記する。(a) 許容し、§6 の例外列挙へ「DB 接続枯渇時の公開表示設定の legacy fallback」を加え、§8.2 の隔離測定で代表照会と同時に表示設定取得を行い発生率を記録する。(b) 失敗時は直前の成功キャッシュ（期限切れでも）を返す LKG を追加する。(b) は B のスコープ拡大になるため、本書では (a) を推奨する。

### R-07【中 / §5.6 D】情報不足の69%（`guide.authoring.*` 1,132件）の帰属解決元が未指定

- **該当**: §5.6 表「帰属」「優先順」
- **事実**: 1,644件はすべて `planned` で、active は0件。id から game/subjectId が読めるのは `character.<game>.<id>.*` の512件だけで、残り1,132件は `guide.authoring.<定義ファイル>.<連番>.*` 形式。
- **指摘**: (1) 「characterRecords等の構造化された既存ID対応から解決」だけでは、`guide.authoring.*` をどの既存データ（guide 定義の identity / lookupKey 等）から解決するかが実装者の推測になる。解決できなければ1,132件が「game 不明は末尾」に並び、優先順の実用性が大きく落ちる。(2) 現データでは優先度1（active 不足）群が空なので、§8.1 backlog 試験は active を含む合成 fixture でしか優先順を検証できない。
- **推奨対応**: `guide.authoring.*` の帰属は既存の guide 定義が持つ identity（`unresolvedGuideFields` が参照する `identity.identityKey` と同じ系統）から解決し、`legacy:` 系 identityKey は game のみ採用・subjectId は null、のように解決元と部分解決のルールを §5.6 に固定する。§8.1 backlog 行に「active を含む合成 fixture で優先順1〜3を検証」「現データで帰属 null 件数を出力し記録」を追加する。

### R-08【中 / §5.9 F】照会状態 hook の抽出は効果に比して変更が大きい（YAGNI）

- **該当**: §5.9 第2段落、§7 F 行、§8.1 F 行

### R-11【低 / §5.8 E-2】公開後検査を走らせる deploy job には依存導入が無い

- `deploy-pages.yml` の `deploy` job は checkout と Node のセットアップだけで、`pnpm install` を行わない。公開後検査を deploy job に置くなら、`scripts/release-contract.mjs` と `scripts/monitor-production.mjs` は **外部依存なし（Node 標準のみ）** であることを §5.7 に制約として明記する。build job 側の `releaseManifest.ts`（tsx 使用）とは実行環境が異なる点も合わせて書く。

### R-12【低 / §5.7 E-1】probe 対象の選び方と digest の変動要因

- probe は「各ゲームの現行カタログ先頭」（例: HSR は `Dr.レイシオ`）で、キャラ追加で先頭が変わり得る。descriptor を毎公開で再生成するので問題はないが、「probe 名の変化は異常ではない」ことを monitor の試験期待値に含める。
- カタログ・詳細の presentation には `contentRevision` が含まれるため、content 変更ごとに digest が変わる。これは意図どおりだが、言語設定（Phase 58 の公開言語）が将来 presentation の出力に影響するようになると、DB 状態で digest が変わり得る。現状は `language:"ja"` 固定（`server/content/presentation.ts:28`）なので、「presentation が DB 状態に依存しないこと」を E の前提として §5.7 に明記しておくとよい。

### R-13【参考 / §5.2 B-1】登録順序の試験は現行構造なら成立する

- 現行の `lookupWithCache` は `loader()` を Promise 生成式の中で同期的に呼び、直後に `inFlight.set` する（`server/gameProviders.ts:586-592`）。`get` と `set` の間に `await` が無いため、同 UID の二重起動は単一スレッドの範囲で起きない。§5.2 手順3の試験は「`get`→ゲート取得→`set` の間に `await` を挟まない」ことを固定する形で書けば十分。指摘ではなく、実装時の目安として記録する。

## 5. 良い点（維持すべき判断）

- B-1 で取得枠を `lookupWithFallback` の外側に置く判断は、`catch {}` で無条件 fallback する現行構造（`server/buildAdvisor.ts:687-693`）を正しく踏まえている。
- B-3 で `queueLimit=0` が「無制限」であることを明記し、非待機の根拠を `waitForConnections=false` に置いている。mysql2 の実装（`pool.js:107-109`）とも一致する。
- C で TLS 検証の無効化経路を一切追加せず、構文検証を接続成功の証拠にしないと明記している。
- D を読み取り専用 CLI に限定し、既存 report の判定器を再利用して別の正本を作らない方針。
- E で main HEAD や監視コードの SHA を期待版に自動採用しない方針。固定 RELEASE（`b5374e3`）の陳腐化という現行の問題を正しく狙っている。
- 本番に人工負荷をかけない、実 UID を測定結果に残さない、ログへ秘密値を出さないといった運用安全の制約が各節に入っている。
