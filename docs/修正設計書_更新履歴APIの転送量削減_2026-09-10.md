## 1. 着手前の実測で、計画書の見立てが外れていた

計画書 §4.3 #5 はこう書いている。

> `build.guideHistory` の応答が非圧縮 210KB。248名 × バッチイベント本文（同じ長文が名前だけ変えて248回）を含む
> → イベント本文をバッチ単位に正規化して返す **API 形の変更**が要るため別途

着手前に本番 API を実測したところ、**主因は応答の形ではなく、API が圧縮を一切していないこと**だった。

```
GET /api/trpc/build.guideHistory
  Accept-Encoding: gzip, deflate, br  →  Content-Encoding ヘッダーなし
  受信 414,137 バイト（無圧縮）
  同じ本文をローカルで gzip -9 → 18,423 バイト（4.4%）
```

`server/_core/index.ts` に圧縮ミドルウェアが無く、`compression` は依存にも入っていない。
Railway も前段で圧縮していない。つまり **248名ぶんの繰り返しだらけの JSON が、そのまま生で流れている**。
実サイズも計画書の 210KB ではなく **404KB** だった。

### 応答の内訳（`JSON.stringify` のバイト数、計 396.2kB）

| 区分 | サイズ | 備考 |
| --- | ---: | --- |
| `characters`（248件） | 374.8kB | うちイベント本文 322.8kB / キャラクター属性 48.5kB |
| ├ `changes` | 93.7kB | **実体は17種**しかない（同じ配列が500回） |
| ├ `summary` | 85.8kB | 292種。**画面が一度も描画していない**（後述） |
| ├ `rationale` | 62.6kB | 実体は16種 |
| ├ `title` | 27.0kB | 実体は22種 |
| └ `date` | 9.6kB | |
| `updateLedger` | 17.0kB | |
| `siteEvents` | 4.3kB | |

イベントは500件（244名が2件・4名が3件）。本文の実体は24通りしかなく、
**同じ長文が名前だけ変わって500回並んでいる**という計画書の指摘自体は正しい。
ただしこの構造は gzip が最も得意とする冗長性で、圧縮すれば 4.4% まで潰れる。

## 2. 決定

### D1. `compression` ミドルウェアをアプリ全体へ入れる（本設計の本体）

`server/_core/index.ts` の `applyBodyParsers(app)` の前に `app.use(compression())` を置く。

| エンドポイント | 現在（実測） | 圧縮後の見込み | 削減 |
| --- | ---: | ---: | ---: |
| `build.guideHistory` | 414,137 B | 約 18,400 B | **95.6%** |
| `build.referenceCatalog`（図鑑一覧） | 17,064 B | 約 2,265 B | 86.7% |
| `build.reference`（1キャラクター） | 11,876 B | 約 4,010 B | 66.2% |

`/updates` の初回表示だけでなく、**図鑑・UID照会を含む全画面**が対象になる。
応答の JSON は 1 バイトも変わらない。

実装後の実測（2026-09-11、ビルド済み `dist/index.js` を `API_ONLY=true` で起動して `build.guideHistory` を取得）:

| `Accept-Encoding` | 受信バイト数 | `Content-Encoding` |
| --- | ---: | --- |
| なし | 414,137 | なし |
| `gzip` | 18,928 | `gzip` |
| `br` | 13,902 | `br` |

`compression` 1.8 は brotli にも対応しており、ブラウザは `br` を優先して送るため、実際の転送量は gzip 見込みよりさらに小さい。

確認する点:

- **`Vary` ヘッダーの衝突**。~~既存の CORS ミドルウェアが `res.setHeader("Vary", "Origin")` で
  上書きしているため、`compression` が付ける `Vary: Accept-Encoding` が消えないことを実測で確かめる。
  消える場合は CORS 側を `res.appendHeader` へ直す。~~
  **【2026-09-11 訂正】前提が誤っていた。** 実装時の実測で、圧縮導入**前**の本番応答の `Vary` は
  `trpc-accept` だけで、`Origin` は最初から残っていなかった。tRPC のアダプタ（`resolveResponse` が
  応答ヘッダーに `vary: trpc-accept` を設定する）が、先に CORS が付けた `Vary: Origin` を上書きしている。
  tRPC が後から上書きするため、CORS 側を `appendHeader` に変えても直らない。
  本設計ではこの既存不具合を直さず（§6 へ）、**圧縮が既存の `Vary`（`trpc-accept`）を上書きせずに
  `Accept-Encoding` を追記すること**だけを確認する。実測では `compression` は `vary` を追記するため
  `trpc-accept, Accept-Encoding` になり、衝突しない。
- **閾値**。既定の 1KB 未満は圧縮しない挙動のままでよい（`build.catalog` のような 159B の応答は
  圧縮するとかえって増える）。
- 圧縮対象を絞る `filter` は入れない。この API は公開ビルドデータが主で、
  応答本文へ攻撃者が制御する文字列と秘密情報が同居する形（BREACH が問題になる形）を持たない。

### D2. 回帰ゲートを1本置く

圧縮は「入れたら見えなくなる」種類の設定で、ミドルウェアの順序が変わると黙って無効化される。
`server/_core/compression.test.ts` を新設し、実サーバーを起動して次を確認する
（Phase 24 の `bodyLimits.test.ts` と同じやり方）。

1. `Accept-Encoding: gzip` を付けた 1KB 超の JSON 応答に `Content-Encoding: gzip` が付く。
2. 受信バイト数が非圧縮時より明確に小さい。
3. `Accept-Encoding` を付けない要求は非圧縮で返り、本文が壊れない。

## 4. 受入条件

1. 本番 API で `build.guideHistory` に `Content-Encoding: gzip` が付き、
   受信バイト数が **414,137 → 2万バイト未満**になる。
2. ~~`Vary` に `Accept-Encoding` と `Origin` の両方が残り、GitHub Pages からの CORS が壊れない。~~
   **【2026-09-11 差し替え】** GitHub Pages からの要求で `Access-Control-Allow-Origin` が残り、
   圧縮が既存の `Vary`（`trpc-accept`）を上書きせずに `Accept-Encoding` を追記する
   （`Origin` の欠落は圧縮導入前からの既存不具合。§2 D1 の訂正・§6 を参照）。
3. `Accept-Encoding` を送らないクライアントに従来どおり非圧縮で返る。
4. `pnpm check` / 全テスト / `build:api` / Pages ビルドが green、ゴールデン比較は全セクション一致。
5. `/updates` を **Chrome で確認**し、表示内容が変わっていないこと（`D:\my-app2` のブラウザ確認ルール）。

## 5. 採用しなかった案: イベント本文の正規化

計画書が提案していた「イベント本文をバッチ単位に正規化して返す」案も試算した。
`eventTemplates` 辞書（24件）を足し、キャラクター側のイベントを `{ date, template }` だけにする形。

| 案 | 生 | gzip 後 |
| --- | ---: | ---: |
| 現行 | 396.2kB | 17.3kB |
| `summary` を落とすだけ | 305.1kB | 13.5kB |
| **正規化（テンプレ辞書24件）** | **111.7kB** | **9.7kB** |

**見送る。** D1 を入れた後で正規化が追加で削るのは 1 リクエストあたり約 8kB にすぎず、
その対価として API の形が変わり、クライアントにテンプレート解決の処理が増え、
ゴールデン比較の `history` セクションと11本のバッチテストの期待値が動く。
`/updates` は全画面のなかで訪問頻度が低く、この複雑さに見合わない（CLAUDE.md §1 の YAGNI、
「迷ったらより単純な方」）。

再検討する条件を決めておく:

- `/updates` の表示が体感で遅く、実測で JSON パースが支配的だと分かったとき
- キャラクターが 248 から大きく増え、生の応答が 1MB を超えたとき
- 更新履歴を差分取得したい要件（ページング・更新日フィルタ）が出たとき

### 付随して見つけた点（本設計では直さない）

キャラクターのイベントが持つ `summary` は、**`/updates` の画面が一度も描画していない**
（テーブルが出しているのは `date` / `title` / `changes` / `rationale` だけ）。
85.8kB がまるごと表示に使われていない。これを消すのは応答形の変更なので、
正規化を実施するときに一緒に扱う。単独では D1 の後に 4kB 弱しか効かない。

## 6. 残課題（本設計の対象外）

- 正規化と `summary` の除去（§5）。
- **`Vary: Origin` の欠落（既存不具合、2026-09-11 発見）**。CORS は要求元を反射した
  `Access-Control-Allow-Origin` と `Allow-Credentials` を返すのに、tRPC が `Vary` を `trpc-accept` で
  上書きするため `Origin` が残らない。共有キャッシュが挟まると、ある要求元向けの応答が別の要求元へ
  返る可能性がある。**現状の実害は低い**: Railway の前段にキャッシュする CDN が無く、tRPC の応答は
  `Cache-Control` を持たない（ヒューリスティックキャッシュの対象にもならない）。直すなら tRPC の
  `responseMeta` で `vary` を `trpc-accept, Origin` として返す形が候補。別の修正設計で扱う。
- レスポンスキャッシュ（`Cache-Control` / ETag）は入れない。更新履歴は不定期更新で、
  現在は tRPC の既定どおり毎回組み立てた結果を返している（プロセス内キャッシュは実装済み）。
