## 2. 重大な指摘（着手前に解消が必須）

### R-01【重大 / P1-01】信頼プロキシの設定が無いと IP 制限が全利用者を巻き込む

- **該当**: `server/_core/index.ts`（`app.set("trust proxy", ...)` が存在しない）、指示書 §3 必須要件「`X-Forwarded-For` を利用する場合は信頼する Proxy 範囲を考慮する」
- **指摘**: Express 4 の `trust proxy` の既定は `false`。Railway は前段にプロキシを持つため、`req.ip` は**全リクエストで同一のプロキシ IP** になる。この状態で IP 単位のレート制限を入れると全利用者が1つのバケットを共有し、上限に達した瞬間に正常利用者まで 429 になる。指示書は「考慮する」としか書いておらず、実装者が本番構成を推測して決める余地が残っている。
- **推奨対応**: 設計書で `app.set("trust proxy", 1)`（Railway の1ホップ）を明記し、`X-Forwarded-For` の**右端から1ホップ分**を採ることを確定させる。合わせて、1ホップ固定で右端しか見ないためヘッダ偽装で任意 IP を名乗れないことを非機能要件に書く。

### R-02【重大 / P1-01】tRPC バッチのため Express 層では procedure 別の制限を実装できない

- **該当**: `client/src/main.tsx:50`（`httpBatchLink`）、`server/_core/index.ts:88-99`（`/api/trpc` へ `createExpressMiddleware`）
- **指摘**: `httpBatchLink` は複数 procedure を1 HTTP リクエストへまとめる。Express ミドルウェアからは「このリクエストに `build.lookup` が何件含まれるか」が分からない（GET なら `input` クエリの解析、POST なら本文の解析が要る）。指示書は `build.lookup` / `feedback.submit` / `auth/github/exchange` にそれぞれ別の上限を求めているが、tRPC 配下の2つは Express 層だけでは実現できない。さらに R-05（POST 化）を行うと URL から procedure 名が消えるため、Express 層での判別は原理的に不可能になる。
- **推奨対応**: 層を分けて設計する。**(A) Express 層** = `/api` 全体の粗い IP 上限（連打の遮断）。**(B) tRPC middleware 層** = `build.lookup` / `feedback.submit` の procedure 別上限。`auth/github/exchange` は tRPC 外なので (A) と同じ仕組みを個別に適用する。

### R-03【重大 / §15 PR分割】P1-01 と P2-04 の実施順序が未確定

- **該当**: 指示書 §15「PR 1 公開API保護（レート制限・UID POST 化）」
- **指摘**: R-02 のとおり、POST 化するかどうかがレート制限の実装場所を決める。同一 PR に両方を入れると、レビュー時に「POST 化前提で書かれたレート制限」と「POST 化」が同時に載り、片方だけを差し戻せない。
- **推奨対応**: PR 内でも順序を固定する（**先に POST 化 → 後にレート制限**）か、はじめから tRPC middleware 方式を前提に設計して順序依存を消す。正本では後者を採った。

### R-04【重大 / P1-02】Last Known Good だけでは外部障害時の応答が遅延したまま

- **該当**: `server/gameProviders.ts:93-105`（`createTimedLoader`）、`:62-90`（`fetchJson` の 14 秒タイムアウト）、`server/enkaFallback.ts:90-104`（`getStaticIndex`、5 秒 × 8 エンドポイント）
- **指摘**: 指示書のフローは「期限切れ → 取得 → 失敗 → LKG 返却」。このままだと**外部障害中は毎リクエストが外部取得を試行する**。HTTP 200 は返せても、GI/ZZZ 経路は毎回タイムアウト分（最大 14 秒）待ってから LKG を返すことになり、「可用性向上」という目的を半分しか満たさない。同時接続が滞留し、レート制限の in-flight とも噛み合わない。既存の HSR 側（`getStaticIndex`）も同じ構造で同じ問題を抱えている。
- **推奨対応**: **失敗時の再試行抑止（negative caching）を必須要件に追加**する。取得失敗時は「次回再試行時刻」（既定 60 秒後）を記録し、その間の要求には外部取得を試みず即座に LKG を返す。HSR 側にも同じ扱いを入れて3ゲームで挙動を揃える。

### R-05【重大 / P2-04】`build.lookup` の mutation 化は「維持すべき既存仕様」と衝突する

- **該当**: `server/routers.ts:88-104`、`client/src/pages/Home.tsx`、指示書 §9 推奨および §13「二重クリック等の in-flight 排除を維持」
- **指摘**: query → mutation の変更は、router の意味論・クライアントの `useQuery` → `useMutation`・React Query のキャッシュ・in-flight 重複排除・エラー表示のすべてを書き換えることになる。指示書自身が §13 で「in-flight 排除を維持」を非変更条件に挙げているが、mutation 化はその土台（クエリキャッシュ）を外す変更であり、自己矛盾している。
- **推奨対応**: tRPC 11.18.0 には **`httpBatchLink({ methodOverride: "POST" })`** と **`createExpressMiddleware({ allowMethodOverride: true })`** があり、**router もクライアント呼出も一切変えずに全 query を POST 化**できる。導入済みパッケージの型定義で実在を確認済み（`@trpc/client` の `HTTPLinkBaseOptions.methodOverride?: 'POST'`、`@trpc/server` の `allowMethodOverride?: boolean`）。これを正案とする。副作用の確認結果: `allowMethodOverride` は GET を禁止せず POST を追加で受けるだけなので、CI の `curl "$API_BASE_URL/api/trpc/build.guideHistory"`（GET）はそのまま通る。

## 3. 中程度の指摘（設計書へ取り込むべき）

### R-06【中 / P1-01】「UID を平文保存しない」と「UID 単位で制限」が矛盾して読める

- **該当**: 指示書 §3 推奨例と必須要件
- **推奨対応**: レート制限キーを **UID の HMAC-SHA256（プロセス起動時に生成する一時鍵）を16進16文字へ切り詰めた値**と定義し、ログ・メトリクス・エラー本文のいずれにも出さないと明記する。

### R-07【中 / P1-01】多重インスタンス時の前提が書かれていない

- **該当**: `railway.toml`（レプリカ指定なし）
- **推奨対応**: インメモリ方式は**単一インスタンス前提**であることを設計書に明記し、スケールアウトすると実効上限が概ねインスタンス数倍になることを残課題として残す。共有ストア（Redis 等）の導入は今回のスコープ外とする（YAGNI）。

### R-08【中 / P1-01】キャッシュヒットの区別は実現できない

- **該当**: 指示書 §3「キャッシュヒット時と外部APIアクセス時を区別できればなお良い」、`server/buildAdvisor.ts:849-860`
- **指摘**: tRPC middleware は `lookupGameBuild` の前に走るため、カウント時点ではキャッシュヒットか否かが分からない。事後に「ヒットならカウントを戻す」方式は、UID キャッシュの TTL が 1〜10 分であるため同一 UID を無制限に回せる穴になる。
- **推奨対応**: **区別しない**と確定させ（単純な方を選ぶ）、上限値はキャッシュヒット込みで妥当な水準に置く。

### R-09【中 / P1-01】429 応答の形式が未定義

- **推奨対応**: (1) tRPC 層は `TRPCError({ code: "TOO_MANY_REQUESTS" })` を投げる（HTTP 429 へ写る）。(2) Express 層は `Content-Type: application/json` の 429 を返す（`safeTrpcFetch` は JSON をそのまま通すため、既存のクライアント処理を壊さない）。(3) 双方に `Retry-After`（秒）を付ける。

### R-10【中 / P1-01】除外すべき経路が挙がっていない

- **該当**: `server/_core/index.ts:34-38`（OPTIONS を 204 で即返す）、`:76-78`（`/api/health`）、`railway.toml`（`healthcheckPath = "/api/health"`）
- **指摘**: `/api/health` は Railway のヘルスチェックが定期的に叩くため、レート制限に含めるとデプロイ時にヘルスチェックが 429 で落ちうる。CORS プリフライト（OPTIONS）も数えるべきではない。指示書にはどちらも記載が無い。
- **推奨対応**: レート制限は CORS 設定の**後**に配置し、`OPTIONS` と `/api/health` を除外することを必須要件に追加する。

### R-11【中 / P1-03】`CACHE_MAX_ENTRIES = 512` の実効値は3倍

- **該当**: `server/buildAdvisor.ts:776`（`lookupCache`）、`server/gameProviders.ts:750-751`（`genshinCache` / `zzzCache`）
- **指摘**: `UidResponseCache` は3インスタンス存在するため、512 は**合計 1,536 件**を意味する。1件は全キャラクター分の正規化済みビルド結果であり、数十〜数百 KB になり得る。上限値の根拠が示されていない。
- **推奨対応**: 初期値を **256（合計 768 件）** とし、実測してから引き上げる。設計書 §10 の要確認事項として残す。

### R-12【中 / P1-03】LRU 化が既存の `set` / `getEntry` と噛み合わない

- **該当**: `server/buildAdvisor.ts:751-773`
- **指摘**: (1) `Map.set` は**既存キーの更新では挿入順を変えない**ため、LRU にするには更新時も `delete` → `set` が要る。(2) `getEntry` は期限切れ時に `delete` する副作用を持ち、`size` を観測する既存テストがこの掃除を前提にしている。`get` 時の再挿入を足すと、この既存テストの期待値と衝突しうる。指示書はどちらにも触れていない。
- **推奨対応**: `set` と `get` の両方で「delete → set」を行うことを明記し、既存の UID キャッシュテストを壊さないことを受け入れ条件に入れる。

### R-13【中 / P2-01】エラー分類の現状認識に一部ずれがある

- **該当**: `server/enkaFallback.ts:485-494`
- **指摘**: 現状は `JSON.parse(raw || "{}")` が HTML で `SyntaxError` を投げ、外側の `catch` が `BAD_GATEWAY` へ落とす。つまり指示書が新規要件として挙げた「HTML 等 JSON 以外 → BAD_GATEWAY」は**すでにそうなっている**。一方で「404 かつ HTML 本文」も現状 `BAD_GATEWAY` になり、新フロー（status を先に見る）では `NOT_FOUND` へ変わる。これはユーザー向けメッセージの変更なので、非変更条件に触れないことを明示する必要がある。
- **推奨対応**: 変更前後の分類表を設計書に載せ、「変わるのは 429 / 5xx / タイムアウトの文言と、HTML 404 の分類」であることを明記する。

### R-14【中 / P2-01】`characters.length === 0` の判定が新フローから落ちている

- **該当**: `server/enkaFallback.ts:489`（`!response.ok || !data.characters.length`）
- **指摘**: 現状は HTTP 200 でもキャラクターが0件なら `NOT_FOUND` を投げている。指示書の新フロー（fetch → status → JSON → 静的カタログ → normalize）にはこの判定が現れない。そのまま実装すると、公開キャラクターが0件の UID で空の結果が返る回帰になる。
- **推奨対応**: 「normalize 後に0件なら `NOT_FOUND`」を維持要件として明記する。

### R-15【中 / P2-02】案 A の中身が未定義で、このままでは実装できない

- **該当**: `client/src/lib/safeTrpcFetch.ts:27-45`、指示書 §7 推奨案A
- **指摘**: 「通常の HTTP エラーとして扱えるクライアント設計へ変更する」だけでは、既存の擬似エラーが存在する理由（HTML 応答で `JSON.parse` 例外になり、React Query に読めないメッセージが出る）を解消できるか判断できない。
- **推奨対応**: 案 A の具体形を「**非 JSON 応答のとき `Response` を返さず、日本語メッセージ付きの `Error` を throw する**」と定義する。`httpBatchLink` は fetch の reject を `TRPCClientError.from(cause)` で包み、**そのバッチに含まれる全 operation へ同じエラーを配る**ため、件数不一致も `path` の誤りも原理的に発生しない。既存のメッセージ文言はそのまま流用できる。

### R-16【中 / P2-03】非同期化の具体形が未定義で、取りこぼし以外のリスクがある

- **該当**: `server/routers.ts:95-103`
- **指摘**: 単純に `await` を外すと、`recordLookupAnalyticsEvent` が reject したとき `unhandledRejection` になる。また「timeout を付ける」は**待つのをやめる**だけで、DB 側の接続・トランザクションは解放されない。
- **推奨対応**: `void recordLookupAnalyticsEvent(...).catch(error => console.error(...))` の形を明記する。timeout は付けない（待たないので不要）。プロセス終了時の取りこぼしを許容することを設計書 §7 リスクへ明記する（方針自体は指示書どおり）。

## 4. 軽微な指摘

### R-17【小 / P3-01】ルート列挙の抜けと、再発防止の具体化

- **該当**: `client/src/App.tsx:64-72`
- **指摘**: 列挙から漏れているのは `/admin/display` のほかに `/404` もある。ただし `/404` は `404.html` で足りるため対象外でよい。また、ルート追加のたびに workflow の更新を忘れる構造そのものは残る。
- **推奨対応**: `admin/display` を追加したうえで、CI に「`App.tsx` の `Route path` 一覧（`/` と `/404` と catch-all を除く）⊆ 生成済みディレクトリ」を検査するステップを入れる。

### R-18【小 / P4-01】対象ファイルの列挙に生成物が漏れている

- **該当**: `server/batch17ConstellationData.generated.ts`（141,541 バイト）
- **推奨対応**: 生成物は分割対象外（生成器側の責務）と方針を明記する。

### R-19【小 / §15】P4-01 は別スコープ

- **指摘**: 指示書自身が「P1/P2 完了後に別 PR」と書いているとおり、巨大ファイル分割は挙動不変のリファクタリングであり、公開 API 保護・耐障害性とは受入条件も検証方法も異なる。「1 設計書 = 1 スコープ」の原則に反する。
- **推奨対応**: 正本の修正設計書からは外し、リファクタリング計画書として別立てにする。

### R-20【小 / §16】完了条件にゴールデン比較が無い

- **該当**: `scripts/golden-snapshot.mjs`

- **推奨対応**: 受け入れ条件に `node scripts/golden-snapshot.mjs` の全セクション一致を追加する。
