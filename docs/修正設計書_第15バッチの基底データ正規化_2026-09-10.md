## 1. 目的・背景

### 1.1 現状（前提コミット `0822df2` で実測）

第15バッチ20名（HSR 8 / 原神 8 / ZZZ 4）は、基底データを持たず**2箇所で API 境界上書き**されている。

| 経路 | 上書き箇所 | 使う関数 |
|---|---|---|
| UID 照会 | `server/routers.ts` の `applyBatch15CuratedOverrides(result)` | `server/batch15CuratedData.ts` |
| 図鑑（UID不要） | `server/characterReference.ts:76-81` の `batch15GuideFor` / `batch15PartyFor` / `batch15ConstellationFor` | `server/batch15{Guides,Parties,Constellations}.ts` |
| 更新履歴 | `server/routers.ts` の `applyBatch15History(guideUpdateHistory())` | `server/batch15History.ts` |

このため次の不整合が残っている（すべて前提コミットで実測）。

1. **メタデータ日付が基準日のまま**: `CHARACTER_GUIDE_METADATA` の20名は `dataAsOf` / `updatedAt` とも `2026-08-18`（基準日）で、応答上の `2026-09-05` は `batch15GuideFor` / `applyBatch15History` が上書きしている値。監査スクリプトは基底メタデータを見るため「精査済みなのに日付が基準日のまま」と警告する。
2. **推奨PTが基底の `generated-*` のまま**: `partyRecommendationsFor("hsr", "御空")` は `generated-hsr-御空-1` を返す（自動生成）。応答上の3案は `batch15PartyFor` が差し替えている。
3. **`communitySources` が空**: `batch15Parties.ts:45` は `communitySources: []`。`assertPartyCatalogIntegrity()`（`partyRecommendations.ts:1230`）の契約「各案に `communitySources` 1件以上」を満たさないため、そもそも基底カタログへ登録できない。
4. **凸の基底データが無い**: 20名とも `constellationProfileFor` は `preparing` を返し、`batch15ConstellationFor` が curated を供給している（20名の source ID はすべて一意に解決できる。§4.3 の表）。
5. **根拠メモが無い**: `docs/batch-15-research-notes.md` が存在しない（第1〜14・16・17 は全て存在する）。

### 1.2 なぜ直すか

- 上書き経路が残る限り、**新しい解決経路を足すたびに「第15バッチにも同じ上書きを足したか」を人が覚えておく必要がある**。実際に Phase 20 の R8（図鑑の凸索引統一）では、第15バッチ上書きが凸にも優先されるという例外を受入条件へ書き足す必要が生じた。
- 監査スクリプト（親リポ `hoyoverse-character-audit`）が基底メタデータを正としているため、20名分の誤検知が恒常的に出る。
- 第16バッチ以降は基底直接更新へ戻しており、第15バッチだけが例外として残っている。

## 3. 全体方針

**「上書きを消す」ではなく「基底へ移してから上書きを消す」**。1コミットで消すと差分が読めなくなるため、データの移設（応答が変わらない）と経路の撤去（応答が変わらないことの確認）を分ける。

同名で複数 source ID を持つ `三月なのか` の扱いが本設計の中心的な設計判断になる。

### 3.1 `三月なのか` 問題

- `hsr:1001`（存護）と `hsr:1224`（巡狩）は、公開メタデータ上いずれも `providerName: "三月なのか"`（`identityCatalogSnapshot` で実測）。`CURATED_IDENTITIES` に 1224 の登録は無く、`variantOf` は `null` になる。
- 第15バッチのガイドは**存護（1001）専用**で、現状は `batch15CuratedData.ts:43` の `isSafeBatch15Identity` が `sourceId === "1001"` を確認して適用を絞っている。
- したがって、ガイドを名前キーの `GUIDE_OVERRIDES["三月なのか"]` へそのまま移すと、**1224（巡狩）の UID 照会にも存護のビルドが適用される回帰**になる（現状 1224 は `generatedHsrGuide` の crit ビルドを返す）。

**採用する方式**: HSR の個別ガイド解決に **source ID キーの索引を1段追加**し、`三月なのか` の存護ビルドだけをそこへ登録する。

```ts
// server/buildAdvisor.ts
/** 同名で複数の実装がある場合だけ使う source ID キーの個別ガイド。名前キーより優先する。 */
const GUIDE_OVERRIDES_BY_SOURCE_ID: Record<string, GuideDefinition> = {
  "1001": /* 三月なのか（存護）の第15バッチ確定ガイド */,
};

export function guideFor(name: string, path: string, identity?: Pick<CharacterIdentity, "variantOf" | "sourceId">): GuideDefinition {
  const byId = identity?.sourceId ? GUIDE_OVERRIDES_BY_SOURCE_ID[identity.sourceId] : undefined;
  const individualGuide = byId ?? (identity?.variantOf ? undefined : GUIDE_OVERRIDES[name]);
  // 以降は既存のまま
}
```

- 図鑑側（`characterReference.ts` の `baseGuideFor`）は、R8 で導入した名前→source ID 索引を使って identity を解決してから `guideFor` に渡す。これで図鑑の `三月なのか` は従来どおり存護のビルドを表示する。
- **退けた代替案**: 名前キーのまま `guideFor` 内で `sourceId === "1224"` を除外するガードを書く方式。1行で済むが、名前キーの表に ID の例外条件が埋まり、次に同名 ID が増えたときに同じ分岐が増える。[character-identity-foundation.md](character-identity-foundation.md) の ID 主キー方針とも合わないため採らない。
- 凸は既に `game:sourceId` キー（`CURATED["hsr:1001"]`）のため、この問題は起きない。推奨PT・メタデータはカタログ名が主キーで、カタログには `三月なのか` が1件しか無いため、存護として登録すれば足りる（1224 は図鑑に出ない）。

### 4.4 推奨PTの移設

- 登録は他バッチと同じ `datedOptions(date, resetTargetChanges)` を使う。第15バッチ用に `const batch15Options = datedOptions("2026-09-05", true);` を追加する（第12〜14・16と同じく `targetChanges: []` を維持するため `resetTargetChanges = true`）。

### 4.6 履歴イベントの移設

## 10. 決定事項（2026-09-10 確定）

起票時の未確定3件は、下記の根拠で確定した。**本設計書に未確定事項は無く、B15-0 から着手できる。**

### D1: サイト全体イベントは日付昇順へ統一する（旧 Q1）

- 根拠（前提コミットで実測）: `client/src/pages/GuideHistory.tsx:28` は `siteEvents` をソートせず配列順で描画する。基底 `SITE_EVENTS` は日付昇順（2026-08-18 群 → 第16 2026-09-07 → 第17 2026-09-08）だが、`applyBatch15History` が第15バッチ（2026-09-05）を先頭へ差すため、**公開ページの並びが現状すでに不揃い**になっている。並びを固定するテストは無い（`guideUpdateHistory.test.ts:10` は `length > 0` のみ）。
- 決定: 先頭配置は上書き実装の副作用であり仕様ではないため、基底へ畳み込む際に日付昇順へ揃える。§2.1 に **V4** として許可済み。
- 退けた案: 現状の先頭配置を `SITE_EVENTS` の先頭要素として再現する。不揃いな並びを正本の配列へ恒久的に焼き付けることになり、次バッチで同じ判断を繰り返すため採らない。

### D2: 親リポの監査スクリプトはコード変更不要。文書だけ更新する（旧 Q2。2026-09-10 に実測して訂正）

**起票時の想定（「監査スクリプトが `batch15*` を名指し import しており、撤去すると解決不能な import で停止する」）は誤りだった。** 着手前に親リポを実測した結果は次のとおり。

- `hoyoverse-character-audit/scripts/audit-characters.mjs` は `batch15*` を名指しで import していない。`loadLatestBatchOverrides()`（同 53〜75行）が `server/` を `readdirSync` して `batchNNGuides.ts` の**最大番号を動的に検出**し、`batch${id}{Guides,Constellations,Parties}.ts` を `.catch(() => null)` 付きで読む実装である。
- 実測: 検出される番号は `[15, 17]` で**採用されるのは 17**。`batch17Guides.ts` の公開名は `BATCH_17_CHARACTER_NAMES` で、スクリプトが探す正規表現 `/^BATCH\d+_CHARACTERS$/` に一致しないため `latestBatchNames` は**空**。`batch17Constellations.ts` は存在しないため `constellationFor` も `null`。つまり**第15バッチの上書きは現時点で監査から見えていない**（リファクタリング計画書 §4.3 #7 が指摘した判定のずれ）。
- 親リポの `.claude/` 配下に `batch15` を参照する**コードは1件も無い**（`grep -rl --include=*.mjs --include=*.js --include=*.ts` で確認）。言及は `hoyoverse-character-audit/references/detection-rules.md:47` ほかの**文書のみ**。
- 決定:
  1. **B15-7 は親リポの作業を待たずに実施してよい**（起票時の順序制約は撤回）。`batch15*.ts` を削除しても検出番号が `[17]` になるだけで、スクリプトの挙動は変わらない。
  2. B15-0 は「監査スキルの**文書**を実態へ更新する」作業へ差し替える。対象は `detection-rules.md:47` の「第15バッチだけは基底ファイルへ畳み込まれず…」の記述。撤去後に実施してよい。
  3. `loadLatestBatchOverrides()` 自体は、B15-7 完了後に override 形式のバッチが1つも無くなるため**死にコードになる**。その撤去とスクリプトの移設（計画書 §4.3 #7）は本設計の範囲外とし、スキル再設計側で扱う。本設計では動かさない。

### D3: スキル再設計の完了を待たない（旧 Q3）

- 決定: 本設計の着手条件は D2 の B15-0 だけとし、親リポ `修正設計書_hoyoverseスキル再設計_2026-09-08.md` の完了は待たない。
- 根拠: §4.1 の根拠メモ作成は「出典 URL と確認日を記録する」データ作業で、スキルの機構変更に依存しない。現行の `hoyoverse-character-curation` で実施できる。
- 実施順は §6 の B15-0 → B15-1 →（B15-2〜B15-6）→ B15-7 → 公開確認。スキル再設計の残り（メンバー名解決ゲート等）はその後に実施する。


### D4: 凸の `rankLabel` は基底の正準ラベルへ揃える（2026-09-10、B15-4 の実測で追加）

- 実測: `batch15Constellations.ts` の `rankLabel()` は HSR `Eidolon` / 原神 `Constellation`・`命座` / ZZZ `意象影画` を返し、基底 `characterConstellations.ts` の `LABELS` は `Eidolons` / `Constellations`・`命之座` / `心象电影`。**第15バッチ20名だけが他228名と違う英・中ラベルを返していた**（日本語は同一）。
- 決定: 基底へ移す。`CuratedEntry` 型は `rankLabel` を持たず `constellationProfileFor` が `LABELS[game]` を付ける設計のため、移設すると自動的に正準ラベルになる。§2.1 に **V5** として許可する。
- 退けた案: `CuratedEntry` に `rankLabel` を追加して第15バッチのラベルを保持する。20名のためだけに型と分岐を増やし、しかも不整合の側を恒久化するため採らない。
