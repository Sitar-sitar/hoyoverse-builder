## SEC-01: 256KB本文上限がmultipartに適用されない

根拠: [bodyLimits.ts](../server/_core/bodyLimits.ts) はexpress.jsonとurlencodedだけを制限。[index.ts](../server/_core/index.ts) のcreateExpressMiddlewareはmaxBodySizeを指定していない。固定されたtRPC 11.18系はmultipartを受け付け、input評価時にreq.formData()で読み込む。Node adapterのmaxBodySize未指定時はstreamサイズを制限しない。

隔離Expressで実コードのbody parser・appRouter・adapterを使用し、user=null、DB処理なしで検査した。512KB JSONは413、512KB multipartをfeedback.submitへ送ると400 BAD_REQUEST（FormDataのZod拒否）となった。**schema拒否の前に本文を読み込むため、400はメモリ保護の代わりにならない。** JSON-onlyの既存本文テストはこの欠落を検出しない。

影響: 未認証の送信者が通常入力サイズより大きなmultipartを送って解析資源を消費できる。複数要求時のOOMはコードからのリスク推定で、本番や大容量攻撃では検証していない。

修正方向:
- このアプリのtRPCが使うapplication/json以外を本文解析前に415で拒否する。OAuthのGET callbackは別経路として維持。
- adapterのmaxBodySizeも256KBへ明示し、Content-Lengthに依存しないstream上限を設定する。
- maxBatchSizeも明示し、巨大なoperation配列の事前解析負荷を制限する。
- JSON/urlencoded/multipart/octet-stream、Content-Lengthなし、chunked、単件/バッチについて、上限超過時にresolver・DBへ到達しないことを実HTTPで検証する。
- 一時検証ファイルは実行後削除済み。商品コードは変更していない。

## SEC-02: compressionの既知メモリリーク

根拠: [package.json](../package.json) のcompression指定は^1.8.1、[lockfile](../pnpm-lock.yaml)は1.8.1固定。[index.ts](../server/_core/index.ts)がpublic API全体へcompression()を登録している。

公式GHSA-vc2v-76pw-4v95 / CVE-2026-87776（2026-09-11公開、10-05更新）は1.8.2未満を対象とし、圧縮応答途中の切断でzlib streamが解放されずnative memoryが蓄積すると説明している。修正版1.8.2。添付の依存一覧にはこの直接依存が抜けている。

修正方向: compressionを1.8.2以上の安全な版へ更新しlockfileを再固定する。通常のgzip/Vary/CORS/guideHistory応答に加え、圧縮応答の途中切断後にstream・接続・メモリが回収される回帰検証を追加する。Northflank LBが切断をAPIへどう伝えるかは今回未実測で、実効攻撃頻度・本番OOMは断定しない。

## SEC-04: プロセス全体の上限・待機キュー

根拠: [buildAdvisor.ts](../server/buildAdvisor.ts)と[gameProviders.ts](../server/gameProviders.ts)はUID別in-flight共有とキャッシュ上限を持つが、異なるIP・UID全体の同時外部取得数は制限しない。[enkaFallback.ts](../server/enkaFallback.ts)のgetStaticIndexはcold cache時の取得Promise共有がなく、並行UIDで8 endpoint取得が重複し得る。[db.ts](../server/db.ts)のpoolはqueueLimitを設定せず、mysql2既定はconnectionLimit=10 / queueLimit=0（無制限）。

修正方向: UID loader全体のpermit、上限付きqueue、cache hitを圧迫しない分離、上流応答のstream byte cap、client中断の伝播を設ける。静的取得もsingle-flight化する。DB queue・query期限を明示する。サイズ・同時数は現行512MB/.2vCPUで正常応答サイズを測って決め、添付の「10〜20」を無条件採用しない。過負荷時はtRPC形式の429/503とRetry-Afterを保持する。

受入: 別IP/UID・異常上流・slow stream・body cap・cancel・permit解放・queue上限を隔離環境で確認し、上流取得数とpeak RSSを測る。本番負荷試験は今回未実施。

## SEC-05: CI権限と自動検出

根拠: [deploy-pages.yml](../.github/workflows/deploy-pages.yml)はworkflow全体にpages:write / id-token:writeを付与し、依存install・テスト・buildも継承する。外部Actionsはmajor tag参照。[validate-api.yml](../.github/workflows/validate-api.yml)はcontents:readで適切。

GitHub RESTでmain-protection active、deletion/non_fast_forward/required validate、bypassなしを取得。Code scanning Default Setupはnot-configured。Dependabot alerts APIは403「Dependabot alerts are disabled for this repository」と返した（token scopeについての補足も表示）。npm/Actionsの週次Dependabot設定はalertsの有効化とは別物である。

修正方向: workflow全体contents:read、deploy jobだけpages/id-token write。Actions完全SHA固定＋Dependabotで更新追従。依存監査ゲート、CodeQL、Dependabot alertsを設定確認・有効化する。有料機能への切替を前提にせず利用可否を確認する。
受入: build環境ではOIDC書込みtoken取得権限がないこと、artifact uploadとdeployは継続成功、CodeQL/依存監査が対象PRで結果を出すこと。

## SEC-06: 本番DB TLSを起動時に検査する

[databaseConnection.ts](../server/_core/databaseConnection.ts)はCA未指定時にuriだけを返す。[db.ts](../server/db.ts)はlazy pool生成の例外をcatchしてnullへ戻す。したがって未設定・読取不能CAでもhealthだけ200になり得る。

現行CA/TLS接続は移行時に確認済みで、今回ライブ資格情報や通信cipherを再取得していない。現行接続を平文と断定しない。

修正方向: productionかつDB利用時にCA指定・読取可能・妥当な接続形式をAPI/Job共通で起動時検査し、欠落時は非zero終了する。TLS検証を緩めるfallbackは禁止。ローカルDBなしの工具用途は維持。CAなし/不存在/不正CA/host mismatch拒否、正しいCA成功を検証する。

## SEC-07: CORSとCSRFは同じ対策ではない

[index.ts](../server/_core/index.ts)は許可Originを追加可能で、許可外でもACAOを付けずnext()する。ブラウザによる読取/非simple要求制限であり、サーバーで処理を拒否する機構ではない。

今回healthへの4本のlive要求で、正式Pagesは200/ACAO一致/credentials=true、localhost:5178・localhost:5173・review.example.invalidはACAOなし。全Originのallowlist不在を網羅的に証明したわけではないが、添付のlocalhost残留懸念は今回の値では再現しなかった。

現在の管理mutationはJSON/Zodによって単純formでの変更を制限しており、任意管理変更CSRFを今回確認していない。ただしSameSite=None Cookie経路があるため、CORSだけをCSRF対策の根拠にしない。

修正方向: production正式モードで許可Originを制約し、余計なOrigin設定を起動拒否。CIに拒否側の検査を追加する。Cookie認証の状態変更はOrigin検証またはCSRF tokenで保護し、Bearer/CLIのOriginなし要求とOAuth callbackを明示的に区別する。第三者Cookie遮断条件の正常ログイン・管理保存も回帰検証する。

## SEC-08: OAuth期限と認証負系統合テスト

[githubAdminAuth.ts](../server/_core/githubAdminAuth.ts)のGitHub token/user fetchはsignal/deadlineなし。UID取得の14秒timeoutを認証通信にも存在すると読み替えない。外部障害時に処理が長く残り得る。

認証の署名algorithm/issuer/audience、allowlist再確認、交換hash/期限/条件付きUPDATEは良好。ただし[githubAdminAuth.test.ts](../server/githubAdminAuth.test.ts)の3テストはID解析・allowlist・return pathだけ。JWT改ざん/期限/issuer/audience、OAuth state不一致、交換期限・再使用・同時消費の統合回帰証拠にはならない。条件付きUPDATEは単回消費の実装根拠で、競合テストPASSとは区別する。

修正方向: OAuth fetch deadline・応答cap・固定安全エラーと、上記失敗ケースのHTTP/DB隔離テストを追加。署名なし/非管理者/allowlist削除で管理resolverが呼ばれないことを確認する。logoutは現在token保存/Cookie消去であり全JWT失効ではない。必要なら後続のsession失効設計を別途決める。直ちにログアウト認証突破と判断しない。

## SEC-09: 生例外・CSP

[db.ts](../server/db.ts)、[routers.ts](../server/routers.ts)、[githubAdminAuth.ts](../server/_core/githubAdminAuth.ts)で例外全体をログへ出し、[notification.ts](../server/_core/notification.ts)では上流本文も出す。mysql2/ORMエラーにSQL・入力・接続metadataが含まれ得る。公開レスポンスの固定メッセージは概ね適切だが内部ログは別の境界である。

公開PagesはCSP header/metaともなし。BearerはsessionStorageにあり、将来XSSが入ると読まれる。Reactのフィードバック表示から現行stored XSSは確認しなかった。なお添付の「dangerouslySetInnerHTMLなし」は厳密には誤りで、[chart.tsx](../client/src/components/ui/chart.tsx)に存在する。ただしChartContainerの使用は確認せず、不信入力到達も未確認。

修正方向: code/name/statusなどallowlist項目の共通logger、SQL/URL/資格情報/入力本文の秘匿化とテスト。Pages配信で有効なCSPを設計し、Google Fonts・画像・inline styles・生成scriptを棚卸しする。meta CSPはframe-ancestorsやReport-Only等に制約があり、添付の最小ポリシーをそのまま貼らない。OAuth・三ゲーム・管理表示と第三者Cookie遮断を回帰検証する。

## SEC-10: PR必須化

現行main rulesetは必須validate、強制push/削除禁止、bypassなし。PR必須ルールはない。独立レビューと履歴経路を強制するため追加を推奨する。緊急対応の手順・必要statusの発火条件を確認してから設定する。今回GitHub設定は変更していない。

## 実施した検証と限界

- 添付レビューを読み、本番main SHAをGitHub RESTで再確認。調査branchとの差分は文書・案内文・コメント中心で、該当workflow/lockfile/認証の動作ロジックに差異なし。
- audit --prod、公式advisory照合、GitHub設定のread-only API、live health/CORS4 Origin、公開HTML/CSP確認。
- 既存githubAdminAuth 3、rateLimitProcedures 8、bodyLimits 4、corsVary 5と隔離再現2、計22テストpass。greenは本文迂回修正済みを意味しない。追加2テストは欠陥の現状を確認するprobeであり、修正受入テストではない。
- 本番の攻撃・DoS・JWT偽造送信・大量要求・DB変更・秘密値読出し・依存更新・コード修正は実施していない。
- DB least privilege、実コンテナの全OS package/CVE、全ブラウザ、すべてのOrigin、LB切断伝播・大容量OOM・供給網の侵害不存在は未検証。
- セキュリティ修正の本番リリースはAPI/Pages同SHAで行い、公開後観察を中断/再開始する場合はその事実を記録する。レビュー完了を移行完了と読み替えない。
- Obsidianは更新していない。添付自体の書換えもしていない。
