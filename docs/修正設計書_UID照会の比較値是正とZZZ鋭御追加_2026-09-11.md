## 1. 目的・背景

### 1.1 HSR: MiHoMo 経路の「現在のステータス」と比較が最終値ではない（最重要）

**再現**（2026-09-11、ユーザーが画面で提示した公開 UID を本番 API `build.lookup` とMiHoMo の生応答で照合。UID は本書に記載しない）。
ショーケースの8名すべてで、「現在のステータス」が最終値ではなく、速度の比較が遺物ぶんの値で行われていた。

| キャラクター | 画面の速度 | 最終値（MiHoMo の `statistics`） | 速度目標（目標） |
| --- | ---: | ---: | ---: |
| 緋英 | 34 | 138 | 134 |
| 爻光 | 73 | 198 | 160 |
| 銀狼Lv.999 | 71 | 201 | 134 |
| キャストリス | **-8.0%** | 87 | （速度目標なし） |

**原因**: MiHoMo `sr_info_parsed` の各キャラクターは、ステータスを4種類返す。

| 項目 | 中身 | 緋英の速度 |
| --- | --- | ---: |
| `attributes` | キャラクター＋光円錐の基礎値 | 104 |
| `additions` | 遺物・軌跡などの加算分（割合も実数へ換算済み） | 34 |
| `properties` | 加算ステータスを割合と実数に分けた生の一覧 | 34（と割合） |
| **`statistics`** | **`attributes` ＋ `additions`＝戦闘外の最終値** | **138** |

`server/buildAdvisor.ts` の `parseCharacter` は、表示（`allStatsFor`）も比較（`comparisonFor`）も **`properties` だけ**を使っている。
これは Manus 時代の初期実装（2026-08-18 `19c5c93`）からで、Phase 18 の設計書も「MiHoMo は取得元の最終値」と誤って前提していた。
（`statistics` が最終値であることは、緋英の HP 2,950＝2,000＋950、攻撃力 2,083＝1,372＋711、爻光の速度 `additions` 97＝実数73＋基礎101×24% で確認した。）

さらに比較の照合（`STAT_MATCHERS` を `${field} ${name}` の連結文字列へ当てる方式）にも欠陥があり、本番で次の結果になっている。

| キー（HSR ガイドでの使用数） | 本番の比較 | 状態 |
| --- | --- | --- |
| `speed`（65名） | 遺物ぶんだけ（緋英 34） | **誤り** |
| `critRate`（38）/ `critDmg`（41） | 基礎 5% / 50% が抜ける（緋英 56.2%、最終は 61.2%） | **誤り** |
| `attack`（33） | `properties` で先に出る**攻撃力%**に当たる（火花: 目標3,600 と「63.0%」を比較） | **誤り** |
| `hp`（12）/ `defense`（4） | 正規表現が連結文字列に当たらず常に「未取得」 | **誤り** |
| `attackPercent`（4）/ `hpPercent`（4）/ `defPercent`（1） | 生データの名前に「%」が無く常に「未取得」 | **誤り** |
| `energyRecharge`（1） | `sp_rate` が照合に当たらず「未取得」。取れても MiHoMo の値は上乗せ分だけ（19.4%）で、Enka 経路・ゲーム内表記の基礎込み（119.4%）と違う | **誤り** |
| `breakEffect`（8）/ `effectHitRate`（14）/ `effectRes`（12） | 基礎値を持たない加算のみのステータスのため一致 | 正しい |

**MiHoMo は HSR の主取得元**なので、Enka フォールバック（Phase 18 で最終値を算出済み）に落ちない限り、**HSR の全84名の UID 照会の比較がほぼ全項目でずれている**。
装備変更の提案（`equipmentActionsFor`）もこの比較から作られるため、同じだけ誤っている。

### 1.2 ZZZ: 新特性「鋭御」とクラレッタ

クラレッタは 2026-09-09 の Ver3.2 前半で実装済み（Game8「前半ガチャ 2026年9月9日 12:00〜 ピックアップ：クラレッタ（新規）」、GameWith キャラ一覧 2026-09-10 に掲載）。
取得元（Enka `store/zzz/avatars.json`、2026-09-11 取得）の `ProfessionType` は7種で、`Armorer` はクラレッタ1名だけ。

| コード | アプリの表示 | 人数 |
| --- | --- | ---: |
| `Attack` / `Stun` / `Anomaly` / `Support` / `Rupture` / `Defense` | 強攻 / 撃破 / 異常 / 支援 / 命破 / 防護 | 17 / 12 / 12 / 8 / 5 / 5 |
| **`Armorer`** | **（未対応）** | **1** |

いまクラレッタが UID 照会に載ると、特性表示が**英語コードの「Armorer」のまま**になり（`ZZZ_PROFESSIONS[profession] ?? profession`）、
ロール共通ガイドが**強攻（`crit`）**に落ちて攻撃力で比較される。鋭御は**スキルダメージを防御力で計算する**特性で（GameWith）、攻撃力は主軸ではない。
Ver3.2 は配信済みなので、この表示はすでに利用者に出うる。

### 1.3 ZZZ: 防御力・HP の目標が常に「未取得」

ZZZ の最終ステータス（`finalZzzStats`）は、表示用（`display`）では防御力と HP を計算しているのに、比較用（`values`）に `defense` と `hp` のキーが無い。
次の9名の目標は、実値があるのに UID 照会で常に「未取得」になっている（2026-09-11、全58名のガイド目標と `values` のキーを突き合わせて確認）。

| キー | 目標に使っている既存キャラクター |
| --- | --- |
| `defense` | シーザー、ベン |
| `hp` | イドリー、シーザー、スターライト･ビリー、セス、リュシア、儀玄、照、蒼角 |

クラレッタの主目標は防御力なので、`defense` を足さないと登録しても比較できない。

### 1.4 ZZZ: 装備変更提案が HSR の部位名を返す（→ §1.6 の一部として Phase E で解消）

`server/buildAdvisor.ts:134` の `defaultSlotsForStat` は、`hp` / `hpPercent` / `defense` / `defPercent` について原神以外をすべて HSR の部位
（胴体・次元界オーブ・連結縄）として返す。部位はまずガイドのメインステータス欄から決まり、該当する記述が無いときだけこの既定値に落ちる。
ZZZ で既定値に落ちるのは **シーザー（HP・防御力）、セス・蒼角（HP）、潘引壺（HP%）**。いま実際に「胴体」などを提案しうるのは値のある潘引壺だけで、
§1.3 の修正で HP・防御力に値が入ると残り3名にも広がる。

### 1.5 HSR: Enka 経路の最終値が、遺物のサブと遺物セット効果を取りこぼしている（Phase A の実測で判明）

Phase A の受け入れ照合（同一 UID を両経路で正規化して突き合わせ）で発見した。**HP・攻撃力・防御力は ±1 で一致する一方、会心率・会心ダメージ・一部の速度/HP/攻撃力が一致しない**。
正しいのは MiHoMo 側（取得元自身が返す戦闘外の最終値＝ゲーム内のキャラクター詳細画面と同じ）で、**Enka 経路が過少に算出している**。原因は独立した2つ。

**E-1. 遺物サブステータスの型が `field: ""` のため、合算から丸ごと落ちている。**
Enka の `_flat.props` は、**メインに `Base` 付きの型、サブに `Base` なしの型**を使う（実データで確認）。

| 箇所 | 実データの型 | `properties.json` の `field` | 現行の扱い |
| --- | --- | --- | --- |
| 胴体のメイン | `CriticalDamageBase` | `crit_dmg` | 正しく加算 |
| 各遺物のサブ | **`CriticalChance` / `CriticalDamage`** | **`""`** | **`classify()` が `StatKey` を引けず "other" へ落ち、`statTotals` に入らない** |

`field` が空になるのは `CriticalChance` / `CriticalDamage` / `StatusProbability` / `StatusResistance` / `BreakDamageAddedRatio` / `SPRatio` の6種で、
**会心率・会心ダメージ・効果命中・効果抵抗・撃破特効・EP回復効率のサブが全て無視される**。
さらに `properties.json` はこれらの `percent` を `CriticalChance: false` のように `Base` 付きと食い違わせているため、**表示も壊れている**（サブが「会心率 0」と出る。生値 0.09072 を実数として `toFixed(0)` した結果）。

**E-2. 遺物セット効果（2セット・4セット）を一切適用していない。**
`relic_sets.json` は段階別の無条件効果を `properties` に持つが、現行は**セット名の表示にしか使っていない**。MiHoMo の `statistics` はこれを含むため、差がそのまま残る。
実測の残差は全てセット効果で説明でき、計算が一致した。

| キャラクター | 項目 | Enka | セット効果 | 補正後 | MiHoMo |
| --- | --- | ---: | --- | ---: | ---: |
| 爻光 | 速度 | 192.6 | 天命に従う旅の卜者 2セット `SpeedAddedRatio +0.06`（基礎101） | 198.7 | 198 |
| ホタル | 速度 | 174.9 | 劫火と蓮灯の鋳煉宮 2セット `+0.06`（基礎104） | 181.1 | 181 |
| キャストリス | HP | 8760 | 静謐な拾骨地 2セット `HPAddedRatio +0.12`（基礎2900.016） | 9108.0 | 9108 |
| キャストリス | 速度 | 95.0 | 亡国の悲哀を詠う詩人 **4セット `SpeedAddedRatio -0.08`**（基礎95） | 87.4 | 87 |
| カフカ | 攻撃力 | 2615 | 酩酊の海域 2セット `AttackAddedRatio +0.12`（基礎1261.26） | 2766.4 | 2766 |

**マイナスの効果もある**（亡国の4セット）ため、符号をそのまま扱う必要がある。
セット効果がこれらを持たないキャラクター（緋英・銀狼Lv.999・火花）は、速度・HP・攻撃力が一致していた——原因の切り分けとして整合する。

この2つは Phase 18（Enka フォールバック）からの既存不具合で、Phase A の変更が作ったものではない。
主取得元は MiHoMo なので**利用者に出るのは Enka へ降格したときだけ**だが、降格時に会心が大幅に過少評価され、装備提案まで誤る。

### 1.6 全ゲーム: 装備提案が、ガイド自身の推奨主ステータスと衝突する（PB-01 の調査で判明）

`equipmentActionsFor` は、不足ステータスに対応する主ステータス欄がガイドに無いとき、
`defaultSlotsForStat(...)[0]`（無ければ `guide.mainStats[0].slot`）という**既定の部位を1つ選んで「主ステータスを変更」を提案する**（[buildAdvisor.ts](../server/buildAdvisor.ts) 153〜160行）。

全251名のガイドの全目標について、この既定へ落ちる組み合わせを数えた。

| ゲーム | 既定へ落ちる目標 | 対象 | **その部位にガイドが別の主ステータスを指定している（＝衝突）** |
| --- | ---: | ---: | ---: |
| HSR | 36 件 | 33名 | **36 件（100%）** |
| 原神 | 18 件 | 18名 | **18 件（100%）** |
| ZZZ | 21 件 | 18名 | **21 件（100%）** |
| 計 | **75 件** | **69名** | **75 件（100%）** |

**既定の部位が正しかった例は1件も無い。** 例:

- ファイノン（HSR）: `hp` と `defense` が**同じ胴体**へ落ち、ガイドの「会心率 / 会心ダメ」と衝突する。同一部位へ相反する変更を2件返す。
- 符玄（HSR）: `defense` が胴体へ落ちるが、ガイドの胴体は「HP%」。
- アルハイゼン（原神）: `energyRecharge` が時計へ落ちるが、ガイドの時計は「元素熟知 / 攻撃力%」。
- シーザー（ZZZ）: `hp` と `defense` が**同じ IV** へ落ち、ガイドの「会心率 / 会心ダメージ」と衝突する（Phase B の D3 で比較が有効になると顕在化する）。
- セス・蒼角（ZZZ）: `hp` が IV へ落ちるが、ガイドの IV は「攻撃力%」——主目標の攻撃力を壊す提案になる。

同じ部位へ複数の目標が同時に落ちるのは6名（ファイノン・千冶・刃・符玄・シーザー・セス・蒼角）で、**相反する主ステータス変更を並べて表示する**。

既定の部位は「そのステータスを主ステータスに置ける部位」を返しているだけで、**ガイドがその部位に何を推奨しているかを見ていない**のが原因。
ガイドの主ステータスは出典で裏づけた推奨であり、それを崩す提案を出す根拠はない。

## 2. スコープ

### 2.1 IN

- **Phase A（HSR）**: MiHoMo 経路の表示と比較を最終値（`statistics`）へ切り替え、`field` を主キーにして照合する（§3 H1〜H4）。
- **Phase B（ZZZ のコード）**: 特性 `Armorer`＝「鋭御」の表示とロール共通ガイド（D1・D2・D6）、比較値への `defense` / `hp` 追加（D3）、ZZZ の希望主ステータス名（D7）。
  **装備提案の部位は Phase E が担当する（D4 は取り下げ。§3 D4）。**
- **Phase C（ZZZ のデータ）**: クラレッタのカタログ追加（第19バッチ、`hoyoverse-character-update` のモード C。D5）。
- **Phase D（Enka 経路の是正）**: 遺物サブの取りこぼし（E1）と遺物セット効果の未適用（E2）を直し、両経路の値を揃える（§3 Phase D）。
- **Phase E（装備提案の部位選択の是正・全ゲーム共通）**: ガイドが主ステータス欄を持たないステータスについて、部位を決め打ちした「主ステータスを変更」をやめる（§3 Phase E。PB-01）。
  **Phase B の D3 は、比較が有効になることで新たに3名ぶんの誤提案を生むため、Phase E と同時かその後にしか出せない。**

### 2.2 OUT

- Enka フォールバック経路の**算出の枠組み**（Phase 18 の基礎値・軌跡・光円錐の扱い）。Phase D は、その枠組みのまま**取りこぼしている入力を加える**だけで、式の考え方は変えない。
  （当初は Enka 経路すべてを OUT にしていたが、Phase A の実データ照合で §1.5 の2件が判明し、§9 の「両経路が一致する」を満たせないため Phase D として IN へ移した。）
- 原神の UID 照会（本書の不具合は再現していない）。
- 既存ガイドの**目標値そのもの**の見直し。比較が正しくなることで「未達」「達成」の見え方は変わるが、目標値は変えない（§7）。
- ロクシー（`zzz:1621`、2026-09-30 開始）。特性は既存の `Stun` で本書の変更は要らない。実装後にモード C で扱う。
- ZZZ の特性名の英語・中国語表示（現行でも日本語の表示名だけを返しており、強攻・撃破と同じ扱い）。
- 鋭御の固有メカニクス（残痕・重傷・暴傷の2回判定）の画面表現。戦闘中の仕組みで比較対象ではない。

## 3. 全体方針

### Phase A（HSR MiHoMo 経路）

**H1. 表示と比較の元を `statistics`（最終値）にする。**
`parseCharacter` で、`statistics` があればそれを最終値として使う。無い・空のときは `attributes` と `additions` を `field` ごとに足して作る（MiHoMo が `statistics` を作る式と同じ）。
どちらも無いときは **`properties` へ戻らず**、Phase 18 と同じく `statsStatus: "unavailable"` にして比較を「未取得」にする（最終値でない数字で比べない＝fail closed）。
最終値を使えたときは `statsStatus: "final"` と、MiHoMo 経路用の注記（「公開中のキャラクター・光円錐・遺物・軌跡を合算した戦闘外の最終値です。戦闘中・条件付き効果は含みません」）を返す。

**H1-b. 最終値を作れない MiHoMo 応答は「不完全な主取得元」として扱い、Enka を試す・キャッシュしない（DR-05）。**
現行の `requestMihomo` は、キャラクターが1名でも居れば応答を成功として `lookupCache` へ入れ、`lookupWithFallback` は主取得元が**例外を投げたときだけ** Enka を呼ぶ。
このままだと H1 で「全員 `unavailable`」になった応答がそのまま最大10分キャッシュされ、静的データから最終値を算出できる Enka が一度も試されない。
Enka 側には既に同じ保護がある（`isEnkaResultComplete` が false なら `lookupCache.set` を呼ばない）ので、MiHoMo 側もそれに揃える。

- **1名も最終値を作れない**場合は、`normalizeMihomoPayload` の後・キャッシュ格納の前に `TRPCError` を投げ、Enka フォールバックへ回す（Enka も失敗すれば従来どおり Enka のエラーを返す）。
- **一部のキャラクターだけ最終値が無い**場合は、その応答を返すが**キャッシュへ入れない**（Enka の部分欠落と同じ扱い。再取得で回復し得るため TTL 中固定しない）。
- これは Phase A の変更で新たに到達可能になる状態への対処であり、MiHoMo が正常な応答を返す通常時の挙動は変えない。

**H2. 比較の照合を、表示名の正規表現から `field` の対応表へ変える。**
Phase 18 が Enka 経路で作った `FIELD_TO_COMPONENT`（`hp`/`atk`/`def`/`spd`）と `FIELD_TO_STAT_KEY`（`crit_rate`/`crit_dmg`/`break_dmg`/`effect_hit`/`effect_res`/`sp_rate`）を
`server/enkaFallback.ts` から共有し、MiHoMo でも同じ表で `StatKey` を引く。対応表を二重に持たない（Phase 18 §4.2「表示名ではなく `StatKey` を主キーにする」を MiHoMo へ広げる）。

**H3. 割合キー（`attackPercent` / `hpPercent` / `defPercent`）は `properties` の割合項目の合計にする。**
`statistics` には割合の項目が無い。Enka 経路はこれらを「遺物・軌跡・光円錐の割合ボーナスの合計×100」としている（`enkaFallback.ts` の `totals.*.ratio * 100`）ので、
MiHoMo でも `properties` のうち `field` が `atk`/`hp`/`def` で `percent: true` の値を合計して同じ意味に揃える。

**H4. 表示ラベルと項目を Enka 経路に揃える。**
`statistics` の名称は「基礎HP」「基礎攻撃力」「基礎防御力」だが中身は最終値なので、`field` から「HP」「攻撃力」「防御力」と表示する。
同一 UID を MiHoMo と Enka のどちらで取得しても、「現在のステータス」の項目名と値が（端数を除き）一致することを目標にする。

**H5. EP回復効率は基礎100%込みで表示・比較する（2026-09-11 ユーザー決定）。**
ゲーム内の表記に合わせ、MiHoMo の `sp_rate`（上乗せ分）を **(1 ＋ `sp_rate`) × 100** に換算する（例: 19.4% → **119.4%**）。`statistics` に `sp_rate` が無いときは上乗せ 0＝100%。
Enka 経路はすでに `(1 + 合計) * 100`（`enkaFallback.ts` の `energyRecharge`）で基礎込みなので変えない。これで両経路の表記が揃う。
既存の HSR ガイドで `energyRecharge` を目標に持つのは**カフカ1名**で、目標は上乗せ分の意味で書かれている（厳選 19.4 / 目標 19.4 / 妥協 0）。
新しい数値を作るのではなく**単位の換算（＋100）**として **119.4 / 119.4 / 100** へ直す（出典の意味＝縄のメインを EP回復効率にする、は変わらない）。

**H6. 達成判定と不足判定に、表示桁より細かい浮動小数点誤差の許容を入れる（DR-01）。**
H5 の換算は `(1 + 0.194) * 100 = 119.39999999999999` となり、表示は「119.4%」でも現行の `>=` 判定では**未達**、不足提案に「あと 0.0%」が残る（レビューで再現済み）。
表示桁への丸めで判定すると `0.1939`（＝119.39）まで達成になってしまうため、**丸めではなく許容差**で吸収する。

```ts
// server/buildAdvisor.ts（共通ヘルパー）
/** 表示桁より細かい浮動小数点誤差だけを吸収する許容差。119.39999999999999 と 119.4 を同値として扱う。 */
const COMPARISON_EPSILON = 1e-9;
export const meetsTarget = (current: number, target: number) => current >= target - COMPARISON_EPSILON;
```

- 達成判定（3水準）と不足提案の抽出（`priorityRecommendations` の `current < 目標`）の両方で `meetsTarget` を使い、判定を一致させる。
- 使う場所は HSR（MiHoMo・Enka）・原神・ZZZ の比較を作る3箇所（`gameProviders.ts` の `comparisonsFromStats`、`enkaFallback.ts` の `comparisonForKey`、MiHoMo 経路の新しい比較）と `priorityRecommendations`。
  **算出式は変えず、数値誤差の扱いだけを共通化する例外**として Enka 経路にも入れる（Phase 18 の式は維持）。
- 不足提案の文言は、実際に不足があるのに丸めで「あと 0.0%」と出る場合、**「あと 0.1%未満」**と表示する（`0.1939` のような本物の未達を「0.0」と見せない）。
- 許容差は 1e-9 固定とし、目標値の桁に応じた丸めや相対誤差は使わない（`0.1939 → 119.39` は未達のまま）。
- **画面側にも同じ判定の複製がある（2026-09-12 実装時に判明）**。`client/src/pages/Home.tsx` の `partyAdjustedComparisons` と `recommendationsFromComparisons` は、
  推奨PT・星魂で目標が変わったときに達成判定と不足文言をブラウザ側で作り直しており、サーバーだけ直すと PT 選択時に同じ誤判定が残る。
  同じ許容差と不足文言をこの2箇所へも入れる（サーバーの `meetsTarget` と同値であることをコメントで示す）。

### Phase B（ZZZ のコード）

**D1. `Armorer` の表示名を「鋭御」にする。** `server/gameProviders.ts:382` の `ZZZ_PROFESSIONS` へ1件足す。

**D2. ロール共通ガイドは既存の `def` プロファイルを使う。**
`zzzProfileIdFor` で `Armorer` を**既存の `ProfileId` `"def"`** に割り当てる。`def` は原神で「防御力でダメージが伸びるアタッカー」（荒瀧一斗・アルベド・千織・ノエル）に使っている分類で、鋭御と概念が一致する。
`ZzzProfileId` に `def` を加えて `ZZZ_PROFILES.def` を新設し、メインステータスは防御力系、**`targets: []`**（役割共通の数値閾値は根拠が無いため推測で登録しない、と `targetContext` に書く）。
推奨PTの自動生成（`genericMembers`）は ZZZ の `def` に専用分岐が無く既定の主力編成になるが、クラレッタには出典の実名PTを登録するので使われない。変更しない。
**退けた案**: 新しい `ProfileId` `"armorer"`。和集合・推奨PT生成・想定プロファイル表に分岐が増えるのに1名のためだけになり、`def` と意味が重なる（CLAUDE.md §1 の YAGNI）。

**D6. ロール共通ガイドの説明が消えないようにする（DR-04）。**
`generatedZzzGuide` は `ZZZ_PROFILES` の `targetContext` を共通文で**無条件に上書き**しており、D2 で書く「根拠が無いため推測で登録しない」が最終応答に残らない。
プロファイル側に `targetContext` があればそれを使い、無ければ従来の共通文を使う形へ直す（既存6特性のプロファイルは `targetContext` を持たないので説明は変わらない）。
Phase B だけを公開した期間と、将来ガイド未登録の鋭御キャラクターが出たときに、この説明が実際に使われる。

**D3. ZZZ の比較値へ `defense` と `hp` を足す。** `finalZzzStats().values`（`server/gameProviders.ts:492`）に、同じ関数の表示用と**同一の式**で2キーを足す。

```ts
hp: scale("11101", "11102", "11103", true),
defense: scale("13101", "13102", "13103"),
```

**D7. ZZZ では、HP・防御力の「実数目標」に対して提案する主ステータスを割合（HP% / 防御力%）にする（DR-06）。**
D3 でシーザーらの `hp` / `defense` が比較できるようになると、ガイドに HP・防御力のメインステータス欄が無いため `defaultSlotsForStat` の既定値へ落ちる。
このとき `STAT_MAIN_LABELS` は `hp` → 「HP」、`defense` → 「防御力」を返すため、Phase E で部位の選び方を直しても、
**ディスクに存在しない「実数のHP・防御力のメインステータス」**を提案してしまう（ZZZ のディスク IV〜VI が持てるのは HP% / 攻撃力% / 防御力%）。
**希望する主ステータス名**をゲーム別にし、ZZZ では `hp` / `hpPercent` → 「HP%」、`defense` / `defPercent` → 「防御力%」を返す。
（部位の決め方は Phase E が担うため、D7 は表示名だけを受け持つ。ガイドが主ステータス欄を持つベンのような場合と、Phase E のサブステータス提案の両方に効く。）
原神・HSR の戻り値は変えない（原神の時計・杯・冠、HSR の胴体・オーブ・縄はいずれも割合表記が既存のラベルと一致している）。
既存の潘引壺（`hpPercent`）にも効くため、Phase B の回帰テストで「提案文に『HP%』が出る」ことを確認する。

**D4.（取り下げ・PB-01）** 当初は「HP・防御力系の既定部位を ZZZ では IV / V / VI にする」としていた。
しかし §1.6 の計測で、既定部位を使う75件すべてがガイドの推奨と衝突しており、**既定部位を正しく選び直す方法が無い**ことが分かった。
Phase E（E3）で既定部位そのものを廃止するため、D4 は不要になった。ZZZ が HSR の部位名を返す問題も同時に消える。

### Phase D（Enka 経路の最終値の是正）

Phase A・B・C とは独立。**MiHoMo 経路・図鑑・原神・ZZZ には一切触れない**（変更は `server/enkaFallback.ts` に閉じる）。

**E1. `Base` の付かない型を、対応する `Base` 付きの型と同じ扱いにする。**
`properties.json` の `field` が空の6種について、型名を主キーにした別名表を `enkaFallback.ts` に持つ。
`classify()` は `meta.field` が空のときこの表を引き、`{ kind: "stat", key }` として `statTotals` へ入れる。

```ts
/** Enka の _flat.props はメインに Base 付き、サブに Base なしの型を使う。
 *  properties.json は後者の field を "" にしているため、型名で対応付ける。 */
const SUB_AFFIX_TYPE_TO_STAT_KEY: Record<string, StatKey> = {
  CriticalChance: "critRate", CriticalDamage: "critDmg", StatusProbability: "effectHitRate",
  StatusResistance: "effectRes", BreakDamageAddedRatio: "breakEffect", SPRatio: "energyRecharge",
};
```

- 値は `Base` 付きと同じ**比率**（実測: `CriticalChance = 0.09072` が 9.072%）。`properties.json` の `percent` は `Base` 付きと食い違うため**参照しない**。
- 表示（`propertyDisplay`）も同じ表を見て百分率で出す。これで遺物のサブが「会心率 0」ではなく「会心率 9.1%」になる。
- 既に `field` が引ける型（`SpeedDelta`・`HPDelta`・`AttackAddedRatio` 等）の扱いは変えない。

**E2. 遺物セット効果の無条件分を加算する。**
`relic_sets.json` の各セットは、段階別の無条件効果を `properties`（`[[2セット分], [4セット分]]`）に持つ。
装備中の遺物を `_flat.setID` で数え、**装備数が満ちた段階の `properties` だけ**を `Contribution` として遺物の寄与へ足す。

- `desc` に書かれた**条件付き効果は足さない**（「攻撃力が2400以上の場合」等）。MiHoMo の `statistics` も含んでおらず、Phase 18 の「戦闘外・無条件のみ」という方針とも一致する。
- **符号をそのまま使う**（亡国の悲哀を詠う詩人の4セットは `SpeedAddedRatio -0.08`）。
- セット効果の型も `Base` 付き・無しが混在するため、E1 の別名表を共用する。
- 4セットが成立するときは2セット分も適用する（ゲーム内と同じ累積）。
- `relic_sets.json` を取得できない・セットIDを解決できない場合は、**Phase 18 と同じ fail closed** で `statsStatus: "unavailable"` にする（欠けた合算値で比較しない）。

**退けた案**: MiHoMo の `statistics` を Enka 経路でも使う。Enka へ降格するのは MiHoMo が落ちているときなので成立しない。
**退けた案**: セット効果を手書きの表で持つ。公式データに同じものがあり、二重管理になる（CLAUDE.md §1）。

### Phase E（装備提案の部位選択の是正・全ゲーム共通）

**E3. ガイドが対象ステータスの主ステータス欄を持つときだけ「主ステータスを変更」を提案する。**
持たないときは、ガイドの推奨主ステータスを壊さないよう**サブステータスの厳選**として返し、部位を1つに決め打ちしない。

```ts
// server/buildAdvisor.ts（equipmentActionsFor）
const configuredSlots = guide.mainStats.filter((entry) => labels.some((label) => entry.value.includes(label))).map((entry) => entry.slot);
if (!configuredSlots.length) {
  // ガイドがこのステータスを主ステータスに指定していない＝主ステータスは別の目的で埋まっている。
  // 部位を選んで上書きを促すと、出典で裏づけた推奨を崩す（§1.6 で75件すべてが衝突）。
  if (!SUBSTAT_CAPABLE_KEYS[family].has(key)) return null;   // 主ステータス専用（E4）＝助言を出さない
  return { …, action: "サブステータスを厳選", slot: ALL_SLOTS_LABEL, slotScope: "any", currentMain: null, equippedName: null, desiredStat, reason: … };
}
```

`equipmentActionsFor` は `null` を除いた配列を返す（`flatMap` などで畳む）。戻り値の型は変えない。

- **`defaultSlotsForStat` は削除する。** 唯一の呼び出し元がこの分岐で、残すと未使用コードになる（CLAUDE.md §1）。
  これにより **D4（ZZZ の既定部位を IV / V / VI にする）は不要になる**——既定部位そのものを持たないため。§3 の D4 は Phase E に吸収して取り下げる。
- 部位のラベルは `ALL_SLOTS_LABEL = "全部位"`（日本語の既定表示）とし、**部位を特定しないことは `slotScope: "any"` で構造として表す**（E5）。
  英語・中国語の画面はこの日本語ラベルを出さず、言語別の文言へ差し替える。
- 文面は「ガイドの主ステータスは別の役割で埋まっているため、サブステータスで補う」という趣旨にし、3ゲーム共通・3言語で1文ずつ用意する（E5 の表）。
- **この分岐が成立するのは、対象がサブステータスとして出現するキーだけ**（E4）。出現しないキーは装備アクション自体を省く。
- **配下の目標が複数同時に不足しても衝突しない**（サブステータスは併存できるため、シーザーの HP と防御力が両方出ても矛盾しない）。
- ガイドが主ステータス欄を持つ場合（ベンの `defense`＝IV「防御力% / 会心ダメージ」など）の挙動は**変えない**。従来どおり部位を指して「主ステータスを変更」または「サブステータスを厳選」を返す。


**E4. そのステータスをサブステータスで伸ばせるかを、ゲーム別に明示する（BDE-03）。**
E3 の「サブステータスを厳選」は、対象がサブステータスとして出現する場合にしか成立しない。
**主ステータスにしか存在しないキー**へ同じ提案を返すと、実行不可能な厳選を案内することになる。

```ts
// server/buildAdvisor.ts
/** そのゲームでサブステータスとして出現しうる StatKey。出典は下表。 */
const SUBSTAT_CAPABLE_KEYS: Record<"hsr" | "genshin" | "zzz", ReadonlySet<StatKey>> = { … };
```

| ゲーム | サブで伸ばせる（E3 の対象） | **主ステータス専用（装備アクションを出さない）** | 出典 |
| --- | --- | --- | --- |
| HSR | `hp` / `hpPercent` / `attack` / `attackPercent` / `defense` / `defPercent` / `speed` / `critRate` / `critDmg` / `breakEffect` / `effectHitRate` / `effectRes` | **`energyRecharge`**（EP回復効率は連結縄のメイン専用） | StarRailRes `relic_sub_affixes.json`（2026-09-12 取得）。サブに出る型は12種で、`SPRatioBase` は含まれない |
| 原神 | `hp` / `hpPercent` / `attack` / `attackPercent` / `defense` / `defPercent` / `critRate` / `critDmg` / `elementalMastery` / `energyRecharge` | （本書が扱う目標キーには該当なし） | 元素チャージ効率・元素熟知はいずれも聖遺物のサブに出る |

**E5. 「部位を指定しない」ことを構造化して返し、3言語で表示する（BDE-02）。**
現行の画面は、日本語だけサーバーの `reason` を使い、**英語・中国語は `action` / `slot` / `currentMain` から文を組み立て直している**（`Home.tsx` の `actionReason`）。
E3 の応答をそのまま渡すと、英語で `全部位 already has HP% as its main stat`（＝全部位のメインが HP%）という**事実と反する文**になり、見出しの `{slot}：{desiredStat}` にも日本語の「全部位」がそのまま出る。

```ts
// server/buildAdvisor.ts
export type EquipmentAction = {
  …
  /** "specific": slot は実在の部位。"any": 部位を特定しない（サブステータス厳選）。 */
  slotScope: "specific" | "any";
};
```

- サーバーは `slotScope` を必ず返す。従来の提案は `"specific"` で、挙動も文面も変わらない。
- 画面は `slotScope === "any"` のとき、**部位ラベルも説明文も言語別の文言に差し替える**（`slot` の日本語文字列を英語・中国語画面へ出さない）。

| 言語 | 部位ラベル | 説明文（`{stat}` に希望ステータスが入る） |
| --- | --- | --- |
| 日本語 | 全部位 | ガイドの主ステータスは別の役割で埋まっています。部位は問わないので、{stat}のサブステータスが付く装備を優先して厳選します。 |
| English | Any slot | The guide's main stats are assigned to other roles. Prioritize pieces with {stat} substats in any slot. |
| 简体中文 | 全部位 | 指南的主属性已用于其他用途。不限部位，优先筛选带有{stat}副属性的装备。 |

- `currentMain` / `equippedName` は `null` を返す（特定の装備を指していないため）。英語・中国語の分岐は `currentMain` ではなく **`slotScope` で判定**する（`currentMain` が `null` になり得るのは従来の提案でも同じため）。
- `action` は既存の2値（`"サブステータスを厳選"`）のままにする。画面のラベル（`rollSubstats`）は3言語とも既存のものを使う。

**退けた案**: キャラクター別の代替部位表を持つ。69名ぶんの出典調査が要るうえ、ガイドの `mainStats` と二重管理になる。
**退けた案**: 優先度と部位制約で競合解決する。同一部位に1つだけ残しても、その1つがガイドの推奨を崩すことに変わりはない（75件すべてが衝突しているため、選び直しでは解けない）。
**退けた案**: ZZZ だけ直す。同じ誤りが HSR 36件・原神18件にあり、片側だけ直すと挙動が分かれる。

## 4. 詳細仕様

### 4.1 HSR MiHoMo の最終値（Phase A）

```ts
// server/buildAdvisor.ts（要点）

const statsStatus = finals ? "final" : "unavailable";
const values = finals ? mihomoStatValues(finals, properties) : {};   // StatKey → 数値（割合は %）
// values の中身
//   hp / attack / defense / speed … finals の hp / atk / def / spd（FIELD_TO_COMPONENT）
//   critRate / critDmg / breakEffect / effectHitRate / effectRes … finals の各 field（FIELD_TO_STAT_KEY）×100
//   energyRecharge … (1 + finals.sp_rate) × 100（基礎100%込み。H5。sp_rate が無ければ 100）
//   hpPercent / attackPercent / defPercent … properties の percent 項目（field = hp/atk/def）の合計×100
const comparisons = guide.targets.map((target) => comparisonFromValue(target, values[target.key]));
```

## 7. リスクと割り切り

- **Phase A で HSR の全キャラクターの UID 照会の見え方が大きく変わる。** 速度・会心・攻撃力が正しい最終値になり、「未取得」だった HP・防御力・割合キーにも値が入る。
  これまで一律に「未達」だった速度が達成に変わるなど、利用者に見える変化は大きいが、**直前までの表示が誤り**なので採る。更新履歴（`/updates`）のサイト全体イベントで告知する。
- **目標値の意味が最終値前提か再確認が要る。** 既存の HSR ガイドは「公開値の速度134」のように最終値を前提に書かれている（Game8・GameWith の目安も最終値）。
  Phase A 後に明らかに不自然な達成・未達が出た目標は、個別に出典を再確認する（本書では目標値を変えない）。
- **EP回復効率は基礎100%込みへ揃える**（H5）。カフカの目標は単位の換算（＋100）で、比較の意味は変わらない。今後 HSR のガイドへ `energyRecharge` を足すときは基礎込みの値で書く（原神の元素チャージ効率と同じ流儀）。
- **鋭御のロール共通ガイドに数値目標が無い。** 個別ガイドを持たない鋭御キャラクターが今後出ると比較表が空になるが、根拠の無い数値より空のほうが正しい。
