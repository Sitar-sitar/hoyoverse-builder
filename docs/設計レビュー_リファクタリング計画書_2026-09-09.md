## 指摘

### DR-01 / P2: R8でimportするゴールデンスクリプトがcollect前に終了する

- 計画書: 184–185、248–295、634行。
- 根拠: `mode = process.argv.slice(2)[0]` に対するCLI分岐がモジュールのトップレベルにある。R8は `tsx -e` からこのモジュールをimportするため、`mode` が未指定となり、末尾のusage出力と `process.exit(2)` が実行される。
- 再現: 計画書のJSブロックをそのまま抽出し、`node --import tsx -e "import('./tmp/design-review/golden-snapshot.mjs').then(m => m.collect())"` を実行。usageを出力してexit 2。対して同ファイルの `snapshot` → `compare` は全10セクション一致で成功した。単体CLIが成功してもimportの使用法は成立しない。
- 影響: R8が要求する `id/catalog mismatch: 0 []` の確認に到達できず、baseline更新前のゲートが止まる。
- 修正方向: CLI処理を `main()` に分離し、直接実行時だけ呼ぶガードを設けるか、比較を専用CLIサブコマンドとして実装する。
- 再レビュー条件: 掲載するCLI操作とimport操作をそれぞれ実行し、import時にusage・exit・baseline書換えが起きず `collect()` を利用できることを確認する。

### DR-02 / P2: R8の差分許可が矛盾し、references全体の更新が凸以外の回帰を隠す

- 計画書: 147、261–288、628–639行。
- 実装根拠: [characterReference.ts](../server/characterReference.ts) 73–92行。図鑑応答には `guide`、`partyRecommendations`、`status`、`batch` と `constellations` が同居する。
- 問題1: 手順2は「catalogConstellationsのみ差分・他9セクション一致」と要求するが、手順3で初めて `references` も差分になると説明する。共通ブロックの注記も `--refresh catalogConstellations` のみで、正しいR8実装でも成功しない手順が残る。
- 問題2: 最終的な `--refresh catalogConstellations,references` は `references` を丸ごと比較対象外にする。`id/catalog` の一致は凸の下位関数だけの検証であり、最終図鑑応答の凸以外の値を保証しない。
- 再現: baselineの `references["hsr:ホタル"].guide.headline` だけを検証用文字列へ変更した別ファイルを作り、上記refreshを実行。対応する独立 `guides` セクションは元のままでも、`references` の文言差分を検出せず `golden compare: all sections equal` / exit 0になった。比較を省略する挙動なので、差分が変更前・変更後のどちら側にあっても同じ欠落が生じる。
- 影響: 「唯一の挙動変更は図鑑の凸」という契約に反した図鑑ガイド・PT・台帳情報の変更まで正常なbaselineとして承認できる。
- 修正方向: R8では最初から2セクションの差分を期待する手順へ統一する。`references` は各キャラの `constellations` だけを除外して旧値と厳密比較し、その凸は期待するID解決結果と比較する。第15バッチは既存上書きが優先されるため、最終応答が従来どおりであることを別に固定する。全検証が成功してから許可したフィールドだけbaselineへ反映する。
- 再レビュー条件: 正しいR8差分は通り、図鑑応答の `guide.headline` / `partyRecommendations` / `status` のいずれかを1箇所変えた検証用データは失敗する。失敗時にはbaselineを書き換えない。

### DR-03 / P2: R4の追加テストは掃除処理が存在しなくても合格する

- 計画書: 443–465行、特に463行。
- 実装根拠: [buildAdvisor.ts](../server/buildAdvisor.ts) 652–672行。現行の `getEntry()` 自体が期限切れエントリを削除してnullを返す。
- 再現: 未変更の `UidResponseCache` に300件を `ttlMs=1, now=0` で登録し、`now=2` で有効な1件を追加した。読み取り前のMapは301件。それでも300件を `get(key, 2)` してnull、有効な1件を取得できるという設計のアサーションはすべて成功した。
- 影響: `set()` 時の掃除を実装し忘れても、目的である保持メモリ削減を確認できないままR4が完了する。
- 修正方向: `get()` の副作用が走る前に保持件数を観測するテストを定義する。テスト内の限定的な内部観測や件数の診断手段を選び、期限切れ300件と有効1件を使って `set()` 直後に有効分だけが残ることを固定する。閾値以下・超過・期限境界で有効値を消さないことも確認する。
- 再レビュー条件: 現行の掃除なし実装で失敗し、提案の掃除あり実装で成功すること。`set()` の掃除部分を外した場合に再度失敗すること。

### DR-04 / P2: R3の必須検索条件が変更案および変更禁止箇所と一致しない

- 計画書: 410、420、437行。
- 実装根拠: [partyRecommendations.ts](../server/partyRecommendations.ts) 75–78行に既存の `checkedAt: "2026-08-25"` が3行ある。バッチラッパーとは別の共通出典定義である。
- 再現: 計画書の `datedOptions` ブロックを読み取り中のソース文字列へ置換した結果、`batchNOptions = datedOptions` は13件だが、`checkedAt: "2026-` の一致行数は3件となる。提案factory自身は `checkedAt: date` なので、このパターンに一致しない。
- 影響: 正しく統合しても「datedOptions内の1件のみ」を満たせない。共通の中断規約に従えばR3で止まり、期待件数を無理に満たせば変更対象外の出典日付へ手を入れることになる。
- 修正方向: `checkedAt: date` がfactory内に1件あること、13個の旧ラッパー本体がなくなったことを対象範囲を限定して確認する。共通出典の3件は変更前後一致とする。
- 再レビュー条件: 提案どおりの置換結果で検索条件が成功し、旧ラッパーを1本戻すと失敗すること。

### DR-05 / P3: R8の修正対象「200名」は最終図鑑応答の実数と異なる

- 計画書: 123、599、665、678行。索引の計画紹介にも同じ数値がある。
- 実装根拠: [characterReference.ts](../server/characterReference.ts) 81行は第15バッチの凸上書きを優先する。[characterConstellations.ts](../server/characterConstellations.ts) 1619行以降は名前キーへのフォールバックと準備中データも扱う。したがって「248−手書き索引48」で最終APIの不具合数を求められない。
- 実測: 現行 `characterReferenceFor()` 全248名は `preparing=177 / curated=71`。計画のR8索引を別の検証関数内で構築し、既存の第15バッチ優先を維持して比較すると、`preparing→curated` と応答変更はともに172名。名前未解決は0件。変更後も準備中となる5名は原神のアーロイ・コロンビーナ、ZZZのシーシィア・ニコ・ピュロイスである。この検証はデータ内容の正当性を新たに認定するものではない。
- 修正方向: 不具合数・挙動変更数を区別し、同一コミットの最終図鑑応答から数え直す。172名の期待差分と76名の非変更集合、残る準備中5名を受入条件に明記する。
- 再レビュー条件: 全248名の変更対象集合と非変更集合を保存し、R8前後の最終応答で一致を確認する。本番の件数は公開確認時に別途測定する。
