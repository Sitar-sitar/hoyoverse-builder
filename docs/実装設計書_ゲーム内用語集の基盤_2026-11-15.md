# 設計書：ゲーム内用語集（世界観を含む）の基盤

崩壊：スターレイル・原神・ゼンレスゾーンゼロの専門用語（戦闘・育成の仕組みから世界観まで）を引ける用語集を追加する。用語の説明文に出てくる別の用語へ、そのまま移動できるようにする。本設計は**仕組みだけ**を対象とし、用語データの投入は利用者の指示があったときに別作業として行う。

## 1. 目的・背景

- ビルドガイドや凸の説明には「使令」「願力」「愉悦度」のようなゲーム固有の用語が説明なしで出てくる。用語と世界観をサイト内で引けるようにする。
- 用語は互いに参照し合う。説明文の中の用語から、その用語の説明へ直接移動できることを必須とする。
- データは今後、利用者の指示のたびに少しずつ増やす。**更新者（AI を含む）が「どこに・何を・どの形式で書くか」で迷わないこと**を最優先の設計条件とする。

## 2. スコープ

### 2.1 IN

- 用語データの型・置き場所・ID 規約・リンク記法
- 検査（リンク切れなど）と、手編集 1 ファイルから残りを作る生成コマンド
- 公開 API（ゲーム単位で用語一覧を返す）
- 公開画面 `/glossary`（一覧・検索・カテゴリ絞り込み・用語詳細・用語間の移動）
- 更新手順書 `content/glossary/README.md`

### 2.2 OUT

- **用語データそのものの投入**（3 ゲームとも 0 件で出荷する）
- ビルドガイド・凸・推奨PT の文章から用語集へのリンク（§4.9 に拡張の入口だけ用意する）
- ゲームをまたぐ用語リンク
- 英語・中国語の翻訳作成と公開（既存方針どおり日本語のみ公開）
- 用語データ更新用の Skill 化（データ更新を数回行い、手順が固まってから判断する）
- 既存の UID 照会・図鑑・更新履歴の挙動変更

## 3. 全体方針

| 論点 | 採用 | 退けた案と理由 |
| --- | --- | --- |
| 手で編集する場所 | **ゲームごとに 1 ファイル**（`content/glossary/<game>.ts`）。日本語原文ファイルと翻訳レコードはそこから生成する | 既存バッチと同じく原文・英・中・authoring の 4 ファイルを手で書く案は、1 用語の追加で 4 か所を揃える必要があり書き漏らしやすい |
| 用語リンクの付け方 | 説明文に**明示記法** `[[用語ID]]` を書く。リンク切れは検査で失敗させる | 用語名の自動検出は、日本語に単語の区切りが無く「速度」が「攻撃速度」の中で誤って当たる。結果が検査できない |
| リンクの付け忘れ対策 | 検査コマンドが「用語名が本文に出ているのにリンクになっていない箇所」を**警告**として一覧表示する | 付け忘れをエラーにすると、意図的にリンクしない文（同じ語の一般的な用法）が書けない |
| 配信方法 | 既存の図鑑と同じく tRPC の公開 query で返す | 用語本文をクライアントに同梱する案は、「Pages に原文コーパスを含めない」という既存方針（`scripts/content/commands.ts` の manifest 生成）に反する |
| リンクの解析場所 | サーバーで記法を解析し、クライアントには「文字」「用語リンク」の配列を渡す | クライアントで文字列を解析して HTML を組み立てる案は、表示の安全性の確認箇所が増える |
| 0 件のときの見せ方 | 用語が 1 件も無いゲームはタブを出さず、3 ゲームとも 0 件ならナビのリンク自体を出さない | 空のページを公開する案は、利用者に未完成の画面を見せる |

### 4.1 ファイル構成

### 4.2 用語エントリの型

```ts
// shared/content/glossary.ts
export type GlossaryEntry = {
  /** 用語ID。ゲーム内で一意。英小文字・数字・ハイフンのみ。公開後は変更しない。 */
  id: string;
  /** categories.ts にあるカテゴリID。1 つだけ。 */
  category: GlossaryCategoryId;
  /** ゲーム内の日本語正式表記。 */
  name: string;
  /** よみ。ひらがなと長音「ー」のみ。五十音順の並びと検索に使う。 */
  reading: string;
  /** 別名・略称・旧称。検索と「リンク付け忘れ」検出の対象。無ければ省略。 */
  aliases?: string[];
  /** 1 文の要約（80 字以内）。リンク記法は書けない。一覧とリンクの補足表示に使う。 */
  summary: string;
  /** 本文。空行で段落を分ける。リンク記法を書ける。 */
  body: string;
  /** 関連用語のID。片側に書けば両方の用語に表示される。 */
  related?: string[];
  /** 関連キャラクターの identityKey（例 "hsr:1305"）。図鑑へのリンクになる。 */
  characters?: string[];
  /** true のとき本文を折りたたんで表示する（ストーリーの核心に触れる用語）。 */
  spoiler?: boolean;
  /** 根拠にした出典。1 件以上。 */
  sources: Array<{ label: string; url: string }>;
  /** 内容を確認したゲームのバージョン（例 "3.7"）。 */
  gameVersion: string;
  /** 内容を確認した日（YYYY-MM-DD）。 */
  dataAsOf: string;
  /** 過去に使っていた用語ID。古い URL を新しい用語へ案内する。 */
  formerIds?: string[];
};
```

- すべての必須項目は型で強制する。任意項目は 5 つ（`aliases` / `related` / `characters` / `spoiler` / `formerIds`）だけ。
- 項目を足すときは、この型・検査・DTO・README の 4 か所を同時に直す（README にも明記する）。

### 4.3 ID 規約

- **用語ID**: ゲームの英語版での正式名称を kebab-case にする（例: 星神 → `aeon`、運命 → `path`）。英語名が無い・不明な場合は日本語のローマ字にし、推測の英訳は作らない。
- 形式は `^[a-z0-9]+(-[a-z0-9]+)*$`、40 字以内。
- **公開後は変更しない**。どうしても変える場合は新 ID にして旧 ID を `formerIds` へ入れる。
- 文章 ID（`TextId`）は生成コマンドが決める。手で書かない。
  - `term.<game>.<id>.name` / `term.<game>.<id>.summary` / `term.<game>.<id>.body`
  - カテゴリ表示名は `term.category.<categoryId>`
  - `TextId` の接頭辞 `term` は `shared/content/types.ts` に定義済みで、型の変更は要らない。
- `reading`・`aliases`・出典の `label`・`url` は翻訳対象外の内部値として扱う（文章 ID を作らない）。

### 4.4 リンク記法

本文（`body`）の中だけで使える。

| 書き方 | 表示 | 使いどころ |
| --- | --- | --- |
| `[[aeon]]` | リンク先の用語名（「星神」） | 基本形。用語名が変わっても追従する |
| `[[aeon\|星神たち]]` | 「星神たち」 | 活用・略称・文脈上の言い換えで表示を変えたいとき |

- リンク先は**同じゲームの用語ID**。存在しない ID・自分自身・`formerIds` の ID を指すと検査エラー。
- 同じ段落で同じ用語を何度リンクしてもよい（制限しない）。
- 既存の変数記法 `{name}` とは文字が重ならない。本文に `{` `}` は書けない（検査エラー）。
- 生成コマンドは、本文中の `[[id]]` と `[[id|` を `protectedTokens` に自動で入れる。翻訳でリンクが消えたり別の用語を指したりすると、既存の翻訳検査で検出される。

解析結果の型（サーバーからクライアントへ渡す形）:

```ts
export type GlossaryNode =
  | { type: "text"; text: string }
  | { type: "term"; id: string; label: string };
```

### 4.5 カテゴリ

`content/glossary/categories.ts` に、全ゲーム共通のカテゴリを配列で定義する。配列の順が画面の並び順になる。

| ID | 表示名 | 入れるもの |
| --- | --- | --- |
| `battle` | 戦闘 | 戦闘中の仕組み・状態・効果 |
| `growth` | 育成 | 育成要素・装備・素材の仕組み |
| `content` | コンテンツ | 高難度・周回・イベントなどの遊び方 |
| `world` | 世界観 | 世界の成り立ち・概念・歴史 |
| `faction` | 組織・勢力 | 国・陣営・団体 |
| `place` | 地名 | 星・国・都市・施設 |
| `being` | 人物・存在 | プレイアブル以外の人物・神・種族 |

- カテゴリの追加は、配列に 1 行足して生成コマンドを実行するだけにする。
- カテゴリの ID は用語エントリの `category` の型（`GlossaryCategoryId`）になり、存在しない ID は型エラーになる。
- この 7 種で開始する（§10 U-2 で確定）。データ投入時に不足があれば足す。

### 4.6 生成と検査

#### 4.6.1 コマンド

| コマンド | 役割 |
| --- | --- |
| `pnpm glossary:sync` | 入力ファイルを検査 → 日本語原文を生成 → 翻訳レコードを同期 → `content:catalog-index generate` → `content:generate` を順に実行する。**データ更新後に実行するのはこれ 1 つ** |
| `pnpm glossary:report` | 警告（§4.6.3）と件数を表示する。終了コードは常に 0 |
| `pnpm content:check`（既存） | 生成物が入力と一致しているか・検査エラーが無いかを確認する。`pnpm build` の先頭で必ず走る |

翻訳レコードの同期規則:

- 新しい文章 ID → 既存バッチと同じ形（`text` は日本語原文、`sourceHash: null`、`origin: "legacy"`、`review: "pending"`）で追加する。
- すでにあるレコード → **一字も変更しない**。
- 入力から消えた文章 ID → レコードを削除する。

既存スクリプトの変更点は 1 か所: `scripts/content/catalogIndex.ts` の走査対象に `content/ja/glossary` を加える（モジュール名は `glossary/<game>`、翻訳側は `glossary_<game>`）。

#### 4.6.2 検査エラー（`glossary:sync` と `content:check` を失敗させる）

エラー文には必ず「ゲーム・用語ID・項目名・直し方」を含める。

| 検査 | 例 |
| --- | --- |
| 用語ID の形式・ゲーム内の重複（`formerIds` を含む） | `hsr / aeon: 用語IDが重複しています` |
| `category` が未定義 | 型エラーで検出 |
| `reading` がひらがな・長音以外を含む | |
| `name`・`aliases` が同じゲームの別の用語の `name`・`aliases` と重複 | 検索結果が曖昧になるため |
| `summary` が空・80 字超・リンク記法を含む | |
| `body` が空・`{` `}` を含む・リンク記法が閉じていない | |
| リンク先・`related` が存在しない、自分自身を指す、`related` 内で重複 | `hsr / path: body のリンク先 "aeons" がありません。近い候補: aeon` |
| `characters` が図鑑（`content/characters.ts`）に無い、別ゲームのキャラ | |
| `sources` が 0 件、`url` が `https://` で始まらない | |
| `dataAsOf` が `YYYY-MM-DD` でない・未来日 | |
| 生成物が入力と一致しない | `pnpm glossary:sync を実行してください` |

リンク先が無いときは、編集距離の近い用語ID を候補として表示する。

#### 4.6.3 警告（`glossary:report` に表示。失敗させない）

- **リンク付け忘れ候補**: ある用語の `name`・`aliases` が、別の用語の `body` にリンクなしで出ている箇所。
- **孤立した用語**: どの用語からもリンク・`related` されておらず、自分からも出していない用語。
- **確認日が古い用語**: `dataAsOf` から 365 日を超えた用語。

### 4.7 公開 API と画面

#### 4.7.1 API

`build.glossary`（公開 query）を `server/routers.ts` に追加する。入力は `{ game: "hsr" | "genshin" | "zzz" }`。入力検証・回数制限は既存の `build.reference` と同じ扱いにする。

```ts
export type GlossaryDTO = {
  schemaVersion: 1;
  contentRevision: string;
  language: "ja";
  game: Game;
  categories: Array<{ id: string; label: string }>;   // 用語が 1 件以上あるカテゴリのみ
  entries: Array<{
    id: string;
    category: string;
    name: string;
    reading: string;
    aliases: string[];
    summary: string;
    body: GlossaryNode[][];                            // 段落 → ノード
    related: Array<{ id: string; name: string }>;      // 自分が指す用語 ∪ 自分を related に書いた用語
    mentionedBy: Array<{ id: string; name: string }>;  // 本文で自分へリンクしている用語（related と重複するものは除く）
    characters: Array<{ identityKey: string; name: string }>;
    spoiler: boolean;
    sources: Array<{ label: string; url: string }>;
    gameVersion: string;
    dataAsOf: string;
  }>;
  redirects: Record<string, string>;                   // formerIds → 現在の用語ID
};
```

- `related` と `mentionedBy` はサーバーが計算する。更新者は逆方向を書かなくてよい。
- 並び順は `reading` の五十音順（同じなら `id` 順）でサーバーが確定する。
- 1 ゲーム分を 1 回で返す。500 件 × 本文 400 字を想定しても圧縮前 1MB 未満で、既存の `compression` で足りる。これを超えたら分割を検討する（§7）。

#### 4.7.2 画面 `/glossary`

- URL: `/glossary?game=hsr&term=aeon`。図鑑（`/characters?game=…&character=…`）と同じクエリ形式にする。
- 構成: ゲーム切替 → 検索欄 → カテゴリ絞り込み → 用語一覧 → 用語詳細。1024px 以上は一覧と詳細を左右に並べ、未満は一覧から詳細へ切り替える。
- 検索対象: `name`・`reading`・`aliases`・`summary`（部分一致）。
- 用語詳細の表示順: 用語名・よみ・カテゴリ → 要約 → 本文 → 関連用語 → この用語に触れている用語 → 関連キャラクター（図鑑へのリンク） → 出典・確認バージョン・確認日。
- **用語リンクの動作**:
  - クリックで同じ画面のまま対象の用語詳細へ切り替え、`term` を `history.pushState` で更新する。**ブラウザの「戻る」で直前の用語に戻れる**（図鑑の `replaceState` とは意図的に変える）。
  - 切り替え後は詳細の見出しへフォーカスを移す。
  - ポインタを載せる・キーボードでフォーカスすると、リンク先の `summary` を既存の Tooltip で表示する。
  - リンクは `<a href="/glossary?game=…&term=…">` として描き、新しいタブで開く・URL をコピーする操作ができるようにする。
- `term` が `redirects` にあれば現在の ID へ置き換える（`replaceState`）。どちらにも無ければ「この用語は見つかりません」を表示し、一覧はそのまま使える状態にする。
- `spoiler: true` の用語は、要約までを表示し本文は「本文を表示」を押すまで隠す。
- 共通ヘッダー（`SiteHeader`）に「用語集」を追加する。`SitePage` に `"glossary"` を足し、`App.tsx` の `THEME_SWITCHABLE_PATHS` に `/glossary` を加える。画面は他のルートと同じく `lazy` で読み込む。
- 画面の固定文言（見出し・検索欄の説明・0 件の案内など）は、既存の UI 文言と同じ手順（`content/ja/ui` → `content:generate`）で登録する。

#### 4.7.3 0 件のときの扱い

- `content:generate` が作る `client/src/content/manifest.ts` に `glossaryGames`（用語が 1 件以上あるゲームの配列）を加える。
- ヘッダーの「用語集」は `glossaryGames` が空でないときだけ表示する。画面のゲーム切替は `glossaryGames` にあるゲームだけを出す。
- `/glossary` を URL で直接開いた場合、対象ゲームが 0 件なら「準備中」の案内を表示する。
- これにより、**データを 1 件入れて `glossary:sync` を実行すれば、画面側のコードを触らずにナビと画面が有効になる**。

### 4.8 更新手順書（`content/glossary/README.md` に書く内容）

README は「この 1 ファイルを読めば更新できる」ことを条件とし、次の構成にする。

1. **編集するファイルは 1 つ**: `content/glossary/<game>.ts`。`content/ja/glossary/` と `content/translations/*/glossary_*` は生成物で、手で触らない。
2. **コピーして使う雛形**（全項目入りのエントリ 1 件と、項目ごとの書き方・良い例・悪い例）。
3. **作業別の手順**:

   | やりたいこと | 手順 |
   | --- | --- |
   | 用語を追加する | 配列の末尾にエントリを足す（並びは画面で五十音順になるので、ファイル内の順は問わない） |
   | 説明を直す | `summary`・`body` を直し、`dataAsOf`・`gameVersion` を更新する |
   | 用語ID を変える | 新 ID にして旧 ID を `formerIds` へ。他の用語の `[[旧ID]]` は検査エラーで全箇所が示されるので、それに従って直す |
   | 用語を削除する | エントリを消す。その用語を指していたリンク・`related` は検査エラーで示される |
   | カテゴリを足す | `categories.ts` に 1 行足す |

4. **書き終えたら**: `pnpm glossary:sync` → `pnpm glossary:report`（リンク付け忘れ候補を確認して必要なら直す） → `pnpm check` → `pnpm test`。
5. **書き方の規則**:
   - 本文は**自分の言葉で要約**する。ゲーム内テキスト・攻略サイトの文章を写さない。
   - 出典が確認できない内容は書かない。推測・考察は書かない（公式に明かされていない点は「明かされていない」と書く）。
   - 1 つの用語は 1 エントリ。同じ概念の別名は `aliases` に入れ、別エントリを作らない。
   - 本文に別の用語が出てきたら、その用語がすでにあれば `[[ID]]` でリンクする。無ければリンクせずに書き、後でその用語を追加したときに `glossary:report` の候補から拾う。
   - ストーリーの核心に触れる用語は `spoiler: true` にする。
6. **エラーが出たとき**: §4.6.2 の一覧と直し方。

### 4.9 将来の拡張の入口（今回は実装しない）

- **ガイド文から用語集へのリンク**: `GlossaryText` 部品と `GlossaryNode` 型はガイド側でもそのまま使える。ガイド原文に同じ記法を許可するかは別設計で判断する。
- **ゲームをまたぐリンク**: 記法を `[[genshin:xxx]]` に広げる余地を残すため、用語ID に `:` を使わない（§4.3 の形式で保証済み）。
- **入力ファイルの分割**: 1 ゲームのファイルが大きくなったら `content/glossary/<game>/` 配下の複数ファイルに分ける。型と検査は配列を受け取るだけなので変更は読み込み部分に限られる。

## 7. リスクと割り切り

- **翻訳レコードの `origin: "legacy"`**: 新規文章にも既存バッチと同じ値を使う。英中を公開しない現状では表示に影響しない。翻訳を始めるときは既存の翻訳基盤の手順に従う。
- **本文を 1 つの文章 ID にする**: 段落を 1 つ直すと本文全体の翻訳が「古い」扱いになる。段落ごとの固定 ID を手で振る負担より、更新者の単純さを優先する。
- **入力が TypeScript ファイル**: 更新者は TS の文字列を書く必要がある。代わりに型で必須項目とカテゴリ ID の誤りをエディタ上で検出できる。JSON・Markdown 入力は検査を自作する範囲が増えるため採らない。
- **1 ゲーム 1 応答**: 用語が 1 ゲーム 1,000 件を超える規模になったら、一覧と本文を分ける API へ変更する。
- **ロールバック**: ナビの表示は `glossaryGames` で決まるため、用語データを 0 件に戻して `glossary:sync` すれば公開画面から消える。コードの差し戻しは不要。

## 8. テスト・検証

- **解析（`shared/content/glossary.ts`）**: 基本形・表示名つき・連続するリンク・閉じていない記法・段落分割。
- **検査（`server/content/glossary.ts`）**: §4.6.2 の各エラーを架空の用語（テスト内 fixture）で 1 件ずつ再現する。エラー文に用語ID と直し方が含まれること。
- **逆引き**: `related` を片側だけ書いたとき両方に出ること、本文リンクが `mentionedBy` に出ること、重複が除かれること。
- **生成**: 既存の翻訳レコードが変わらないこと、消えた ID のレコードが削除されること、2 回続けて実行しても差分が出ないこと。
- **画面**: 用語リンクのクリックで詳細が切り替わり URL が変わること、「戻る」で前の用語に戻ること、`redirects`・存在しない `term`・`spoiler`・0 件ゲームの表示。
