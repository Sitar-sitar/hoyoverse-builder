## 3. 全体方針

1. **レート制限は HTTP 境界ではなくプロトコル境界で分ける。** `/api/trpc` に Express 層から通常 JSON の 429 を返すと、`httpBatchLink` が期待する tRPC バッチレスポンス形式を壊す可能性がある。したがって **tRPC は tRPC middleware 内で全体上限＋procedure 別上限を適用**し、Express 層の粗い IP 上限は `/api/trpc` を除く `/api` のみへ適用する。
2. **クライアント IP は Railway の `X-Real-IP` を使う。** Railway 公式の Public Networking 仕様では `X-Real-IP` が client remote IP 用ヘッダーとして提供される。Railway 実行時（`RAILWAY_PROJECT_ID` が存在）だけ検証済み `X-Real-IP` を信頼し、それ以外は `req.socket.remoteAddress` を使う。レート制限のためだけに `app.set("trust proxy", 1)` を全体へ導入しない。
3. **POST 化は router を変えずに行う。** `build.lookup` の mutation 化は行わない。tRPC 11.18.0 の `httpBatchLink({ methodOverride: "POST" })` ＋ `createExpressMiddleware({ allowMethodOverride: true })` により、React Query の query キャッシュ・同時照会抑止を維持したまま query を POST 送信する。
4. **Last Known Good には negative caching を必ず添える。** 取得失敗後は `nextRetryAt` を記録し、60 秒間は外部へ再アクセスしない。LKG があれば即返し、LKG が無ければ直前エラーを即再送出する。HSR は既存仕様に合わせ、LKG が無い場合は `EMPTY_STATIC_INDEX` を即返す。
5. **新しい依存は増やさない。** レート制限と LRU は `Map` で実装し、`express-rate-limit` / `lru-cache` は導入しない。
6. **UID はキーにするが平文で持たない。** UID 単位のレート制限キーは、プロセス起動時に生成した一時鍵による HMAC-SHA256 を16進16文字へ切り詰めた値とする。ログ・エラー本文・メトリクスには出さない。
7. **UID 応答キャッシュは 256 件/インスタンスで固定する。** HSR / 原神 / ZZZ の3キャッシュで合計最大768件。期限切れ掃除後も上限を超える場合は LRU で追い出す。初期値は保守的に固定し、将来の増加は実メモリ計測を根拠に別変更とする。

## 4. 詳細仕様

### Phase 42: tRPC query の POST 化

**目的**: UID を GET URL へ載せない（入力文書 P2-04）。

- `server/_core/index.ts` の `createExpressMiddleware` に `allowMethodOverride: true` を追加する。`responseMeta` による `vary: Origin` は Phase 41 の仕様であり、そのまま残す。
- `client/src/main.tsx` の `httpBatchLink` に `methodOverride: "POST"` を追加する。
- `server/routers.ts` は変更しない（`build.lookup` は query のまま）。`client/src/pages/Home.tsx` も変更しない。
- `client/src/lib/safeTrpcFetch.ts` は Phase 45 で扱う。ここでは変更しない。

**確認済みの前提**（導入済みパッケージの型定義で実在を確認）:
- `@trpc/client` `HTTPLinkBaseOptions.methodOverride?: 'POST'`
- `@trpc/server` `allowMethodOverride?: boolean`
- `allowMethodOverride` は GET を禁止せず POST を追加で受け付けるだけである。したがって CI の `curl "$API_BASE_URL/api/trpc/build.guideHistory"`（GET）はそのまま通る。**この GET は変更しない**（Railway API の疎通確認であり、UID を含まない）。

**注意**: `methodOverride` は**そのリンクを通る全 query**に効く。`build.guideHistory` や `display.settings` も POST になる。いずれも動的応答で HTTP キャッシュを前提にしていないため影響は無い。

### Phase 43: 公開 API のレート制限

**新規ファイル**: `server/_core/rateLimit.ts`（固定ウィンドウ計数。外部依存なし）

```ts
export type RateLimitRule = { windowMs: number; max: number };
export type RateLimitVerdict = { allowed: boolean; retryAfterSeconds: number };

export function createRateLimiter(rule: RateLimitRule, maxEntries = 10_000): {
  consume(key: string, now?: number): RateLimitVerdict;
};

export function clientIpFromRequest(req: Request): string;
export function rateLimitKeyForUid(uid: string): string;
export function applyRetryAfter(res: Response, seconds: number): void;
```

- 固定ウィンドウとする。スライディングウィンドウは状態が増え、今回の目的（濫用の遮断）に対して過剰。
- 内部 `Map` に最大 10,000 キーを設ける。上限超過時は期限切れを掃除し、それでも超える場合は古いバケットから削除する。レート制限機構自体がメモリ枯渇経路にならないこと。

**(A) クライアント IP の確定**

- Railway production では `process.env.RAILWAY_PROJECT_ID` が存在する場合のみ `req.get("x-real-ip")` を候補とし、`net.isIP()` が 1 以上の値だけを採用する。Railway 公式仕様上、`X-Real-IP` は client remote IP を識別するためのヘッダーである。
- Railway 以外（ローカル・テスト・別ホスティング）では `X-Real-IP` / `X-Forwarded-For` を信頼せず、`req.socket.remoteAddress` を使う。
- Railway 実行時に `X-Real-IP` が欠落または不正なら `req.socket.remoteAddress` へフォールバックし、**警告を1回だけ**記録する。UID / Bearer Token / IP 自体は警告本文へ出さない。
- **`app.set("trust proxy", 1)` は追加しない。** レート制限以外の Express 挙動へ影響を広げず、Railway が明示提供するヘッダーを限定的に利用する。

**(B) Express 層 — 非 tRPC `/api` の粗い上限**

- 配置順: `configureCors` → **非 tRPC API レート制限** → `compression` → `applyBodyParsers` → 各ルート。CORS プリフライトは `configureCors` 内で 204 返却されるためカウントされない。body parser より前に置き、濫用時の不要な本文解析も避ける。
- 対象: `/api` 配下。ただし **`/api/trpc`、`/api/health`、`OPTIONS` を除外**する。
- `/api/trpc` を除外する理由: Express から `{ "error": "Too Many Requests" }` を返すと tRPC バッチエンベロープではなくなり、`httpBatchLink` のデコードを壊し得るため。tRPC 側は (C) で同じ粗い上限を適用する。
- 上限: **IP あたり 1 分 120 回**。
- 超過時: HTTP `429` / `Content-Type: application/json` / `{ "error": "Too Many Requests" }` / `Retry-After: <秒>`。
- 2026-09-19 の production HTTP ログ（取得可能な直近96件）では source IP 単位の最大は 18 request/min だった。120/min は通常利用に十分な余裕を持つ初期値として確定する。

**(C) tRPC 層 — 全 procedure の粗い上限＋個別上限**

- `server/_core/trpc.ts` に `globalApiRateLimitMiddleware` を追加し、次のように **全 base procedure の共通土台**へ適用する。

```ts
const baseProcedure = t.procedure.use(globalApiRateLimitMiddleware);
export const publicProcedure = baseProcedure;
export const protectedProcedure = baseProcedure.use(requireUser);
export const adminProcedure = baseProcedure.use(requireAdmin);
```

- 全 tRPC operation: **IP あたり 1 分 120 回**。HTTP バッチ1回ではなく **operation 1件を1回**として数える。
- tRPC で超過した場合は `TRPCError({ code: "TOO_MANY_REQUESTS" })` を投げる。`applyRetryAfter()` は既存 `Retry-After` より長い秒数を保持し、バッチ内で複数 operation が制限された場合もレスポンス全体に最長値を付ける。
- `build.lookup`: `.input(...)` **の後**に個別 middleware を付け、**IP 20回/分** かつ **UID 6回/分**。UID キーは `` `${game}:${rateLimitKeyForUid(input.uid)}` `` とし、ゲーム間で共有しない。
- `feedback.submit`: `.input(...)` の後に個別 middleware を付け、**IP 5回/10分**。
- キャッシュヒットは区別しない。middleware 実行時点で外部アクセス有無を判別できず、ヒット分を戻す方式は制限回避経路になるため。

**(D) GitHub 管理者交換 API**

- `/api/auth/github/exchange` は tRPC 外なので (B) の 120回/分に加え、個別に **IP 10回/分** を適用する。
- 交換コードは 32 バイト乱数・ハッシュ保存・単回使用・短 TTL の既存仕様を維持する。ここでの制限目的は総当たり対策ではなく DB 照合負荷の抑制。

**UID キー**

```ts
const RATE_LIMIT_SALT = randomBytes(32); // プロセス起動ごと。永続化しない。
export const rateLimitKeyForUid = (uid: string) =>
  createHmac("sha256", RATE_LIMIT_SALT).update(uid).digest("hex").slice(0, 16);
```

再起動で計数がリセットされる点は許容する。2026-09-19 時点の Railway production は `iad` 1 replica であるため、今回のプロセス内計数方式の前提を満たす。
### Phase 44: 原神・ZZZ 静的カタログの Last Known Good と再試行抑止

**対象**: `server/gameProviders.ts:93-105`（`createTimedLoader`、`getGenshinCatalog` / `getZzzCatalog` が使用）、`server/enkaFallback.ts:90-104`（`getStaticIndex`）

`createTimedLoader` を次の状態機械へ置き換える。

```
TTL 内のキャッシュあり ─────────────────────────► fresh を返す
       │なし
       ▼
再試行抑止中（nextRetryAt > now）
       ├─ 有効な LKG あり ─────────────────────► stale LKG を即返す
       └─ 有効な LKG なし ─────────────────────► lastError を即 throw（外部へ行かない）
       │抑止中でない
       ▼
取得を実行（同一 Promise を共有し重複実行しない）
       ├─ 成功 ─► キャッシュ（TTL 24h）と LKG（savedAt=now）を更新
       │           nextRetryAt / lastError をクリアして返す
       └─ 失敗 ─► nextRetryAt = now + 60s、lastError = error
                   ├─ LKG が savedAt から7日以内 ─► stale LKG を返す
                   └─ それ以外 ─────────────────► error を投げる
```

- LKG 保持期間は **7 日**、再試行抑止は **60 秒**。
- **LKG が無い初回障害でも 60 秒の抑止を効かせる。** 直前エラーを保持し、その間は同じエラーを即時再送出する。これにより起動直後・キャッシュ未形成時の障害でも外部 API を毎リクエスト叩かない。
- **HSR 側にも再試行抑止を追加する。** `getStaticIndex` の静的データ取得は複数エンドポイントを並列取得し各 fetch の timeout は5秒。失敗後60秒は再取得せず、LKG があればそれを、無ければ既存仕様どおり `EMPTY_STATIC_INDEX` を即返す。
- 成功時は `nextRetryAt` と保持中の失敗状態を必ずクリアする。
- 内部で `fresh` / `stale` を判別できる状態は保持するが UI 表示は今回のスコープ外。`stale` 返却時は保存時刻のみ `console.warn` に出し、UID は出さない。
- 同時アクセス時に取得を重複実行しない現行 `pending` の挙動は維持する。
### Phase 45: Enka フォールバックのエラー分類と `safeTrpcFetch`

#### 45-1 `server/enkaFallback.ts` の `fetchEnkaPayload`

処理順を変更する。

```
現行: fetch → response.text / JSON.parse → getStaticIndex() → normalize → status 判定
変更: fetch → status 判定 → response.text / JSON.parse → getStaticIndex() → normalize → 0件判定
```

**Content-Type を新たな必須条件にはしない。** 現行は本文を JSON.parse できれば処理できるため、HTTP 200 の JSON 本文が正しいのに Content-Type が欠落・誤設定された場合まで新規に失敗させない。非 JSON は `JSON.parse` 失敗として `BAD_GATEWAY` にする。

分類表（変更前 → 変更後）:

| 条件 | 現行の結果 | 変更後 | メッセージ |
|---|---|---|---|
| 404（JSON） | `NOT_FOUND` | `NOT_FOUND` | 公開中のキャラクターが見つかりません。ゲーム内の巡星ビザ設定をご確認ください。（変更なし） |
| 404（HTML） | `BAD_GATEWAY` | **`NOT_FOUND`** | 同上（分類が変わる） |
| 429 | `BAD_GATEWAY`（文言は「見つかりません」） | **`TOO_MANY_REQUESTS`** | 照会が集中しています。数分後に再度お試しください。 |
| 5xx | `BAD_GATEWAY`（同上） | `BAD_GATEWAY` | 外部データサービスが一時的に応答していません。数分後に再度お試しください。 |
| その他の非2xx（400 / 401 / 403 等） | 多くは `BAD_GATEWAY` | `BAD_GATEWAY` | 外部データサービスから正常な応答を取得できませんでした。数分後に再度お試しください。 |
| 200 だが非 JSON | `BAD_GATEWAY`（`JSON.parse` 例外経由） | `BAD_GATEWAY` | 外部データサービスが一時的に応答していません。数分後に再度お試しください。 |
| Abort / timeout / ネットワーク | `BAD_GATEWAY` | `BAD_GATEWAY` | 公開データサービスへ接続できませんでした。数分後に再度お試しください。（変更なし） |
| 200・JSON・キャラ0件 | `NOT_FOUND` | `NOT_FOUND` | 公開中のキャラクターが見つかりません。（維持） |

- **404 / 429 / 5xx / その他の非2xx のときは `getStaticIndex()` を呼ばない**。
- HTTP 200 でも JSON parse に失敗した場合は `getStaticIndex()` を呼ばず `BAD_GATEWAY`。
- **`!data.characters.length` の 0 件判定は normalize の後に必ず残す**。
- `TRPCError` は外側 catch でそのまま再 throw する既存構造を維持する。
- 文言とコードは `server/gameProviders.ts` / `server/buildAdvisor.ts` の分類へ可能な範囲で揃える。共通関数化は今回行わない。
#### 45-2 `client/src/lib/safeTrpcFetch.ts`

擬似 tRPC レスポンスの自前生成（`trpcErrorResponse`）を**廃止**する（入力文書の案 A）。

```ts
export async function safeTrpcFetch(input, init?, implementation = fetch): Promise<Response> {
  let response: Response;
  try {
    response = await implementation(input, { ...(init ?? {}), credentials: "include" });
  } catch {
    throw new Error("照会サービスへ接続できませんでした。通信環境を確認して再試行してください。");
  }
  const contentType = response.headers.get("content-type") ?? "";
  if (contentType.toLowerCase().includes("application/json")) return response;
  const status = response.status || 502;
  throw new Error(status >= 500
    ? "照会サービスが一時的に応答していません。1〜2分後にもう一度お試しください。"
    : "照会リクエストを処理できませんでした。UIDと公開設定をご確認ください。");
}
```

- `httpBatchLink` は fetch の reject を `TRPCClientError.from(cause)` で包み、**そのバッチに含まれる全 operation へ同じエラーを配る**。したがって「要求数とエラー数の不一致」も「`path` が `build.lookup` 固定」も原理的に起きなくなる。
- メッセージ文言は現行をそのまま流用する（表示の変更なし）。`message` が `TRPCClientError.message` として React Query 側に出ることを回帰テストで固定する。
- JSON 応答（tRPC の正常応答・tRPC 由来の 429）は**無加工でそのまま返す**。Phase 43 で `/api/trpc` を Express 層の通常 JSON 429 から除外するため、`safeTrpcFetch` が受けるアプリ由来 JSON は tRPC エンベロープであることを設計上の不変条件とする。

### Phase 46: Analytics の応答分離と `/admin/display` の Pages 対応

#### 46-1 `server/routers.ts` の `build.lookup`

```ts
const result = await lookupGameBuild(input.game, input.uid);
// Analytics は匿名のベストエフォート。照会応答を待たせない。

  .catch(error => console.error("[Analytics] Failed to record lookup:", error));
```

### Phase 47: UID 応答キャッシュの件数上限・LRU 化

**対象**: `server/buildAdvisor.ts` の `UidResponseCache<T>`。同クラスは HSR の `lookupCache`、原神の `genshinCache`、ZZZ の `zzzCache` の3インスタンスで使用される。

**確定値**:

```ts
const CACHE_MAX_ENTRIES = 256;
```

- **1キャッシュ最大256件、3ゲーム合計最大768件**とする。
- 2026-09-19 時点の Railway production は 1 replica、メモリ上限約 1.0 GB、直近24時間のメモリ使用量最大は約 0.268 GB。初期上限256/キャッシュは現行余力を残す保守的な値として採用する。将来引き上げる場合は1エントリ実測サイズとヒット率を根拠に別変更とする。

**LRU の挙動**:

- `getEntry(key)`:
  1. 無し → `null`
  2. 期限切れ → `delete` して `null`
  3. 有効 → `delete(key)` → `set(key, entry)` で末尾へ移し、最終アクセス順を更新して返す
- `set(key, value, ttlMs)`:
  1. 同一 key があれば `delete`
  2. 新値を `set`（更新でも末尾へ移す）
  3. size が256を超えたら期限切れを全掃除
  4. なお256を超える間、`Map.keys().next().value` の先頭（最も古くアクセスされた key）を削除
- `size` getter と期限切れ削除の既存副作用は維持する。
- TTL、`inFlightLookups` / `genshinInFlight` / `zzzInFlight`、不完全結果を通常キャッシュしない仕様は変更しない。

**受入テスト**:

- 256件までは保持される
- 257件目で LRU 1件だけが削除され、size は256
- `get` したエントリは最終アクセス扱いとなり、その後の eviction で残る
- 既存 key の `set` も最終更新扱いとなり末尾へ移る
- 期限切れがある場合は LRU eviction より先に期限切れを削除する
- 全件有効でも256を超えない
- 既存の「期限切れ `getEntry` が削除する」テストを維持する

## 7. リスクと割り切り

- **レート制限はプロセス内メモリで保持する。** Railway production は 2026-09-19 時点で `iad` 1 replica と確認済み。2 replica 以上へ変更すると実効上限が replica 数倍になるため、**スケールアウト前に Redis 等の共有ストアへ移行することを必須条件**とする。
- **クライアントIPは Railway の `X-Real-IP` を前提とする。** Railway 実行中にヘッダーが欠落した場合は socket address へフォールバックするが、同一プロキシ IP へ収束する可能性がある。production 結合テストで複数クライアントを識別できない場合は Phase 43 を完了扱いにしない。
- **上限値は初期運用値。** 直近ログでは source IP 単位の最大が18 request/min で、全体120/minには十分な余裕がある。`build.lookup` 20/min・同一UID 6/min等は濫用遮断値として開始し、正規利用が429になる実測が出た場合のみ別変更で調整する。
- **Last Known Good は古いデータを返しうる。** 新キャラクター追加直後に外部障害が重なると、そのキャラクターが認識されない期間が最大7日発生する。全面障害より継続利用を優先する。
- **negative caching 中は直前エラーを再送出する。** LKG が無い場合も60秒間は外部再試行しないため、外部復旧直後でも最大60秒は失敗が継続しうる。外部負荷保護とのトレードオフとして許容する。
- **Analytics はプロセス終了時に取りこぼす。** 課金・監査用途ではないため許容する。
- **HTML 404 の分類が変わる。** Enka が 404 を HTML で返した場合、`BAD_GATEWAY` から `NOT_FOUND` へ変える。意図した変更。
- **UID キャッシュは最大768件（3ゲーム合計）。** production のメモリ上限約1GBに対し直近24h最大使用量は約0.268GB。256/キャッシュから開始し、将来の引上げは実測に基づく別変更とする。
- **ロールバック方針**: Phase 42〜47 はそれぞれ独立 PR とし、原則として個別 revert 可能。Phase 43 の tRPC/Express 2層は同一 PR 内で一体として revert する。

## 10. 確定事項・運用前提

本設計の実装判断に必要な未確定事項は残さない。以下で確定する。

1. **UID キャッシュ最大件数**: 256件/キャッシュ。HSR / 原神 / ZZZ 合計最大768件。Phase 47 の独立 PR で LRU 化する。

5. **tRPC 429**: `/api/trpc` は Express 粗いリミッタから除外し、tRPC middleware 内で制限する。通常 JSON の 429 を tRPC endpoint へ返してはならない。
