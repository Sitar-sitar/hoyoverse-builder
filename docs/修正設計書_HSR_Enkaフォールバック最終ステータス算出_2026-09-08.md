## 1. 目的・背景

2026-09-08、同一キャラクター・同一装備について、HoYoverse Builder の `ENKA FALLBACK` 表示と HoYoLAB の公開キャラクターステータスを比較したところ、HP・攻撃力・防御力・速度・会心率・EP回復効率などが一致しなかった。

取得されたキャラクターIDは `hsr:1502` で、キャラクター、レベル、凸、光円錐の同一性は保たれていた。問題はID解決ではなく、`server/enkaFallback.ts` が次の部分値を単純加算し、最終値として返していることにある。

- 遺物の `_flat.props`
- 一部だけ選択された軌跡プロパティ
- キャラクターの速度・会心率・会心ダメージの初期値

現在の実装はキャラクターと光円錐のレベル別基礎HP・攻撃力・防御力を合成せず、割合値と固定値の適用順も区別していない。さらに、光円錐の重畳ランク由来の常時有効プロパティ、EP回復効率の100%基準、プロパティの正式名称を扱っていない。このため、遺物の固定HP `782`、固定攻撃力 `471`、固定防御力 `78` が、そのままキャラクターのHP・攻撃力・防御力として表示された。

- HP、攻撃力、防御力、速度、会心率、会心ダメージ、撃破特効、効果命中、効果抵抗、EP回復効率、属性ダメージ、愉悦度を含む公開ステータスの正規化。

## 3. 現状・再現事実・制約

### 3.1 現在の取得ルート

```text
Home.tsx

  -> server/routers.ts applyBatch15CuratedOverrides(lookupGameBuild(...))
  -> server/gameProviders.ts lookupGameBuild("hsr", uid)
  -> server/buildAdvisor.ts lookupUidBuild(uid)

```

`server/batch15CuratedData.ts` は対象キャラクターのガイド、比較、提案を差し替えるが、`allStats` 自体は変更しない。したがって本件の根本原因は、その前段のEnka正規化にある。

### 3.2 ユーザー提示画面による差分

同じ公開プロフィールを同時点で比較した代表値は次のとおりである。UIDとプレイヤー名は設計書・テストfixture・ログへ保存しない。

| ステータス | 現在のBuilder | HoYoLAB | 現在実装の問題 |
| --- | ---: | ---: | --- |
| HP | 782 | 4612 | 遺物の固定HPだけを表示 |
| 攻撃力 | 471 | 1543 | 遺物の固定攻撃力だけを表示 |
| 防御力 | 78 | 1262 | 遺物の固定防御力だけを表示 |
| 速度 | 170.4 | 198 | 光円錐・軌跡を含む合成が不足 |
| 会心率 | 68.6% | 73.9% | レベル条件付きの解放済み軌跡が欠落 |
| 会心ダメージ | 90.8% | 90.8% | この項目は偶然一致 |
| EP回復効率 | `SPRatioBase 0` | 119.4% | 正式名称・100%基準・割合表示が欠落 |
| 効果抵抗 | 7.8% | 7.7% | 取得元精度と表示丸めの差を要統一 |
| 愉悦度 | `ElationDamageAddedRatioBase 10` | 10.0%相当 | 内部キーがUIへ漏出 |

公開静的データと画面の黒字基礎値を照合すると、このキャラクターと光円錐の合算基礎値はHP約2300、攻撃力約994、防御力約1184である。画面の値は概ね次の式で再現でき、現在表示の782・471・78が固定加算分であることを確認できる。

```text
HP     = 2300 × (1 + 66.5%) + 782 ≒ 4612
攻撃力 =  994 × (1 +  7.8%) + 471 ≒ 1543
防御力 = 1184 × (1 +  0.0%) +  78 ≒ 1262
```

### 3.3 現在コードで確認した欠落

- `StaticIndex` と `getStaticIndex()` は `light_cone_promotions`、`light_cone_ranks`、`properties` を取得しない。
- `characterBase()` は速度・会心率・会心ダメージだけを返し、HP・攻撃力・防御力およびレベルごとの `step` を無視する。
- `totalsFrom()` は固定値と割合値を表示名ごとに足すだけで、基礎値に割合を乗算しない。
- `traceProperties()` は静的データ側の必要キャラクターレベルと、Enka側のノードランクを同じ尺度として比較する。レベル80で解放済みの会心率5.3%ノードが落ち、画面差分5.3ポイントと一致する。
- `property()` はハードコードされた一部名称しか持たず、`SPRatioBase` と `ElationDamageAddedRatioBase` を正式名称へ解決できない。
- `calculatedValue(target.label, totals)` は表示ラベルをキーにするため、`攻撃力（モチーフなし）`、`会心率（出雲込み）` など注記付きラベルを正規化済み統計へ対応付けられない。
- 静的JSONの取得失敗は空オブジェクトへ変換され、不完全な結果でも正常応答・UIDキャッシュの対象になる。
- 既存テストは「基礎速度＋遺物速度」の部分和 `112.9` を正解として固定しており、HP・攻撃力・防御力、光円錐、EP回復効率、レベル80軌跡を検証していない。
- `docs/guide_sources.md` は基礎値・解放済み軌跡・遺物に基づく比較値と説明しているが、現在コードはその契約を満たしていない。

StarRailResは `character_promotions`、`character_skill_trees`、`light_cone_promotions`、`light_cone_ranks`、`properties`、`relic_sets` を同じ言語別インデックスとして公開している。[StarRailRes README](https://github.com/Mar-7th/StarRailRes/blob/master/README.md?plain=1)

### 3.4 制約

- EnkaのHSR応答には完成済みキャラクターステータス一覧がなく、`avatarDetailList` のレベル・昇格・光円錐・遺物・軌跡から組み立てる必要がある。
- 遺物 `_flat.props` は表示値より高い内部精度を含む場合がある。中間計算では丸めず、表示時だけ丸める。
- 外部静的データは更新・スキーマ変更・一時障害があり得る。必須データ欠落を0として補完しない。
- 現在の公開APIクライアントとの互換性を維持し、既存フィールドを削除・改名しない。
- 実UIDや生レスポンスは個人識別につながり得るため、テスト、設計書、ログ、エラーメッセージへ残さない。

## 4. 設計方針

### 4.1 単一の最終ステータスを作る

Enkaフォールバックでは、内部の `StatKey` ごとに次のカテゴリを分離して保持する。

1. 基礎値: キャラクター、光円錐。
2. 割合加算: HP%、攻撃力%、防御力%、速度%など。
3. 固定加算: HP、攻撃力、防御力、速度など。
4. 独立割合: 会心率、会心ダメージ、撃破特効、効果命中、効果抵抗、EP回復効率、属性ダメージ、愉悦度など。

カテゴリを合成した `FinalStatMap` を唯一の値源とし、`allStats`、`comparisons.current`、`recommendations`、`equipmentActions` はすべて同じMapから生成する。遺物表示カードだけは、従来どおり個々の `_flat.props` を表示する。

### 4.2 表示名ではなく `StatKey` を主キーにする

内部集計、合成、比較は既存の `StatKey` を使う。日本語表示名は出力時の属性とし、注記付きの目標ラベルを検索キーにしない。

最低限、次の対応を一元化する。

| `StatKey` | StarRailRes/Enka型の例 | 日本語表示名 |
| --- | --- | --- |
| `hp` | `BaseHP`, `HPDelta` | HP |
| `hpPercent` | `HPAddedRatio` | HP% |
| `attack` | `BaseAttack`, `AttackDelta` | 攻撃力 |
| `attackPercent` | `AttackAddedRatio` | 攻撃力% |
| `defense` | `BaseDefence`, `DefenceDelta` | 防御力 |
| `defPercent` | `DefenceAddedRatio` | 防御力% |
| `speed` | `BaseSpeed`, `SpeedDelta` | 速度 |
| `speedPercent`（内部） | `SpeedAddedRatio` | 速度% |
| `critRate` | `CriticalChance`, `CriticalChanceBase` | 会心率 |
| `critDmg` | `CriticalDamage`, `CriticalDamageBase` | 会心ダメ |
| `breakEffect` | `BreakDamageAddedRatio` | 撃破特効 |
| `effectHitRate` | `StatusProbability`, `StatusProbabilityBase` | 効果命中 |
| `effectRes` | `StatusResistance`, `StatusResistanceBase` | 効果抵抗 |
| `energyRecharge` | `SPRatioBase` | EP回復効率 |
| `elation`（内部） | `ElationDamageAddedRatioBase` | 愉悦度 |

名称、割合か固定値か、表示精度は可能な限り `properties.json` のメタデータを使う。アプリ固有の `StatKey` 対応表は比較・式のために残すが、日本語名を個別ハードコードで増やす方式は採らない。未知プロパティは内部診断へ記録し、内部キーを一般画面へそのまま表示しない。

### 4.3 公開プロフィールに含める効果の境界

含めるのは、キャラクター詳細画面を開いた時点で常時反映される戦闘外の値だけとする。

| 入力 | 取扱い |
| --- | --- |
| キャラクターのレベル別基礎値 | 含める |
| 光円錐のレベル別基礎値 | 含める |
| 遺物のメイン・サブステータス | 含める |
| `skillTreeList` に存在する解放済みステータス軌跡 | 含める |
| `light_cone_ranks.properties` の常時有効ステータス | 含める |
| 遺物セットの無条件かつキャラクター画面へ反映されるプロパティ | 実測fixtureで反映を確認したものだけ含める |
| 戦闘開始、スキル使用、敵状態、編成、ターン、HP条件などを要する効果 | 含めない |
| 効果説明の `params` にしか存在しない条件付き数値 | 含めない |
| 凸効果、推奨PTによる戦闘中補正 | 現在値へ含めず、既存の目標変更・注記へ残す |

常時有効か判別できないプロパティを推測で加算してはならない。新しい型が出た場合はfixtureとHoYoLAB表示で分類を追加する。

### 4.4 必須データはfail closedにする

静的データ取得が部分的に失敗した場合、空Mapを正常値として新しいキャッシュへ保存しない。静的バンドル全体を検証し、必須Mapと対象IDがそろった場合だけ算出する。

キャラクター単位で最終値を保証できない場合は次の状態にする。

- キャラクターと装備の公開情報は、解決できる範囲で表示する。
- `allStats` は不完全な部分和を返さない。
- `comparisons.current` は `null`、達成状態は `null`、強化提案は生成しない。
- `statsNote` に「最終ステータスを算出できないため比較を保留した」旨を3言語で表示する。
- 内部診断にはUIDや生payloadを含めず、欠落したデータ種別・対象source ID・取得元だけを記録する。
- 不完全なキャラクター結果を通常のUIDキャッシュへ保存しない。

既存API互換のため既存フィールドは維持する。状態の明示が必要な場合は `CharacterProfile.statsStatus?: "final" | "unavailable"` を追加し、旧レスポンスを受けるUIはフィールド欠落を従来の最終値として扱う。

### 4.5 キャッシュは完成した値だけを保持する

- UIDキャッシュのTTL範囲（1分〜10分）とキーは維持する。
- `dataSource` をキャッシュ値へ含め、キャッシュヒット時も `ENKA FALLBACK` 表示が失われないことを保証する。
- 静的データは、全必須Mapの構造検証に成功したバンドルだけを24時間キャッシュする。
- 24時間経過後の更新に失敗した場合は、プロセス内の直近正常バンドルを最大7日まで使用できる。使用時は内部警告を残す。
- 直近正常バンドルがない、7日を超えた、または対象IDがない場合は0補完せず `unavailable` とする。
- 修正版デプロイ時はプロセス再起動で旧UIDキャッシュを破棄する。永続キャッシュ移行は不要である。

## 5. 詳細仕様

### 5.1 静的データバンドル

`server/enkaFallback.ts` の `StaticIndex` は少なくとも次を保持する。

- `characters`
- `lightCones`
- `relicSets`
- `characterPromotions`
- `characterSkillTrees`
- `lightConePromotions`
- `lightConeRanks`
- `properties`

取得は並列とするが、各レスポンスについてHTTP成功、JSON object、対象Mapの非空を検証する。静的取得には5秒の上限を設け、既存Enka本体14秒、MiHoMo主取得6秒の予算を無制限に延ばさない。中止・タイムアウト・JSON不正は静的バンドル更新失敗として扱う。

### 5.2 レベル別基礎値

キャラクターと光円錐のレベル別値は、対象ID・`promotion`・`level` に対応する `values[promotion]` の `base` と `step` から算出する。

```text
levelValue = base + step × (level - 1)
```

入力レベル・昇格段階は有限整数かつ静的データの範囲内であることを検証する。範囲外を端値へ丸めて正常化してはならず、そのキャラクターを `unavailable` とする。

光円錐の `equipment._flat.props` に同じレベルの `BaseHP`、`BaseAttack`、`BaseDefence` がそろう場合は、その高精度値を優先できる。欠落時は `light_cone_promotions` から同じ式で算出する。両方あるfixtureでは許容差内で一致することをテストし、不一致時はEnka個体値を優先して内部警告を残す。

### 5.3 軌跡の選択

`skillTreeList` に存在する `pointId` は解放済みノードとして扱う。`node.level` はノード内の効果ランクであり、静的 `levels[].level` の必要キャラクターレベルと直接比較しない。

1. `pointId` で `character_skill_trees` を解決する。
2. `node.level` に対応する効果段階を1始まりで選ぶ。
3. 静的段階が要求する `promotion` とキャラクターレベルを、avatarの `promotion`・`level` に対して検証する。
4. 選択段階の `properties` だけを一度加算する。
5. 不正なランク、存在しないpointId、要件不一致は0補完せず診断対象にする。

レベル80で解放される会心率5.3%のように、必要キャラクターレベルとノードランクが異なる値でも除外されないことをfixtureで固定する。

### 5.4 光円錐ランク

`equipment.tid` と `equipment.rank` で `light_cone_ranks` を解決する。選択した重畳ランクの `properties` は戦闘外の常時有効値として集計する。説明文の可変 `params`、戦闘条件を要する効果は集計しない。

`rank` の基数はEnkaと静的データで明示的に変換し、S1をS2として扱うoff-by-oneを防ぐ。S1とS5の境界fixtureを用意する。

### 5.5 最終値の合成式

全中間値はJavaScriptの有限数として保持し、表示前に丸めない。

```text
baseHP      = characterHP + lightConeHP
baseAttack  = characterAttack + lightConeAttack
baseDefence = characterDefence + lightConeDefence

finalHP      = baseHP      × (1 + hpRatioTotal)      + hpFlatTotal
finalAttack  = baseAttack  × (1 + attackRatioTotal)  + attackFlatTotal
finalDefence = baseDefence × (1 + defenceRatioTotal) + defenceFlatTotal
finalSpeed   = characterBaseSpeed × (1 + speedRatioTotal) + speedFlatTotal

finalCritRate       = 5%   + unlockedAndEquipmentCritRate
finalCritDamage     = 50%  + unlockedAndEquipmentCritDamage
finalEnergyRecharge = 100% + unlockedAndEquipmentEnergyRecharge
```

静的キャラクターデータに会心率・会心ダメージ・EP回復効率の基準値がある場合は、その値を優先し、5%・50%・100%は欠落時のゲーム共通既定として使う。既定を使用した事実はテスト可能な診断情報として保持する。

撃破特効、効果命中、効果抵抗、属性ダメージ、愉悦度などは0%を基準とし、対象プロパティを加算する。光円錐が基礎速度そのものを持つ場合だけ速度の基礎項へ加える。

### 5.6 比較・提案

`guide.targets` の比較は `target.label` ではなく `target.key` で `FinalStatMap` を参照する。注記付きラベルでも同じ値を参照する。

```text
target.key = attack
target.label = 攻撃力（モチーフなし）
=> FinalStatMap.attack を比較する
```

現在値が `unavailable` の場合、達成・未達を確定しない。未取得を0として不足量や装備変更を提案しない。パーティ・凸による既存の目標側補正は、最終値算出後に従来どおり適用する。

### 5.7 表示

- HP・攻撃力・防御力は最終値を整数表示する。
- 速度は内部精度を保ち、小数第1位まで表示する。整数の場合の末尾 `.0` は既存UI方針に合わせて省略してよい。
- 割合は小数第1位まで表示する。
- HoYoLABと取得元の丸め差について、整数ステータスは±1、速度・割合は±0.1を受入許容差とする。許容差を超える差は算出不一致である。
- ステータス順は `HP -> 攻撃力 -> 防御力 -> 速度 -> 会心率 -> 会心ダメ -> 撃破特効 -> 効果命中 -> 効果抵抗 -> EP回復効率 -> 属性/特殊値` を基本とする。
- `SPRatioBase`、`ElationDamageAddedRatioBase` などの内部キーを一般画面へ表示しない。
- Enka時の `statsNote` は「公開中のキャラクター・光円錐・遺物・解放済み軌跡から算出した戦闘外最終値。戦闘中・条件付き効果は含まない」という意味を3言語で表示する。
- `ENKA FALLBACK` の取得元表示は維持する。

## 6. 既存機能の非破壊条件

- `CharacterProfile` の既存フィールドとtRPC `build.lookup` の入力を削除・改名しない。
- キャラクターID `hsr:1502`、名称、属性、運命、凸、光円錐名、遺物カード、個別ガイド、PTを変えない。
- MiHoMo成功時はEnka用算出を通さず、既存の取得元最終値を表示する。
- 原神・ZZZのテストfixtureと公開照会結果に差分を出さない。
- 戦闘中・条件付き効果を現在値へ加えない既存データ規約を維持する。
- `targets: []` の「固定目標値が未登録」分岐を維持する。
- UIDは従来どおりブラウザ端末内にのみ保存し、サーバー側に新しい永続化を追加しない。
- 外部API障害を理由に、静的なキャラクター図鑑を利用不能にしない。

## 8. テスト・検証

## 10. リスク・ロールバック

| リスク | 予防 | 検出 | 回復 |
| --- | --- | --- | --- |
| 常時効果と条件付き効果を混同 | `properties` と `params` を分離し、採用表をfixture化 | HoYoLAB同時点差分、値源別単体テスト | 問題の効果型を非採用にし再デプロイ |
| 静的データのスキーマ変更 | object・必須Map・対象IDを検証 | 静的取得テスト、内部警告 | last-known-goodへ退避、算出不能は保留 |
| レベル・重畳ランクのoff-by-one | 境界fixtureと範囲検証 | Lv1/Lv80、S1/S5テスト | 該当変換を修正し旧結果をキャッシュしない |
| 丸め順による1差 | 中間値を丸めず最後だけ表示整形 | ±1/±0.1の受入比較 | 表示整形だけ修正し算出値を維持 |
| Enka改善がMiHoMo等へ波及 | 分岐とテストを取得元別に維持 | 全回帰とレスポンス比較 | Enka変更コミットをrevert |
| 静的取得追加で応答時間増加 | 並列取得、24時間キャッシュ、5秒上限 | 冷間・温間の経過時間計測 | last-known-good使用、必要なら静的データ同梱を別設計 |
| 不完全値を再キャッシュ | 完全性判定後だけUIDキャッシュへ保存 | 欠落Mapとキャッシュテスト | API再起動でメモリキャッシュ破棄 |

ロールバックは第18パッチの実装コミットをrevertし、RailwayとPagesを直前の正常コミットへ戻す。現在のEnka部分値表示は正しい仕様ではないため、ロールバック中も「誤値を正値として継続表示」するより、HSR Enkaフォールバックの比較を一時的に利用不能として明示する方を優先する。DB変更はないためデータ移行・復元は不要である。

## 11. 採用しない案

### 11.1 Enkaフォールバックを廃止する

MiHoMo一時障害時にHSR照会全体が利用不能になるため採用しない。フォールバックを維持し、算出契約を正しく実装する。

### 11.2 遺物由来の部分値を「推定値」として残す

HP782、攻撃力471のような値は最終値の近似ではなく、固定加算成分にすぎない。目標比較と強化提案を誤らせるため採用しない。

### 11.3 HoYoLAB画面値をキャラクター別にハードコードする

装備・レベル・軌跡が変わるたび破綻し、全公開キャラクターへ一般化できないため採用しない。

### 11.4 日本語表示ラベルを集計キーにする

注記・翻訳・表記差で比較不能になるため採用しない。`StatKey` を正規化主キーとする。

### 11.5 静的JSON欠落を0で補完する

部分値を正しい最終値に見せる現在不具合を再発させるため採用しない。

## 12. 未確定・要確認事項

- **非ブロッキング**: HoYoLABとEnkaの小数表示規則は項目ごとに差があり得る。第18パッチでは内部精度を維持し、整数±1・速度/割合±0.1の数値一致を合格条件とする。完全な文字列一致が必要と判明した場合は表示整形だけを追補する。
- **非ブロッキング**: 遺物セットの無条件プロパティがキャラクター詳細画面へ反映される範囲は、代表fixtureで採否表を確定する。条件不明の値を先に加算しない。
- **実装開始時確認**: StarRailResの現在スキーマで `light_cone_ranks` のrank基数と `character_skill_trees.levels` の選択規則をfixture化する。スキーマが本書の前提と異なる場合は、コードで推測せず本書を先に改訂する。
- **本番受入時確認**: 同時点比較に使う公開UIDについて、ユーザーの明示許可を得る。許可がなければ本番の数値一致ゲートは未完了として残す。

現時点で、実装着手を妨げる未決定事項はない。
