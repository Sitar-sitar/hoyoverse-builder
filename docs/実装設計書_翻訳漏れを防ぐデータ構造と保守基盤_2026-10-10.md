## 1. 目的・背景

利用者の決定は「今は翻訳しない」「キャラ詳細・通常スキル詳細・凸・推奨ビルドなどで、将来日本語を追加しても翻訳対象が漏れない」「メンテナンスしやすい構造へ修正する設計書を作る」の3点である。

完了の意味を分ける。**構造移行の完了は、日本語の挙動を保ち、未翻訳や未登録を正しく列挙できること。翻訳完了ではない。** 機械検査によって対象・版の漏れを検出する。訳文の意味・公式名称の正しさは、後続の翻訳レビューが必要であり、ハッシュや文字種の検査では保証しない。

## 2. スコープ

### 2.1 IN

- 日本語表示文章の単一正本、固定項目ID、共通の翻訳レコード、原文変更検知、完全性検査。

- 通常スキルとキャラ紹介は将来の入力先と未登録状態を定義する。現在ない解説や効果数値は作らない。
- 既存日本語・既存英語・既存中国語を変更せず移す。既存訳は未確認として保全する。
- 図鑑とUID照会の両経路に表示用データを供給する。既存APIと計算ロジックを維持する。
- 差分抽出、構造検査、将来の言語公開可否検査、CI・ビルドへの組込み。

### 2.2 OUT（既存挙動を保つ）

- 翻訳の実施、機械翻訳APIへの送信、翻訳サービス選定、訳文の修正・一括承認。
- スキルや人物紹介の新規調査・取得、装備推奨・目標値・PT採用順位・凸補正の変更。

## 4. 設計方針

### 4.1 採用構成

Git管理のTypeScriptデータを正本とする。ドメインデータの文章欄は `TextRef`、文章の日本語定義は用途ごとのカタログ、訳文は英語・簡体字の別ファイルに分離する。既存型の三言語オブジェクトは公開互換アダプターで組み立てる。

- `shared/content/types.ts`（新規）: 型だけ。ブラウザにNode依存を持ち込まない。
- `content/ja/`（新規）: ui、terms、characters、skills、guides、constellations、teams、history。ゲーム別・キャラ別・チーム別に適度に分割。
- `content/translations/en/` と `content/translations/zh-CN/`（新規）: 同じ分類単位の既存訳と将来の訳。
- `content/coverage/`（新規）: 必須セクション・未収集理由・ID移行対応表・例外の明示記録。
- `server/content/`（新規）: 正本組立て、参照検証、表示投影、公開可否。
- `scripts/content/`（新規）: 移行、manifest生成、対象出力、検査。
- `client/src/content/`（新規）: UIで使う文章だけの生成成果物と共通resolver。

全データを1つの巨大JSONにしない。同じ文章でも意味・用途が異なるなら別IDにする。共通用語のみ意味を確認して共有する。共有PTの文章はTeam.id単位で1件保持し、キャラごとにコピーしない。

### 4.2 代替案と判断

| 案 | 判断 |
| --- | --- |
| 現行のja/en/zhを全箇所に手で追加 | 原文更新の追従を管理できず重複が増えるため不採用 |
| 翻訳SaaS・DB編集機能を先に導入 | 外部同期・認証・復旧の保守負担が増える。現段階では不要 |
| すべての文章を日本語文字列検索で抽出 | 数値・コード・内部ログとの区別や、項目そのものの欠落を検出できない |
| 公開APIの既存stringを即TextRefへ置換 | 旧Pages・計算・既存テストを壊すため不採用 |
| 項目ID＋別訳文＋型・実データ検査＋追加表示DTO | 採用。データの単一正本と既存互換性を両立 |

## 5. 共通文章・翻訳の詳細仕様

### 5.1 項目IDと参照

`TextRef = { kind: "textRef"; id: TextId }` とする。IDは `character.<game>.<sourceId>.name`、`guide.<game>.<sourceId>.<guideId>.headline`、`skill.<game>.<sourceId>.<skillId>.description`、`constellation.<game>.<sourceId>.<level>.description`、`team.<Team.id>.synergy.<blockId>`、`history.<eventId>.summary`、`ui.<screen>.<key>` のように名前空間を持つ。

sourceIdは確認済みIDに限る。未解決の場合はmigration対応表の固定legacy IDで保全し、確認後に明示的なaliasを登録する。同名・別形態を統合しない。既存Team.idに日本語が含まれていても互換のため維持する。配列添字・表示名・日本語本文から毎回IDを生成しない。新規段落・スキル・履歴イベントには固定blockId/skillId/eventIdを付け、順番は別フィールドで保持する。

カタログは重複ID、未知参照、別gameの参照、循環alias、複数定義を拒否する。ID変更時は参照・訳文・履歴の移行表を同じ変更に含める。

### 5.2 日本語の定義

`SourceText` の必須フィールドは id / ja / context / placeholders / dependencies / audience。jaは空白のみを不可とする。contextはゲーム・項目種別・視点・用語の意味を含み、翻訳者向けの情報とする。audienceは public または admin。サーバ内部ログ・非表示の精査メモは翻訳不要の内部型で明示する。

placeholdersは `{name}`, `{count}`, `{value}`, `{unit}` 等の名前と型・出典を宣言する。dependenciesには名称・用語等、意味を変える参照IDとその契約版を列挙する。表示文章は平文または宣言済みテンプレートのみ。HTML挿入、任意コード実行、訳文からの計算はしない。

### 5.3 翻訳レコードと状態

`TranslationRecord` は text / sourceHash / review / origin / reviewedAt? を持つ。reviewは pending または approved、originは legacy または reviewed。訳文なしはレコード自体を持たず、空文字・日本語コピーで埋めない。

| 導出状態 | 判定 |
| --- | --- |
| missing | 対象言語レコードがない、またはtextが空白のみ |
| stale | sourceHashが現在と不一致、または移行時にnullのまま |
| pending | ハッシュ一致だがreviewがpending |
| approved | ハッシュ一致、reviewがapproved、必須検査合格 |
| invalid | 未知ID、変数不一致、alias不正、レコード形式不正など |

状態と件数は生成し、手動の「翻訳済み」フラグや台帳の集計値を正本にしない。reviewの変更は後続の翻訳確認作業だけで行う。本構造移行では既存訳すべて `review: pending, origin: legacy, sourceHash: null`。**現在の日本語がその既存訳の翻訳元だった証拠はないため、移行時のハッシュ一致を捏造しない。**

### 5.4 原文ハッシュと変更検知

Node標準のSHA-256を用いる。入力はschemaVersion、id、ja、context、変数の名前・型、依存契約版をキー順の固定JSONで直列化したUTF-8。改行のみLFへ統一し、jaのtrim・空白圧縮・Unicodeの同一視はしない。変数と依存はID順にソートする。生成側はハッシュを毎回計算するが、翻訳側のsourceHashを自動更新しない。

日本語・文脈・変数・意味依存の変更でstaleにする。配列順やファイル移動だけではstaleにしない。訳文を作成する後続工程は取得時のハッシュを添え、取込時に現ハッシュと一致しない候補を拒否する。用語の意味を変更する場合も依存契約版を更新し、該当文章を再確認対象へする。

### 5.5 同一文・数値・名称

日本語と同じ訳文は自動合格にしない。HP・ATK・URL等は用語単位で `sameTextAllowed` と理由を登録し、レコードの版を検査する。日本語文字・漢字の有無は補助警告のみとし、完了判定に使わない。

固定数値・単位・効果量はドメイン側で保持し、可能なら変数として文章へ挿入する。現在の自由文に埋まった数値は本移行では一字も書き換えず、保護トークンとして原文側に登録する。将来の訳文取込ではトークン一致を検査し、数字の意味や条件の対応はレビューで確認する。

正式名称はゲーム＋確認済みID＋種類をキーに持つ名称辞書へまとめる。取得元の言語名、取得日・版・出典を保持する。今回新しく外部の英語・中国語名称を取得しない。現在ある名称だけを保全し、日本語のまま入っていたen/zhはpendingとして列挙する。プレイヤー名など利用者入力は翻訳せず表示する。

## 6. 各領域のデータ構成

### 6.1 キャラ詳細

`CharacterContent` は identityKey / nameRef / elementKey / roleKey / introduction / skills を持つ。introductionは `Section<TextRef[]>`、skillsは `Section<SkillDefinition[]>`。game/sourceId/variantOfを識別子として維持する。既存name-based API入力や台帳キーは互換対応表で維持し、訳文から逆引きしない。

`Section<T>` は次の判別共用体とする。

- registered: dataと根拠を持つ。必須配列が0件なら不正。
- notCollected: reasonとrequiredKinds等の期待項目を持つ。dataは持たない。
- notApplicable: reasonと根拠を持つ。情報がないだけの場合は使用不可。

紹介・スキルが現存しないキャラは全件notCollectedとし、空のregisteredや「準備中」という文章で登録済み扱いにしない。既存キャラ精査台帳のreviewedと新しいcontent completenessは別軸である。

### 6.2 通常スキル詳細

`SkillDefinition` は skillId / kind / order / nameRef / descriptionRef / effects / notes / sources を持つ。effectsは固定effectId、条件のTextRef、levelと数値・unit・scalingKey・参照StatKeyを持つ配列。効果数値は不明ならunknownを明示し、推測して埋めない。スキル定義は表示用で、現在値や比較目標へ加算しない。

`content/coverage/skillRequirements.ts` にゲーム別の期待種類を登録する。

| ゲーム | 期待する分類 |
| --- | --- |
| HSR | 通常攻撃、戦闘スキル、必殺技、天賦、秘技、追加能力・軌跡。召喚物・別形態等は個別の期待項目として明示 |
| 原神 | 通常攻撃、元素スキル、元素爆発、固有天賦。派生攻撃・形態は確認済み定義に従う |
| ZZZ | 通常攻撃、回避、支援、特殊スキル、連携スキル、終結スキル、コア・追加能力。複数技は固定IDで区別 |

種類だけで全キャラのスキル数を断定しない。キャラごとの期待スキルID一覧は出典確認後に登録する。未収集時は期待種類を未確定のまま報告し、全スキル完備とは判定しない。今回の構造実装では収集や新規表示を行わず、notCollectedを正しく検出できれば構造ゲートは合格する。

### 6.3 推奨ビルドと計算の分離

`GuideContent` は guideId / headlineRef / equipmentRecommendations / mainStatPreferences / targetDefinitions / targetContextRef? / sourceRefs を持つ。装備推奨は固定recommendationId、セットID・必要個数・選択肢・優先順・理由Section・代替候補Sectionを持つ。現行の複合セット文字列を推測解析しない。未確認の装備IDは固定legacy参照と原文を保全し、ID未解決として報告する。

mainStatPreferencesはslotKey、statOptions（StatKeyまたは安定したmain-statキー）とvalueRefを分離する。targetDefinitionsは既存StatKey / unit / 数値 / labelRefを持つ。評価水準は内部tierKey（strict/goal/base）に整理可能だが、公開互換フィールドの「厳選」「目標」「妥協」は変更しない。

現行の計算は日本語文字列を利用しているため、**計算用GuideDefinitionを日本語互換投影で供給し続ける**。表示用TextRefや訳文を `equipmentActionsFor`、部位判定、target比較へ渡してはいけない。slot/statの安定キーは同時に定義するが、計算の安定キー移行は全件の旧判定との同値性を検証できたものだけに限定し、未解決分は現行日本語判定を維持する。今回の目的のために計算式を改修しない。

headline・relicSet・planarSet・mainStats.slot/value・targets.label・targetContext・sourceLabel、強化理由・装備操作理由は表示対象に登録する。現在ない採用理由・代替候補はnotCollectedとし、追加文章を生成しない。

### 6.4 凸・推奨PT・関連編成

凸は現在の段数・名称・説明・注意・targetChangesの値を保全し、すべての文章をTextRefにする。名称の汎用ラベルがある場合も、正式名称と同一と認定しない。凸数・データ状態curated/preparingは翻訳状態と別軸で維持する。

Team.id、共有化、origin、保存順、refs、viewId、見送り、履歴連動は既存正本の契約を維持する。文章定義はチーム側1件とし、`resolve.ts` と `appearances.ts` の両方から同じIDを参照する。メンバーはnameRefに加えて確認済みidentityKeyを持つ。現行のname.jaによる本人判定は日本語互換投影を使い続ける。

タイトル・役割・相性の全段落・targetSummary・補正label/reason・出典label・communitySources.note/labelを検査する。先頭のsynergyだけを検査して後続段落を漏らさない。推奨外の関連編成も検査対象に含める。非公開のPartySkip.reasonは内部記録として明示し、翻訳対象からの除外理由を登録する。

### 6.5 更新履歴・画面文言・外部取得データ

履歴イベントへ固定eventIdと変更行blockIdを追加する。`PartyLinkBatch.summary`等はテンプレートIDと型付き変数へ置換し、計算した数・名称を渡す。イベント順・日時・文章・更新判定は日本語投影で同一にする。title / summary / 全changes / rationale / sourceNote / 公開される精査基準・参照範囲を含める。

`LanguageContext`と画面ローカル辞書は共通UIカタログへ移す。固定コード・ブランド名等はliteral許可表に理由を持ち、それ以外のユーザー向け文字列は参照・テンプレートを使う。エラーメッセージは安定errorCode＋UI文章へ対応させ、内部ログや未知の外部エラー本文を翻訳完了の分母に混ぜない。

外部プロフィールの値・装備ID・name等の元データを改変しない。既存日本語の表示は維持する。多言語名称を保証できない項目はunresolvedとして表示準備レポートへ載せる。未知IDを別キャラ・装備へ推測置換しない。取得元に多言語辞書があっても、今回追加取得・翻訳・公式訳確認はしない。

## 7. 網羅性とメンテナンスの仕様

### 7.1 3段階の検査

1. **構造**: 項目型、ID、参照、重複、必須セクション、未登録状態の理由、未知フィールド、ID対応表、UIバイパスを検査。
2. **情報の充足**: 登録文章数、未収集セクション数、期待スキル未確定数、未解決名称数を別々に報告。
3. **言語の準備状態**: 英語・中国語ごとにmissing/stale/pending/invalid、用語・変数・保護トークンを検査。

notCollectedは構造上有効だが情報完備ではない。空配列やnotApplicableで分母を減らして100%にしない。未確認訳をハッシュ更新だけでapprovedにしない。日本語のみの構造移行は、2・3段階の未完了を明示して受け入れられる。

### 7.2 対象の登録漏れを防ぐ方法

各ドメインの表示モデルはTextRef/名称参照/明示literal/数値に制限する。TypeScriptの型検査だけでなく、正本を厳密なスキーマで実行時検査し、未知のフィールドを拒否する。

ドメインごとのvisitorを実装し、全セクション・全配列要素・templates・関連編成を列挙する。型のキーを全列挙したfield policyを必須にして、文章フィールド追加時にvisitorが未対応ならコンパイルエラーにする。正本を一度連結してmanifestを生成する。手書きの対象一覧を別正本にしない。

UIはTypeScript ASTでJSX文字列・文字列属性・ユーザー表示用定数の直接使用を検査する。resolver・明示literal・互換境界以外の表示経路を許可しない。既存互換境界は固定ファイル・記号・理由・撤去段階を登録し、範囲が増えたらCIで拒否する。コード全体の日本語grepだけには依存しない。

### 7.3 コマンド契約（今後追加するコマンド）

| コマンド | 挙動・終了コード |
| --- | --- |
| `pnpm content:check` | 全構造、参照、UI迂回、生成物一致を検査。0=合格、1=不正。訳文不足・notCollected自体では失敗させない |
| `pnpm content:report -- --format json` | 全件の情報充足・言語状態・影響先を標準出力。0=生成成功、1=不正。UID/利用者データを読まない |
| `pnpm content:export -- --language en`（zh-CNも同様） | 未翻訳・要更新・確認待ちのid/ja/旧訳/context/hash/変数/依存/利用箇所を標準出力。外部送信・翻訳・書込みなし |
| `pnpm content:ready -- --language en --scope public` | 公開対象でmissing/stale/pending/invalid/必要情報欠落が0なら0、準備未完了なら2、構造不正なら1 |
| `pnpm content:generate` | 決定的にmanifest・UI成果物を生成。翻訳レコードや正本を書き換えない |

report/exportはid順に出力し、同じ入力は同じ内容とする。時刻・絶対パス・UIDを成果物に含めない。大量データは分類別に出力できるが、全件検査を省略しない。失敗時の一部レポートをPASSとして扱わない。

日常運用は日本語正本を編集 → generate → check → report/export → 日本語の構造変更をレビュー、の順。翻訳は別依頼でexportの対象だけを処理する。日本語追加によるpending/stale増加を隠さず、キャラ・項目・言語・利用画面を報告する。

## 8. API・画面・公開言語の互換仕様

### 8.1 既存API

`build.lookup/reference/referenceCatalog/guideHistory` の既存入力と既存フィールド型は維持する。既存stringは日本語互換投影、既存LocalizedTextは保全した旧三言語の投影とする。公開互換型はメタデータを内包しない。古いフィールドへTextRefや状態オブジェクトを直接入れない。

追加フィールド `presentation` をschemaVersion 1の表示DTOとし、contentRevision、キャラの表示セクション、ガイド、凸、PT、関連編成、表示状態を持つ。版付きDTOを共通型に置き、TextRefを解決済みの日本語と状態へ投影する。本構造移行のDTOは `language: ja` のみ。スキル未登録状態はDTOに残すが、新しい画面には展開しない。

表示DTOは既存ドメインから一度生成して両経路へ供給し、UID照会と図鑑で違う正本を選ばない。PagesのUI辞書だけを静的生成する。全キャラ・全訳文カタログをPagesへバンドルしない。内部context、review履歴、管理専用文言は公開DTOへ含めない。

旧APIにはpresentationがないため、新Pagesは日本語の旧投影を使う。schemaVersion不明・contentRevision不一致・manifest不正は日本語へ戻し、管理側に不一致を報告する。一般利用者へ項目ID・スタックトレースを出さない。

### 8.2 準備段階の公開制御

構造移行のカタログmanifestには `translationMode: preparation` と `readyLanguages: [ja]` を固定する。DBのenabledLanguagesは既存形式のまま保持し、公開APIは希望言語とreadyLanguagesの積集合を有効言語として返す。日本語は常時有効。準備段階でen/zhを有効化しようとするpublishは tRPC PRECONDITION_FAILED と理由コードを返し、DBを更新しない。管理画面に構造準備中と不足件数を表示し、既存訳があるだけでは選択を許可しない。

本設計の実装中にtranslationModeをreadyへ変更しない。実装完了後も英語・中国語を自動で有効化しない。将来の翻訳リリースは、全公開対象のready検査、API/Pages両版一致、管理者の明示的な公開設定を別工程で満たす。admin文言の準備はpublic readinessとは別scopeで判定する。

既存キャラ紹介・通常スキルは現行では公開されていないため、notCollectedをpublic翻訳対象の分母へ黙って含めたり除外したりしない。manifestにactive public sectionsとplanned sectionsを明示する。今回plannedに置く紹介・通常スキルは全体情報充足レポートでは未完了、将来画面を公開対象に追加した時点でpublic readyを必ず止める。

### 8.3 キャッシュ・障害・失敗

UIDキャッシュは言語非依存の数値・既存日本語モデルを保持し、表示DTOは読み出し後にmanifestの版で投影する。翻訳レコードをUIDキーに複製しない。図鑑・履歴の静的キャッシュはcontentRevisionを含める。コンテンツ変更は再ビルド・再配備で反映し、ホットリロードやDB文章編集は導入しない。

構造不正はCI/ビルドで止める。起動時にも検査し、日本語必須参照が壊れた成果物はヘルスでreadyを返さず新配備を受け入れない。多言語準備未完了だけでは日本語APIを停止しない。訳文・UI辞書の障害は日本語へ退避する。利用者のUID取得・数値計算は翻訳処理に依存させない。

## 9. 移行・保全の仕様

1. 最新mainの同一commitで日本語API・全キャラ・共有PT/関連編成・履歴・数値の基準snapshotを保存する。作業コピーの未コミットコードを基準へ混ぜない。
2. 全表示項目を列挙し、安定IDと旧path対応表を作成する。基底・バッチ追加・汎用生成・共有PTをすべて対象とする。
3. 日本語は原文を保存、既存en/zhは文字列を保存する。既存三言語の重複は同一の意味・IDを確認して統合し、異なる訳は勝手に選ばずcollisionエラーにする。
4. 通常スキル・紹介・新しい理由欄はnotCollected。既存の数値なしtargetsや凸preparingを埋めない。
5. 新データから日本語の旧モデルを組み立て、全基準と比較してから依存箇所を切り替える。旧文章の二重編集を禁止する。
6. 移行CLIは `--dry-run` を既定、書込みは `--write` 明示。schemaVersion/migrationId/入力digest/出力digestを記録する。繰返しで同一結果。既存成果物が一致ならno-op、不一致なら上書きせず失敗。
7. 一時出力で全検証を完了後に正本を反映し、Git差分を確認する。途中失敗では現行ソースを残し、部分生成物を読まない。再開は同じ入力snapshotから実施する。

DBの文章移行は行わない。enabledLanguagesの既存保存値は読み取りフィルタと新publish条件で扱い、無断で削除しない。移行IDと成果物はGitで管理する。移行元のコードから記事や新しい訳文を生成してはいけない。

## 11. テスト・検証

### 11.1 構造・状態の検証

- 重複ID、未知TextRef、循環alias、ゲーム違い、未知field、未収集理由なし、登録済み空配列を拒否する。

- 旧訳移行でsourceHash=null/pendingを維持する。空訳・日本語コピー・同一文例外・変数・保護トークンを検査する。
- visitorのキー対応を削除、UIで日本語を直接表示、manifest版一致を無効化等の変異でテストが失敗することを確認して復元する。
- notCollectedのキャラが「全スキル登録済み」「翻訳100%」と表示されないことを確認する。

### 11.2 日本語と計算の回帰

全カタログの図鑑・UID側のguide/constellation/PT・関連編成・履歴・metadataを比較する。既存snapshotは新mainでimport可能か先に確認し、古いallow指定を流用しない。全旧フィールドの完全一致を検査する。presentationは別に一致を確認する。

静的キャラ全件のsnapshotに加え、3ゲームの保存済み匿名化fixtureを使った実際のlookup正規化経路を検査する。数値・目標・達成判定・装備操作・不明値・targets=[]・凸/PT補正・同名別形態・装備部位判定を維持する。日本語互換GuideDefinitionへ翻訳文字列を渡す変異で検査が赤になることを確認する。

確認コマンドは、既存 `pnpm check`、対象テスト、`pnpm test`、`pnpm build:api`、`pnpm exec vite build --config vite.pages.config.ts`、新contentコマンド、`git diff --check`。新コマンドは実装後に使用するもので、本書作成時点の実行結果ではない。

### 11.3 画面・API版の境界

ChromeでUID照会・図鑑・関連編成・更新履歴・公開言語設定を確認する。UI各variant、初回ロード・通信失敗・旧API・新API・不明schemaVersion・旧Pages・manifest不一致を対象とする。日本語表示内容と操作を基準比較する。新スキル画面や翻訳表示の追加を受入条件にしない。

API応答の実転送量とPages JSのgzip後バイト数を同じfixture/ビルド条件で比較する。管理context・翻訳レコード全量が公開応答/JSへ混入したら不合格。表示DTOの追加増加は項目内訳を記録し、必要な選択キャラだけを返す。数値だけ測って機能受入の代わりにしない。

## 12. 受け入れ条件

構造改修を受け入れる条件は以下をすべて満たすこと。

1. 旧日本語・旧三言語本文・計算値・推奨PT順位/共有/関連編成が同一。許可差分は追加DTOと非公開の構造・管理状態のみ。
2. 全表示項目が参照/テンプレート/明示literalに分類され、未知フィールド・未登録参照・説明なし除外が0。
3. 全キャラについて通常スキル等のregistered/notCollected/notApplicableが明示され、期待情報の不足を列挙できる。
4. 新規翻訳・既存訳修正・承認・新規情報調査・公開を実施していない。既存訳は全件pending/nullで保全される。
5. 日本語更新で当該項目だけstaleになり、共有文の影響先を漏れなく列挙できる。翻訳側ハッシュが自動追従しない。
6. structure check/型/テスト/ビルド/日本語画面が合格。en/zh readyの未完了は期待する失敗として記録される。
7. preparationで日本語のみ有効、en/zhのpublishが拒否される。旧API・版不一致・障害時も日本語が機能する。
8. 移行dry-run、再実行、途中失敗復旧、snapshot全件比較、変異検査、ロールバック手順を確認済み。
9. 正本・索引・実装ログ・親概要・Obsidian要約を実装の実状態に同期する。本書の着手前を実装済みと取り違えない。

**将来の翻訳公開条件**は別ゲート：対象public sectionsの情報欠落・missing/stale/pending/invalid・未解決正式名称が0、全訳レビュー済み、API/Pages版一致、言語別画面受入、管理者の明示公開設定。本構造改修の完了では満たしたことにしない。
