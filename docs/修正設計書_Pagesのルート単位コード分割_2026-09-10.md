# 修正設計書: Pages のルート単位コード分割（2026-09-10）

[リファクタリング計画書_2026-09-08.md](リファクタリング計画書_2026-09-08.md) §4.3 #6 の回収設計。

- 対象: `client/src/App.tsx`（ルート定義）
- 前提コミット: `a2de20a`
- 種別: 修正設計書（**画面の内容は不変。読み込みの仕方が変わる**）

## 1. 背景と問題

Pages ビルドで単一チャンクが 500kB を超え、vite が毎回警告を出す。

```
../dist/public/assets/index-DN-MTee_.js  529.98 kB │ gzip: 157.86 kB
(!) Some chunks are larger than 500 kB after minification.
```

全7ルートの画面が1本の JS に入っており、`/` を開くだけで管理画面（`/admin`・`/admin/feedback`）や
`/updates`・`/feedback` のコードまで転送される。

### 実測（minify 前・rollup の renderedLength）

| 区分 | サイズ |
| --- | ---: |
| `react-dom` | 548.2kB |
| `@trpc` / `@tanstack` / `tailwind-merge` / `@floating-ui` / `sonner` / `@radix-ui` ほか | 約 470kB |
| **画面7本（`pages/*.tsx` + `TranslationFeedbackForm`）** | **約 136kB** |
| 合計 | 1,281.2kB（minify 後 529.98kB） |

画面のうち `Home.tsx` が 61.2kB、`CharacterCatalog.tsx` 22.3kB、`FeedbackAdmin.tsx` 19.9kB、
`GuideHistory.tsx` 14.7kB、`AdminHome.tsx` 10.1kB。**管理画面2本（30kB）は一般利用者が一度も開かない。**

## 2. 決定

### D1. ルート単位の `React.lazy` に限定する

`manualChunks` によるベンダー分割は行わない。ベンダーは全ルートが共有するため分けても
初回転送量は減らず、チャンク数だけ増える。画面コードを剥がすだけで entry は約 136kB（minify 前）
＝ minify 後およそ 55kB 減り、警告の 500kB を下回る見込み。**実測して下回らなければ本設計を見直す**
（受入条件 1）。

### D2. `NotFound` だけ同期のまま残す

2.1kB と小さく、かつ `<Switch>` の catch-all である。ここを遅延にすると、存在しない
パスで一瞬フォールバックが出てから 404 が出る。効果が無く体感だけ悪くなるため同期に置く。

残る6ルート（`/`・`/characters`・`/updates`・`/feedback`・`/admin`・`/admin/feedback`）を
`React.lazy` にする。

### D3. フォールバックは画面の外枠だけを描く

`<Suspense>` の fallback にスピナーやテキストを置くと、`/` の初回表示で
「読み込み中」が一瞬出てからページに差し替わる（ちらつき）。各画面の外枠
（`min-h-screen`）と同じ高さの空要素だけを返し、レイアウトシフトと文言の点滅を避ける。

`/` は landing route なので、遅延化によって**初回表示が1往復ぶん遅くなる**。
これは受け入れる。全ルートのコードを常に配るより、gzip 後 40kB 前後を毎回節約するほうが
GitHub Pages + Railway の構成では有利で、`/` 以外の5ルートは初回転送から完全に外れる。

### D4. `ErrorBoundary` の位置は変えない

チャンクの取得に失敗した場合（デプロイ直後の古い index.html など）は
既存の `ErrorBoundary` が受ける。リトライ機構は足さない（YAGNI）。

## 3. 変更範囲

| ファイル | 変更 |
| --- | --- |
| `client/src/App.tsx` | 6ルートの静的 import を `lazy(() => import(...))` へ、`<Switch>` を `<Suspense>` で包む |

**変更しないもの**: 各画面の実装、ルーティングのパス、`vite.pages.config.ts`、
API、サーバー、テスト対象の振る舞い（テストは画面コンポーネントを直接 import しており App を経由しない）。

## 4. 受入条件

1. Pages ビルドで **500kB 超の警告が出ない**（entry チャンクが 500kB 未満）。
2. 画面が7本ぶんの独立チャンクに分かれ、`/admin` 系のチャンクが entry から外れている。
3. `pnpm check` / 全テスト / `build:api` が green。ゴールデン比較は全セクション一致（サーバー応答は不変）。
4. 本番 Pages（`https://sitar-sitar.github.io/hoyoverse-builder/`）で
   `/`・`/characters`・`/updates`・`/feedback` が表示され、直リンク（SPA 404 フォールバック経由）でも
   チャンクが 404 にならない。**Chrome で確認する**（`D:\my-app2` のブラウザ確認ルール）。

## 5. 残課題（本設計の対象外）

- 計画書 §4.3 #5（`build.guideHistory` 非圧縮 210KB）は応答形の変更のため別設計。
- ベンダーチャンクの分割・`chunkSizeWarningLimit` の調整は行わない（D1）。
