運用時の判断ミス、外部障害時の処理滞留、変更時の確認負担を減らす。既存の単一API・MySQL・GitHub Pages構成とPhase 59の日本語正本・互換DTO・不足検出基盤を活用する。

## 4. 設計方針

1. 新しい永続ストアやサービスを増やさず、APIプロセス内の有限枠、既存プール設定、既存CLIで実現する。
2. キャッシュと同一UID共有を先に評価し、新規の取得作業だけを制限する。既存の回数制限は別途従来どおり適用する。
3. 設定不備は起動失敗、外部障害は既存の失敗応答、監視の不一致は非合格として観測する。黙って安全性を下げない。
4. 不足情報・翻訳状態・未解決の同一性を混同せず、一覧化によって原文や公開条件を変えない。
5. 公開版は成功したPages成果物とAPIの一致から確定する。main HEADや監視コードのSHAを公開版へ自動採用しない。
6. Fの抽出は挙動保存が目的で、純粋計算の移動に限る。照会状態hook、汎用provider基盤、全面型統合は採用しない。

## 5. 詳細仕様

### 5.1 A：現行運用情報の入口

- READMEは構成、開発コマンド、現行手順へのリンク、現在有効な公開入口を中心にする。長い検証履歴は対応する実装ログ・実装後メモへのリンクに置き換える。既存履歴本文の移動が必要なら移動先の保存を確認してからREADME側を短縮する。
- `northflank-production.md`を「現行運用」「通常更新」「migrationを伴う更新」「切戻し」「過去記録」の順に整理する。設定表に確認日と根拠を付ける。実環境を未確認なら「文書上の最終受入」「現在値未確認」を明記する。
- 通常更新はPR検証→API自動配備→health対象SHA一致→Pages配備→公開受入。DB変更時はAPI/手動Jobの同image・SHA確認を加える。Jobは自動実行しない。
- 既存の移行完了に付随する明示例外や未検証事項は消さず、移行完了判定・実装ログへ誘導する。
- E導入後の切戻し手順には、forward以外のPagesモードで復旧しdescriptorを生成しない間は`release_descriptor_missing`、取得できたdescriptorが非対応モードを明示する場合は`mode_unsupported`で監視が失敗し続けること、通常更新ではAPI先行窓で`api_ahead`が記録され得ることを書く（§5.7・§5.8）。
- Aの編集だけでもmain更新がAPI配備を誘発し得るため、公開を行う場合は従来の同SHAゲートを通す。docs変更を理由に自動配備を迂回しない。

### 5.2 B-1：新規UID照会作業の8枠

新設`server/_core/lookupCapacity.ts`で、プロセス内共通の非待機型ゲートを提供する。依存方向はbuildAdvisor/gameProviders→lookupCapacityとし、ゲートからproviderをimportしない。

`lookupUidBuild`と`lookupWithCache`の順序を次に固定する。

1. 既存キャッシュに有効な値があれば従来応答を返す。
2. 同じゲーム・UIDのin-flightがあればそのPromiseを返す。
3. 新規作業のPromiseを生成・in-flightへ登録し、その実行開始時に共通ゲートを同期的に取得する。現行は`loader()`をPromise生成式内で同期的に呼び直後に`inFlight.set`するため、in-flightの`get`→ゲート取得→`set`の間に`await`を挟まないことをテストで固定する。
4. 空きがなければ`TRPCError(SERVICE_UNAVAILABLE)`と既存`public.busy`文言で拒否する。待機・上流fetch・fallback・キャッシュ書込は行わない。拒否Promiseもfinallyでin-flightから消す。
5. 空きがあれば取得→必要な静的データ取得→正規化→既存キャッシュ処理まで1枠を保持する。HSRはMiHoMoからEnkaへのfallbackを同じ枠内で行う。
6. 成功・同期throw・rejectのすべてでfinallyによる解放を1回だけ行う。負値・二重解放を許さない。

`lookupWithFallback`の内側で枠不足を投げるとEnkaへ誤fallbackするため、取得枠はfallback呼出し全体の外側に置く。tRPC応答はランタイムに任せ、Expressで独自503 JSONを生成しない。2件以上の混合batchで他のprocedureが巻き添えにならないことを検証する。

既存キャッシュヒット・共有は枠を消費しないが、routerのIP/UID回数制限は従来どおり先に評価される。これを回避するためのカウント返却は行わない（返却は回数制限の迂回経路になる）。そのため容量拒否を受けた利用者の再試行は、上流取得が行われていなくてもUID制限を消費する（§10）。容量拒否は`SERVICE_UNAVAILABLE`、上流429は既存の`TOO_MANY_REQUESTS`とcodeで区別するが、文言は既存`public.busy`を共用する。新規文言は翻訳基盤の対象となり本書の範囲を広げるため追加しない。正常時の`cached/fetchedAt/cacheExpiresAt`、不完全なHSR応答を保存しない条件、既存static loaderのsingle-flight/LKG/negative cacheは維持する。

8は同時UID作業数でありHTTP通信本数ではない。static loaderの既存固定fan-outは許容する。すべての低水準fetchに同じ8枠を再帰適用する方式はデッドロックを招くため採用しない。外部への新規リトライは追加しない。

### 5.3 B-2：OAuth通信期限

`exchangeCodeForToken`と`fetchGitHubUser`はそれぞれfetch開始からJSON本文読取完了まで5,000msのAbortController期限を持ち、finallyでtimerを解除する。signalは実際のfetchへ渡す。token交換の再送は行わない。

- `idle → requesting → success / aborted / failed`。失敗後の処理へ進まず、現行callbackの502固定メッセージを返す。
- OAuth state Cookieの消費・削除時点、管理者ID検証、DBユーザー確認、session/exchange code発行の順序を維持する。期限切れ時にsession Cookieやexchange codeを新規発行しない。
- DB処理時間を含めたcallback全体10秒以内とは保証しない。2回の外部通信が直列であることを測定結果に記録する。
- 変更対象catchのログは固定理由コード`oauth_timeout`または`oauth_upstream_failed`だけを出す。code/state/token、URL/query、上流本文、例外オブジェクトを出さない。既存の他認証経路のログ整理は別スコープ。

### 5.4 B-3：DBプール待機の廃止

`getDb`の生成箇所で接続オプションへ`connectionLimit:10`、`waitForConnections:false`、`queueLimit:0`、`connectTimeout:10000`を明示する。ここでqueueLimit=0を安全性の根拠にせず、waitForConnections=falseによる非待機を根拠にする。設定検証は§5.5で行う。

- 接続10本を使用中の追加要求はドライバの取得失敗として即時rejectする。独自の待機列・自動再送・接続上限超えのpool再生成は行わない。
- poolの生成完了を接続成功とは扱わない。接続確立の期限とSQL実行時間を区別する。
- analyticsのbest effort記録は従来どおり照会の応答を待たせず、rejectを回収する。公開設定の既存fallback、保存処理の失敗通知、管理者ログインのDB確認を維持し、保存失敗を成功へ変換しない。
- 公開表示設定（`readPublicDisplaySettings`）は成功時だけ60秒キャッシュし、取得失敗時は全キーlegacyを返す。非待機化後は、キャッシュ切れの瞬間に接続10本が埋まっているとその要求は管理者選択のvariantではなくlegacy表示を受け取る。これを本書では許容し（§6の例外）、失敗時LKGの追加は行わない。発生率は§8.2の隔離測定で記録する。
- URL・SQL・パラメータ・利用者識別子を含む例外を追加ログへ出さない。新規資源ログは固定理由と件数のみ。
- 10本の長時間SQLが残ればDBを使う処理は拒否され得る。Promise.raceで終了したように見せたり、実行中SQLを使い回したりしない。SQLキャンセル・実行期限の追加は別設計とする。

### 5.5 C：本番DB設定の起動前検証

`databaseConnection.ts`に副作用を分離した検証関数を追加し、APIの`startServer`でlisten前、Jobの`drizzle.config.ts`で設定生成前に実行する。`getDb`のcatchだけに置かず、設定不備をnullへ変えて起動継続しない。DBなしのオフラインCLI・buildでは検証を実行しない。

設定不備は固定コードの例外に変換してから最上位へ渡し、既存の`process.exitCode=1`を維持する。検証失敗時にHTTPポートを開かず、poolや再試行timerを生成しない。読取エラーのpathや生のURL解析例外を最上位のconsoleへ渡さない。

| 条件 | 必須動作 |
| --- | --- |
| `NODE_ENV=production`のAPI起動 | DATABASE_URLとDATABASE_SSL_CA_FILEの両方が必要 |
| 本番JobのDrizzle実行 | 上記と同じ検証を必要とする。imageは`Dockerfile.northflank`で`NODE_ENV=production`を固定済み。Northflank側のJob環境変数で上書きされていないことを運用ゲートで確認 |
| 全環境でDATABASE_URLが設定されている場合の、URL不正、mysql以外のscheme、host/database欠落 | 固定エラーコードで起動拒否。developmentでも`getDb`のcatchでnullへ落とさない |
| 本番URLにqueryオプションあり | 起動拒否。TLS/待機設定をURLから上書きさせない。既存query利用があれば公開前に等価な明示設定へ移す |
| productionでCA未設定、または全環境で指定したCAが空・読取不可・PEM証明書として解析不可 | APIはHTTP受付前、Jobは設定生成前に拒否。development/testのCA未指定はこの拒否条件に含めない |
| 全環境でCAを指定し正常に解析できた場合 | 現行の`ssl.ca`と`rejectUnauthorized:true`を必ず設定 |
| development/testでDB URL未設定 | 既存のDBなしローカル検証を許可。接続を作らない |
| development/testでCAを指定 | 指定ファイルが不正なら失敗。検証無効化へfallbackしない |

CAは複数PEM証明書を含むbundleを許容し、各証明書をNodeのX509Certificateで解析する。独自の期限・発行先検証器は追加せず、信頼・ホスト名等の接続時検証はTLSへ委譲する。構文検証だけをTLS接続成功の証拠にしない。

`drizzle.config.ts`は`drizzle-kit generate`（`db:push`の前段）でも評価される。NODE_ENV未設定のローカルgenerateではCA必須検証を行わず、DATABASE_URLがあればURL形式だけを検証する。

query禁止には現行の非対称を解消する目的もある。現行`drizzle.config.ts`はCAありのときURLをhost/user等へ分解してqueryを捨てる一方、APIは`uri`をmysql2へそのまま渡すためqueryが効く。本番URLのquery禁止による既存設定との互換性は公開前ゲート。秘密値を表示せず「queryなし/あり」と必要な設定名だけを確認する。API/JobのCA mountが独立している点を維持する。ログは固定コードのみで、URL、認証情報、CA本文は記録しない。`rejectUnauthorized:false`を許す設定は追加しない。

### 5.6 D：情報不足の作業一覧

新設`pnpm content:backlog --format json|md [--baseline <JSONファイル>]`は読み取り専用。実体は`scripts/content/improvementBacklog.ts`と純粋な集約関数に置き、既存repository/coverage（`server/content/coverage.ts`）と`externalNameReport`（`content/externalNames.ts`の関数）の判定を再利用する。ネットワーク・DB・原文生成・承認・保存APIを呼ばない。結果は標準出力へ出し、baseline保存は利用者の明示的なファイル出力で行う。

JSON schemaVersion=1で、`sourceRevision`（Gitの40桁SHAまたはnull）、`contentRevision`、`summary`、`items`、`delta`を出す。Git状態がdirtyなら`sourceDirty:true`を併記する。Git不明時もcontentRevisionで対象を識別し、推測SHAを埋めない。

| 項目 | 契約 |
| --- | --- |
| 一覧対象 | `information.notCollected`全件と`externalNames`のunresolved境界全件。単位別に集計し総和を「キャラ数」と呼ばない |
| 一意キー | `information:<section.id>` / `external:<boundary.id>`。本文や表示名をキーにしない |
| 行 | key/category/subjectId/game/identityKey/visibility/priority/reason/requiredKinds/ownerModule。非該当の値はnullまたは空配列に統一 |

baseline未指定ならdelta=null。指定時はschemaVersion=1、重複keyなし、同じ行schemaのJSONだけを受け付け、全itemsをkeyで比較し`added/removed/changed`を各配列で出す。changedは行の意味フィールドの差だけとし、SHAや出力順の変更だけで全件changedにしない。added/changedには新行、removedには旧行を保持する。旧contentRevisionが異なっても比較可能とする。別schema・壊れたJSON・重複keyは終了1で拒否し、自動変換・上書きをしない。

### 5.7 E-1：公開版の記述ファイル

Pages artifactのルートへ`release.json`を生成し、公開成功によって期待版を確定する。現行forwardの公開パスは`/hoyoverse-builder/release.json`。アプリ内のcontent manifestやAPI schemaVersionとは別の運用形式とする。

生成は依存導入済みのbuild jobで新設`scripts/content/releaseManifest.ts`を実行する。配置先は既存の`dist/pages-artifact/release.json`に固定し、任意パス書込引数を持たせない。`scripts/pages.mjs --verify`によるAPI一致・artifact組立ての後、upload前に生成・検証する。ローカルで対象SHAが不明ならrelease生成を成功扱いにしない。

JSONの必須項目は`schemaVersion:1`、`revision`（対象mainの40桁SHA）、`contentRevision`（64桁hash）、`mode:"forward"`、`catalogDigest`、`probes`（3ゲーム各1件のgame/name/referenceDigest）。生成時刻、secret、UID、本文・原文全集、翻訳レビュー情報は含めない。

- カタログ期待値は`withCatalogPresentation(characterReferenceCatalog())`、詳細期待値は`withPresentation(characterReferenceFor(game,name))`のJSONシリアライズ後の値から生成する。game/nameは各ゲームの現行カタログ先頭の実在エントリを採用し、生成時にnull・重複・空文字を拒否する。
- digestはJSONのobject keyを再帰的にコードポイント順へ揃え、配列順は保持したUTF-8 JSONのSHA-256。新設`scripts/release-contract.mjs`を生成と監視で共用し、処理の二重実装を避ける。
- 内容検証は実際のtRPC応答の`result.data.json`を取り出して同じdigestへ変換する。`error`、欠落envelope、HTMLや空データを成功としない。
- probeのgame/nameは毎公開で再生成するため、キャラ追加等で先頭エントリが変わってもprobe名の変化自体は異常としない。
- descriptorのAPI URLは持たせない。監視のAPI/Pages Originは固定許可先とし、公開JSON経由の任意URL取得を防ぐ。
- digestの一致はpresentationがDB状態（公開言語設定等）に依存しないことを前提とする。現行は`language:"ja"`固定（`server/content/presentation.ts`）。presentationがDB状態に依存する変更を行う場合は、本書のdigest契約を先に改訂する。
- `scripts/release-contract.mjs`と`scripts/monitor-production.mjs`はNode標準機能だけで動作し、外部依存をimportしない。公開後検査を行うdeploy jobは`pnpm install`を行わないため。build jobの`releaseManifest.ts`（tsx経由・依存導入済み）とは実行環境が異なる。
- descriptorはforwardモードのartifactにだけ生成する。他モードでは生成せず、artifactに以前の`release.json`を残さない。監視から現在の配備モードを欠落だけで推測することはできないため、descriptor欠落は常に`release_descriptor_missing`（終了1）とする。有効なJSONが非対応mode（legacy/parallel/rollback）を明示する場合だけ`mode_unsupported`（終了1）とする。rollback等で復旧している間は定期監視の失敗が続くことを運用ガイドの切戻し手順（A）へ明記し、失敗を理由に監視を止めない。モード移行・旧ホストを正常扱いする拡張は別設計。

`HOYOVERSE_MONITOR_REVISION`と過去の固定RELEASEによる期待版上書きを廃止する。古いvariableが残っていても公開descriptorを優先し、値をログへ出さない。手動の切戻しも戻したPages artifactのdescriptorと対応APIで検証する。descriptor欠落時は過去版へfallbackせず`release_descriptor_missing`で失敗する。

### 5.8 E-2：公開機能監視と配備競合

現行scheduleと手動起動を保持し、各runで次を直列に行う。外部UID照会・認証・feedback送信・DB保存を監視へ追加しない。

1. Pagesのrelease descriptorを読む。
2. API healthを読み、revision/CORS/maintenance=false/migrationPreview=falseを検査する。
3. 開始時点でAPIとdescriptorのrevisionが一致するときだけ、図鑑一覧と3件の代表詳細を読み、CORS・JSON形式を検査してdigestを計算する。開始時にrevisionが異なる場合、この4取得を省略する。
4. API healthとPages descriptorを再読し、検査中に対象版が変わらなかったことを確認する。開始・終了で同じrevisionが一致している場合だけ期待digestと比較する。

正常な完全検査は8リクエスト、開始時の版不一致では4リクエスト、取得自体の失敗はその時点で打ち切る。各fetchは本文読取を含め10秒でabort、監視全体は90秒で打ち切る。credentials omit、redirect error、cache no-storeとし、各body上限を1MiBにする。上限超過はstreamをcancelし、途中までのJSONを成功扱いにしない。1MiBは2026-10-19実測（カタログ35,476 byte、全256名詳細の最大37,946 byte）に対して十分な余裕を持つ。

GitHub PagesはCDN経由で`Cache-Control: max-age=600`を返し、`cache: "no-store"`はCDNエッジのキャッシュを迂回する保証にならない。descriptorの取得URLには取得ごとに異なるcache-bustingクエリを付ける。識別子は1検査呼出しごとのNode標準`crypto.randomUUID()`と、その検査内の取得通番を組み合わせる。開始・終了の2読取、公開後の各再試行、ローカル手動実行でも同じ値を再利用しない。固定Origin・固定パスの許可先判定はクエリを除いたパスで行い、クエリへ秘密値・UIDを入れない。CDN側がクエリを区別するかはG-05で実測し、fixture成功だけで伝播を保証しない。

結果理由は次の優先順で1つに決める。

| 理由 | 条件 | 扱い |
| --- | --- | --- |
| `release_descriptor_missing` | descriptorのHTTP 404。モードや配備履歴は推測しない | 終了1。以降の比較は行わない |
| `mode_unsupported` | 有効なJSONがlegacy/parallel/rollbackのmodeを明示 | 終了1。以降の比較は行わない |
| `descriptor_invalid` / `request_failed` / `health_invalid` | descriptorの形式不正、その他HTTP/通信/本文の失敗、healthの不正flags・CORS等 | 終了1。取得不能・不正応答を版変化や公開途中へ読み替えない |
| `release_transition` | 開始・終了でAPI revisionまたはdescriptorが変わった | 終了1。次の定期runで自然回復を確認 |
| `api_ahead` | 開始・終了で不変のまま、API health revision ≠ descriptor revision | 終了1。通常リリースのAPI先行・Pages未公開窓として記録し、次の定期runで自然回復を確認。この場合digest比較は行わない |
| `payload_mismatch` | revisionは一致するがdigestが違う | 終了1 |

通常更新ではAPIがPages buildより先に新SHAへ切り替わるため、各リリースで`api_ahead`が1回以上記録され得る。これは仕様どおりの非合格であり、PASSへ読み替えない。`api_ahead`が次の定期runでも続く場合は、Pages配備の失敗・停止を疑い運用ガイドの手順で確認する。スケジュールの5分間隔は実行保証・連続監視保証ではない。

`api_ahead`はここでは安定した版不一致を表す分類名であり、SHA文字列だけからAPIが新しいことを証明するものではない。切戻し時を含め実際の配備履歴と照合する。途中で版が変わった場合はdigest差より`release_transition`を優先し、配備中のデータ差を`payload_mismatch`と誤分類しない。

結果artifactはschemaVersion=2にし、固定check名、結果理由、観測時刻、期待/観測revision、contentRevision、status、latencyMsだけを保存する。本文・キャラ名・URL query・例外文字列は記録しない。現在のartifact名・7日保存・終了0/1を維持し、外部通知サービスや自動修正を追加しない。独立テストが従来形式を固定している場合は同時更新する。

Pages deploy成功後に、同一の監視関数を「workflow対象SHAとdescriptorが一致すること」を加えて実行する。descriptor・API・内容digestが互いに一致していても対象SHAでない場合は、公開後検査専用の理由`expected_revision_mismatch`（終了1）とする（2026-10-19 実装時に追加。定期監視では使わない）。伝播待ちの再試行は全体120秒以内・10秒間隔とし、その間の1回の完全検査は残時間以内にabortする。再試行は読み取りのみ。失敗時はjobを失敗にするが、自動revert・DB復元・期待版更新は行わない。既存の公開直前API再確認は削除しない。

初回E公開時は、deploy成功から公開後検査がdescriptorの新SHAを観測するまでの伝播時間を実測し、実装ログへ記録する。cache-busting後も120秒を超える場合は窓の値を測定根拠付きで改訂する。

初回E公開前に旧監視workflowから新監視への切替順序を確認する。公開前に新monitorだけがmainへ入るとdescriptor欠落となるため、descriptor生成・新monitor・workflow変更を同じ公開単位に含める。公開途中の失敗は記録し、初回公開後の手動runと次の定期runの成功までEを閉じない。

### 5.9 F：変更箇所の局所化

### 8.2 測定と数値採否

- 基準HEADと候補HEADを同じ隔離環境で比較する。固定した合成プロフィール・遅延100ms/6秒/14秒・cold/warm static catalogの組合せを用い、同時新規UID 1/4/8/9の成功数、拒否数、最大active、完了後active=0、応答p50/p95を記録する。実UIDやIPは測定結果に残さない。
- 8以下で新しい容量拒否がなく、9件目だけが即時拒否されること。取得枠導入によるwarm fixtureのp95増分が50ms以下、30反復後にactive/in-flightが残らないことを採用条件とする。外部応答の速さそのものを保証する値ではない。
- DBは1/5/10/11並列の隔離試験で拒否・回復を確認する。本番最大接続数からAPI10本とJob/管理接続の予算を確保できない場合はB/Cの公開を止め、実測に基づく小さい値を本書へ反映する。未確認のまま10本を安全と断定しない。
- プール待機廃止により通常利用でも保存失敗が増える場合は公開しない。実利用観測から判断できない場合、隔離で代表照会と設定保存を同時に実施して保存の成功を確認し、公開後の観測を残ゲートとする。
- 同じ隔離試験で公開表示設定の取得も同時に行い、キャッシュ切れ時にlegacy fallbackへ落ちた件数を記録する（§5.4・§6の許容事項の発生率）。

## 10. リスク・ロールバック

| リスク | 予防・検出 | 回復 |
