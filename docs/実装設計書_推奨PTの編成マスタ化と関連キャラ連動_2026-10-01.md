## 1. 目的・背景

### 1.1 起きていること

新キャラを実装すると、そのキャラ本人の推奨PTは登録されるが、新キャラが入る編成に参加している既存キャラの推奨PTは更新されないことが多い。

- **第23バッチ（原神 ヴェスナ・ヴォジャニーツァ）**: 追加直後（`e3d75d2`）に `party-impact.mjs` を実行すると、既存キャラ側で新キャラに言及している案は0件（新キャラ同士の1件だけ）。原神は同じ役割の候補も出ない。ファルザン・ディオナ・スカーク・フリーナ・エスコフィエへの追補は、利用者の追加指示で別コミット（`05cccb0`）として行った。
- **第21バッチ（HSR パール）**: 同じ役割の置換候補5行を全行据え置きにした。翌日、利用者の指摘で緋英の1案目だけを追補した（`e6c6b0f`）。

### 1.2 構造上の原因

1. **同じ編成がキャラごとに別データになっている**。推奨PTは「キャラ → 最大3案」の配列で、編成を足しても他のメンバーには届かない。
2. **既存キャラ側への反映がバッチ専用のコードになっている**。第23バッチは `BATCH23_EXISTING_PARTY_UPDATES` と専用ループ、セット期日の上書き、更新履歴の特別扱いの4か所で実装した。次のバッチでは使い回せないうえ、次の2つの欠陥がある。
   - 推奨PTが自動生成のキャラに使うと、ループ内の `previous` が `undefined` になり、モジュール読み込み時に落ちる。
   - `partyRecommendationsFor` は原神の第17バッチ28名を `batch17PartyFor` で先に返す。そのため、この28名に書き込んでも反映されず、エラーも出ない。
3. **影響レビューの探す方向が逆**。`partyImpact.ts` は「既存の案が新キャラに言及しているか」から探す。新キャラ追加時点では既存側にまだ名前が無いので、原理的にほぼ拾えない。
4. **確認結果を記録・強制する仕組みが無い**。影響レビューの出力はチェックリストで、全行据え置きでもCIは通る。

### 1.3 目的

- 編成を1件ずつ持つ**編成マスタ**を導入し、各キャラは**編成IDの参照リスト**で推奨PTを表示する。
- 編成を登録した時点で、参加しているカタログ上のキャラ全員について参照するか見送るかを決めないとテストが失敗する**連動ゲート**を設ける。
- 公開APIの形と画面は変えない。Phase 1 は出力を1バイトも変えない。

## 3. 全体方針（決定事項）

### D1. 編成を正本にし、キャラは参照を持つ

編成（`Team`）を1件ずつ持つマスタを正本にする。各キャラは順序付きの参照（`PartyRef[]`）を持ち、先頭から最大3件を表示する（`MAX_PARTY_OPTIONS = 3` は据え置き）。

### D2. 参照を書かないキャラは「自分起点の編成」を既定で参照する

参照リストを明示していないキャラは、自分が起点（`origin`）の編成を `originOrder`（保存順）の昇順で並べ、先頭3件を参照する。このため、既存256名のうち第23バッチの既存5名を除く251名は、参照リストを1行も書かずに済む。

保存できる編成数と表示3枠は分ける（レビュー PT-01）。同じ起点の編成はマスタにいくつでも保存でき、`originOrder` は表示順位ではなく保存順の正の整数とする。起点の保存編成が4件以上になったキャラは、表示する3件を明示参照（`refs`）で選ぶ（テスト A6 で必須化）。非表示の旧編成は削除せず残し、ID で引ける。

### D3. 旧データは書き換えず、読み込み時に変換する

第1〜22バッチのデータ（`MANUALLY_CURATED_HIGH_USAGE_CATALOG` / `PARTY_CATALOG` / `batch17Parties.ts`）は記述を変えない。起動時に1案＝1編成として**旧形式編成**（`shared: false`）へ変換する。

旧形式編成は起点キャラの視点で書かれている。役割の約59%が並び順で付けた汎用ラベルで、注記の81%に起点キャラ名が入っている。そのため、起点キャラ以外からは参照できない。

### D4. 他キャラから参照できるのは共有編成だけ

視点に依存しない書き方をした編成を**共有編成**（`shared: true`）と呼び、起点以外のメンバーから参照できるのはこれだけにする。視点に依存しない書き方とは、実際の役割を三言語で持ち、注記にメンバー名を書かないことを指す。第24バッチ以降に登録する編成はすべて共有編成にする。第23バッチの4編成は移行時に共有編成にする（既に視点非依存で書かれている）。

### D5. 3枠に何を入れるかは自動で決めない

参照リストで人が決める。理由は次の2つ。

- 出典ポリシーでは、各キャラの個別ガイドが主な根拠だから（[party-recommendation-source-policy.md](party-recommendation-source-policy.md)）。
- 押し出される旧案の判断を記録に残すため。

外した旧案はマスタに残る（参照されないだけ）。

参照の入れ替えは**変更記録**（`PARTY_LINK_RECORDS`。追記専用）に1件ずつ残し、更新履歴はこの記録から作る（レビュー PT-02）。現在の参照リストは「いま何を表示するか」だけを表し、過去の履歴の入力にはしない。後のバッチで参照を差し替えても、過去のイベントの日時・件数・文言は変わらない。初回登録時の採用参照は `INITIAL_PARTY_REFS` に固定し、それ以後の追加・除外は自分起点を含めて記録する。所属バッチと編成バッチの比較による免除は行わない（PT-05・PT-06）。

### D6. 連動ゲートで新キャラだけの更新を止める

すべての共有編成について、参加メンバーのうちカタログに載っているキャラ（起点を除く）は、次のどちらかを満たさなければならない。満たさないとテストが失敗する。共有編成の `batch` は**共有編成として登録・共有化を実施したバッチ**で、23以上でなければならない（テスト D10）。旧形式から共有化した編成も実施バッチを入れ、元の精査バッチは `sourceBatch` に分けて持つ（レビュー PT-04）。このため、共有化した編成がバッチ番号の指定でゲートを素通りすることはない。

- **同じメンバー構成の編成を参照している**（その編成自体でも、同じ顔ぶれの別編成でもよい）。
- **見送り記録（理由・確認した出典URL・確認日）がある**。

実装待ちのメンバー（例：オデット）は対象外。そのメンバーがカタログに加わった時点で、自動的にゲートの対象になる。

### D7. 公開応答の形と既存IDを保つ

案のIDは画面の選択状態（`Home.tsx` / `CharacterCatalog.tsx` の `useState`）にしか使われておらず、保存されていない。それでも Phase 1 の受入条件を「完全一致」にするため、第23バッチの既存6行は参照に `viewId` を持たせて現行IDを維持する（互換専用。新規には使わない）。

### D8. 実行時は fail-safe、整合性はテストで保証する

存在しない編成への参照、本人が入っていない参照、旧形式編成を起点以外から参照するものは、実行時には黙って読み飛ばす。参照がすべて読み飛ばされたら現行と同じ汎用案を返す。起動時には例外を投げない。不整合はテスト（§4.8）で止める。

### D9. 保存先はリポジトリ内の TypeScript のまま

PRレビュー・CI・ゴールデン比較が効くことを優先する（§7 R9）。

#### 4.7.1 定義

**初期参照の固定記録（第3版、PT-05・PT-06）**: `server/parties/initialRefs.ts` に `INITIAL_PARTY_REFS: Readonly<Record<string, readonly string[]>>` を置く。キーは `game:カタログ名`、値は初回登録時に採用した編成IDの配列（重複なし、0〜3件）。空配列は専用編成を持たず汎用案へフォールバックする初回登録を表す。既存256名は第23バッチ追補前の自分起点の先頭3件を一度だけ書き出して固定する。第23バッチの既存5名の参照変更は既存の `PARTY_LINK_RECORDS` の5行で再生する。現在のマスタから実行時に再生成しない。

新キャラ追加時は、初回に採用した自分起点・他起点の参照全体を末尾へ1行追記する。初回に見送った編成は含めない。初回採用では追補の変更記録を作らず、後日採用・除外・再採用はその実施バッチへ追加・除外を記録する。既存の初期参照行は変更・削除しない。移行時256名の記録は回帰テストのSHA-256で固定し、後続追加を許容する。

検査は初期参照の集合から始め、変更記録をバッチ昇順で再生する。各行は `removed` を除いてから `added` を加える。未参照IDの除外・参照済みIDの追加を E7 とし、最終集合を明示参照または既定参照の全表示IDと比較する（E2）。自分起点も比較対象。参照順だけの変更は集合を変えないため、本記録の対象外。初期参照のIDは後日除外が記録されていればマスタから消えていてもよい（Phase 4での旧形式削除）。新しい初期参照への書き込みは、初回登録の根拠・本人の参加・参照規則をレビューで確認する。

採用理由: 固定した初期参照と追記専用の差分だけで継続更新を説明できる。バッチ番号による免除は後日採用を初回採用と区別できず不採用。自分起点専用の別履歴モデルは再生・更新日の二重管理になるため不採用。安全側の扱いは初期参照欠落・再生不一致をテストで失敗させ、公開応答の実行時フォールバックはD8を維持する。

#### 4.11.2 サーバーとAPI契約

`server/parties/appearances.ts` を新設し、次の公開型と関数を置く。テスト用の入力注入を追加してよいが、通常呼出は2引数で成立させる。

```ts
export type PartyAppearance = Omit<PartyRecommendation, "rank"> & { teamId: string; origin: string };
export function partyAppearancesFor(game: PartyGameId, name: string): PartyAppearance[];
```

1. `game` 内の正規カタログ名だけを受け付ける。カタログ外・別ゲームの同名には空配列。`characterReferenceFor` の既存NOT_FOUND契約は変更しない。
2. `resolvePartySet(game, name, store, parties).options` の最終表示を `rosterKey` へ変換する。refsだけの比較にはしない。有効参照なしの汎用案フォールバックも、実際に表示される構成として除外に使う。
3. `store.teams` から `shared === true`、同ゲーム、`members[].name.ja === name` の本人参加を満たすものだけを選ぶ。参加判定には日本語正規カタログ名を使い、曖昧な別実装名や他言語名で補完しない。構成比較は既存の `rosterKey` を使用し、略記やメンバー順の差を吸収する。
4. 表示中の案と同じ `rosterKey` を持つ候補を除く。見送り記録は除外条件にしない。見送りは本人の3枠に採用しない判断であり、参考欄へ出すことは採用への変更ではない。
5. `updatedAt` 降順 → `dataAsOf` 降順 → `team.id` 昇順でソートする。日付は既存のYYYY-MM-DD文字列。IDはJavaScriptの文字列比較（`<` / `>`）を用い、実行環境のlocaleに依存させない。候補同士も `rosterKey` で重複排除し、先頭の最新1案だけを残してから最大6件へ切る。入力配列をsortで変更しない。
6. `viewOf` の共通表示フィールドを利用する場合も、新しい配列・オブジェクトへ投影する。`rank` を公開しない。`teamId=team.id`、`origin=team.origin`、`id=team.id + "@" + name`。起点本人でも本人を必ず先頭へ移し、残りは保存順。`targetChanges` は常に新しい空配列。既存 `viewOf` 自体の起点順序・ID・rank仕様は変更しない。
7. タイトル・役割・相性・バージョン・基準日・更新日・出典は保存済み内容を維持。`targetSummary` は型互換のため保持するが、参考欄のUIでは表示・目標計算へ使用しない。複数回呼出でも既存マスタ・refs・推薦応答は不変。ネットワーク・DB・永続化・キャッシュ書き込みは行わない。
8. `viewOf` が本人を解決できないなどの無効候補は読み飛ばす。既存の重複ID・壊れた参照・日付／出典不備は連動ゲートのテストで公開を止める。全体をcatchして成功の空配列へ偽装しない。予期しない例外は既存tRPCエラーとして処理する。

`server/characterReference.ts` の `CharacterReference` と `characterReferenceFor` の戻り値に、`partyRecommendations` の直後へ `partyAppearances: PartyAppearance[]` を追加する。新APIでは全カタログキャラに必須の配列とし、0件も `[]` を返す。`build.referenceCatalog`、`build.lookup`、ガイド・凸・既存推薦・履歴の構造は変えない。routerの入力・認証・レート制限・POST照会・CORSは現行を維持する。

#### 6.3.2 移行後の公開・受入・切戻し

1. 公開するmainの40桁SHAを確定。アプリコード公開には `[skip ci]` を使わない。main pushで先行したPages workflowがAPI revision不一致で失敗した場合、既存公開を維持し、API準備後に同SHAのrunを再実行する。ゲートを緩めない。
2. Northflankの `hoyoverse-api` で対象mainをビルドし、`APP_REVISION` build argumentを対象SHAへ合わせ、成功imageを配備する。1 instance／Recreate／資源／接続先／通常受付フラグは変更不要。Recreateの再起動中の短時間エラーは既存の取得エラーとして扱い、成功の空配列に変換しない。
3. 本機能にDB/schema/書き込み変更はないため、migration Job・`db:push`・backup Restoreを実行しない。現行Jobの旧imageを不用意にRunしない。将来migrationを行う場合のAPI同digest固定条件は維持する。
4. health HTTP 200、対象SHA、maintenance=false、migrationPreview=false、内部probesを確認。Pages OriginへのCORS、`build.reference` 全256名の新フィールドと9名の固定値、既存PT・ガイド・凸・履歴の不変を検証済みsnapshotと照合する。全件照会は既存operation制限を守って分割・間隔調整し、検証専用の上限緩和を行わない。429なら成功扱いにせず待機・再照会する。healthだけで機能反映成功としない。
5. 同mainの `deploy-pages.yml` を実行／再実行。`HOYOVERSE_PAGES_MODE=forward` と既存Northflank接続先を維持。`node scripts/pages.mjs --verify` の同SHAゲートpass、workflow／deployment成功、公開JS/CSSの取得を確認する。
6. 正式 `/hoyoverse-builder/app/characters` のChromeで代表キャラの0／1／3件、三言語、出典、推薦3枠不変を確認。旧 `/hoyoverse-builder/characters` は既知ルートとして新入口へ転送されることを確認。既存表示設定を永久変更しない。公開時に確認できない別variantはローカルの証跡と区別し、公開確認済みと記載しない。
7. GitHub外部監視は移行完了時にdisabled_manually、翌朝automationはPAUSED。Phase 56で自動再有効化せず、PCの連続稼働も要求しない。監視を再開する別指示がある場合だけ `HOYOVERSE_MONITOR_REVISION` を実際の公開SHAへ更新して手動確認する。旧24時間観測の追加免除を今回の未達条件へ戻さない。
8. 新APIを先に配備した間は旧Pagesが追加フィールドを無視する。旧API／旧キャッシュと新Pagesの組合せでは§4.11.3の欠落時非表示が働く。ただし公開受入はAPI/Pages同SHAかつ9名の欄が表示される状態を必須とし、互換フォールバックを公開成功とは扱わない。

公開後の結果記録だけを別commitへ保存する場合、そのdocs SHAを配備済みAPIのrevisionに読み替えない。公開済みSHAを本文へ残し、運用ガイドの文書専用 `[skip ci]` 方針で再配信を抑えるか、次の同SHAリリースへまとめる。アプリコード公開時のskip禁止と区別する。

切戻し条件は既存推薦／目標／履歴の差分、抽出誤り、画面クラッシュ、APIゲート・CORS・probes失敗。公開直後に失敗した場合は先へ進まず、自動配備を採用済みならAPIのCI/CDを停止する。Northflank上で直前の検証済みAPI imageを再配備し、対応する旧SHAのPages run／artifactを再配信して整合を確認する。現在の新mainのゲートを旧SHAへ偽装しない。履歴が保持されない場合は実装差分だけをrevertするPRを作り、修正main SHAのAPI → Pages手順を再実施する。新Pagesが残る間は欠落時非表示で既存詳細を保つ。NF DB・保存データは維持し、旧RailwayへURLだけを戻さない。

### 6.5 Northflank APIの自動デプロイ採用検討（2026-10-08追加）

利用者追加依頼により、APIのCI/CDを常にOFFとする方針には固定しない。**推奨は、以下の前提を整えた後に既存Combined serviceのCI・CDをONへ移行すること**。現状コードのままトグルだけONにするのは未受入。策定時は設計・検討のみ。実装後は動的revision・Pages待機・skip設定を反映済み。runtime照合後にCI/CDをONへ変更。全経路の受入は次の実更新待ち。図鑑の機能設計と自動配備の受入を分け、自動化未達ならPhase 56は§6.3.2の手動配備で公開可能とする。

#### 6.5.1 現状の問題と対処

| 問題 | 現行根拠 | 採用する対処 |
| --- | --- | --- |
| revisionが固定値のまま残る | `Dockerfile.northflank` は `ARG APP_REVISION` の40桁形式だけを検証してENVへ保存。healthは `process.env.APP_REVISION` を優先。手動の都度対象SHAへ設定する運用で、実コードとの一致はDockerfile単体では保証しない | Northflankがビルド時に提供する `NF_GIT_SHA` からAPP_REVISIONを設定。固定SHAを保存したままCI/CDをONにしない |
| PagesがAPI配備より先に検査する | main pushでNorthflankと `deploy-pages.yml` が独立に開始。`scripts/pages.mjs --verify` のhealth検査は現状1回だけ | Pages生成前に、対象SHAのAPI正常応答を期限付きで待つ。その後も既存 `--verify` の厳密比較を残す |
| 不要な再起動 | APIは1 instance／Recreate。各配備で短い受付停止があり、文書だけの変更でも全main追随だと再起動する | 文書だけの変更はAPIとPages双方で同じskip方針。アプリ公開は両者が同じmain SHAをビルドする |
| migrationの誤実行 | Jobには独立したCDとimage-change時のRun設定がある。Jobの最新image追随とDB変更は別契約 | APIだけCI/CD ON。migration JobはCD OFF、manual、image-changeによるRunはNever。実行前だけAPIと同digestへ固定 |
| 手動切戻しを自動配備が上書き | 自動CDは最新buildへ追随する | 切戻し前にAPIのCI/CDを停止し、直前のimageを再配備。復旧後も勝手にONへ戻さず、設定・mainの整合を確認 |

公式資料の確認（2026-10-08）: Northflank「Manage CI/CD」はCombined serviceのCIで新commitをbuild、CDで最新buildをdeployする仕様と、手動配備によるCD無効化、Jobのimage-change Run設定を説明。「Inject secrets」はbuild argument `NF_GIT_SHA`、runtime `NF_DEPLOYMENT_SHA`、変数のdynamic templatingを説明。「Build code from a Git repository」はpath rulesとcommit ignore flagsを説明。外部リンクは共通文書ルールに従い正本に置かず、資料名・確認日・本節の契約へ要点を取り込む。

#### 6.5.2 revisionの自動設定

第一選択はNorthflankのbuild argumentsで `APP_REVISION=${NF_GIT_SHA}` をdynamic templatingとして指定すること。Dockerfileの40桁検証を維持し、毎回のビルド対象SHAをENVへ取り込む。API runtime／secret groupに固定のAPP_REVISIONがある場合は上書き元を整理して、image内の値を覆わないようにする。環境変数全件・秘密値を出力せず、対象キーの有無と一致判定だけを確認する。

策定時はテンプレート参照が未確認だった。実装で複数の手動buildへ別の対象SHAが取り込まれることを確認した。runtime NF_DEPLOYMENT_SHAは2026-10-08に対象2変数のみの一致判定で公開a41823fと照合済み。設定editorの参照と手動buildで確認し、`build SHA == imageのAPP_REVISION == health revision == runtime NF_DEPLOYMENT_SHA` を照合する。保存時に固定値へ展開される、文字列が残る、未解決になる場合はCI/CDをONにしない。

その場合の代替はDockerfileへ `ARG NF_GIT_SHA` を追加し、ビルド中に `NF_GIT_SHA` を40桁検証してrevisionファイルをimageへ保存し、APIのhealthがその不変ファイルを読む方式。ローカルbuildは明示APP_REVISIONを代替入力とし、両方与えられて不一致ならbuildを失敗させる。runtimeの任意固定値を配備identityにしない。代替を採用する場合は本節へ採用結果と変更ファイル・回帰を反映してから実装する。GitHubの最新mainを実行時に問い合わせてrevisionにする方式は、稼働imageと無関係なので採らない。

#### 6.5.3 Pagesの待機と同期ルール

自動化を実装する場合、`scripts/wait-production-api.mjs` とそのnode:testを追加し、`deploy-pages.yml` のPages生成直前に実行する。単一APIのforwardモードを対象とし、他の移行モードへ勝手に適用しない。新たなNorthflank管理用tokenは不要。既存公開healthを使う。

- 期待値は当該runの `GITHUB_SHA`（40桁）。HTTPリクエスト毎の上限5秒、再試行の間隔10秒、全体の上限10分。待機はプロセス内の経過時間で判定し、時間切れ後に成功扱いで進まない。
- 旧revision、再起動中の5xx、通信失敗は期限内だけ再試行。HTTP 200・ok=true・期待revision・maintenance=false・migrationPreview=false・Pages OriginへのCORSを全て確認する。非JSON・不正revision・保守true・preview trueは契約エラーとしてfail。応答本文や秘密値をログに残さない。
- 一致を確認したら既存 `scripts/pages.mjs --verify` を通常実行。待機結果を使ってrevision比較やCORS/RPCゲートを無効化しない。期限切れ時は旧Pagesを維持し、API正常化後の同run再実行で回復する。
- Pagesの公開直前にも対象SHAのAPI healthを再確認し、run開始後に別SHAへ更新されていればartifactを公開しない。GitHub側のconcurrencyだけではNorthflankの並行buildを制御できないため、当面は1つのアプリリリースの受入完了まで次のアプリmainマージを行わない運用とする。
- APIのpath rulesは当初アプリ全体を対象とする。clientだけのmainをAPI build対象外にすると、同SHAゲートが成立しなくなるため、API/serverだけのallow listを設定しない。
- 文書だけの記録にはAPI側でも `[skip ci]` をignore flagとして有効化し、Pages側の既存skipと揃える。Northflankのignore flagsは複数commitのpush全体へ影響し得るため、skip付きの文書commitと通常アプリ公開commitを同じpushへ混ぜない。文書記録SHAと公開release SHAは別記する。
- DB migrationを含む将来の非互換リリースは本自動配備契約の対象外。mainマージ前にCI/CDを停止してbackup・同digest Job・停止点・migration・配備順を別途設計する。新しいDB schemaを古いAPIと同時運用できると仮定しない。

#### 6.5.4 ONへ進む実施順・合格条件

1. 実装依頼を受けたら、サービスがCombined／main／現URL／現DB／現CA／1 instance／Recreateであること、build/runtimeのrevision上書き、ignore flags、JobのCDとRun設定、必要なmainのPR検証を確認する。策定時の検討は運用記録と現行コードに基づく。実装時の再取得結果は§12と実装ログへ記録する。
2. 動的revision設定と必要なPages待機コードを、通常のPR検証・レビューで用意する。mainはPRの最新head検証成功後にマージし、直pushで検証を飛ばさない。
3. CI/CD OFFのまま、対象SHAの手動build・配備でrevisionの4者一致、health／probes／CORS／既存図鑑応答、待機と同SHA Pagesを確認する。既存URL・DBデータ・料金プランは変更しない。
4. ここまで受入済みなら既存APIのCIとCDをONにし、main追随・skip設定を保存して再取得。migration JobはOFF／manual／Neverを維持。トグルONによって未確認の最新buildが即配備されないよう、ON直前のlatest buildを対象SHAへ揃える。
5. 次の許可済みのアプリ更新を1件だけmainへ反映し、build SHA・health revision・Pages run SHA一致、手動build不要、旧API期間の待機→新API成功→Pages公開を確認する。実デプロイを起こすダミーcommitだけのために本番を再起動しない。
6. 待機テストでは「旧SHA→期待SHA」「5xx→正常」「期限切れ」「保守／preview／CORS不正」「公開前のSHA変更」を検証する。skip付き文書記録でAPI・Pagesとも再配信されないことも確認し、未確認なら記録してON受入を確定しない。

必要な条件を満たした場合だけ、運用ガイド・設定台帳・本書の現行CI/CD状態と§6.3.2手順をON運用へ更新する。動的revision参照の未確認は自動化採用のゲートであり、図鑑UIを実装するためのブロッカーではない。別途の新規有料Build／Workflow／サービス追加を前提にしない。
