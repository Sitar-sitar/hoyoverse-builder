- `express`を`^4.22.3`、`nanoid`を`^5.1.16`へ更新し、lockfileを再生成する。express 4系の挙動（Router、body parser設定、`trust proxy`未設定）を変えない。更新後のlockfileで、proxy-addr 2.0.8以上・path-to-regexp 0.1.13以上・qs 6.16以上・body-parser 1.20.6以上に解決されたことをauditで確認する。
- 本番依存の監査ゲート`scripts/audit-gate.mjs`（Node標準のみ）を新設し、`validate-api.yml`とdeploy-pagesのbuild jobで実行する。判定は次の順で、1つでも該当すれば終了1。
  1. `pnpm audit --prod --json`の出力をJSONとして読めない、または出力が通信・registryエラーを示す → `audit_unavailable`。pnpmの終了コードは指摘検出時にも非ゼロになるため、終了コードでは判定しない（fail closed。npm側障害時は復旧後に同じheadで再実行する。直近成功結果の再利用はしない）。
  2. High/Criticalの指摘のうち、`security/audit-exceptions.json`に一致する例外が無いもの → `audit_finding`。
  3. 例外の検証: 必須項目は`id`（GHSA）・`module`・`reason`（到達しない根拠）・`reviewedAt`・`expires`（日付）。`expires`が`reviewedAt`から90日を超える、CI実行日が`expires`を過ぎた、または現在のauditに該当指摘が無い（不要になった例外）→ `audit_exception_invalid`。
- 更新後にHigh以上が残った場合だけ、根拠付きの例外を追加し、実装ログへ記録する。

### 5.2 B：上流取得の残り（SEC-04）

**single-flight**: `getStaticIndex`の順序を「有効なTTL内のcacheを返す → 再試行抑止中ならLKG/EMPTYを返す → 進行中の取得があればそのPromiseを返す → 新しい取得を開始し共有する」とする。共有するPromiseは「取得→成功ならcache・LKG更新と抑止解除、失敗（null含む）なら抑止時刻を設定してLKG/EMPTY」までを含み、finallyで共有を解除する。待機者全員が同じ結果（fresh / LKG / EMPTY）を受け取り、解除後に失敗Promiseを再利用しない。原神/ZZZの`createTimedLoader`は既存の共有を維持する。

**本文の上限**: `server/_core/boundedBody.ts`を新設し、`readBoundedText(response, { maxBytes, budget? })`で読む。

- Content-Lengthが上限を超えれば読まずに`response.body.cancel()`して拒否する（早期拒否の補助。判定の本体は次項）。
- ストリームの実byte数（fetchが展開した後の本文）を数え、上限を超えた時点で`reader.cancel()`して拒否する。chunkは上限内でだけ保持し、最後に1回だけ連結・decodeする。
- `budget`を渡した場合は、同じbundleの全ファイルで合計byteを共有し、合計上限を超えたファイルで拒否する。
- 呼出し側の期限（AbortSignal）は本文読取り完了まで維持する（HSR静的5秒、原神/ZZZ 14秒、MiHoMo 6秒、Enka UIDの既存期限）。

| 取得 | ファイル上限 | 合計上限 | 2026-10-20実測 |
| --- | --- | --- | --- |
| HSR静的bundle（8ファイル） | 8 MiB | 16 MiB | 最大2,543,469 B、合計3,809,093 B |
| 原神静的（characters/loc） | 4 MiB | 4 MiB | 合計420,738 B |
| ZZZ静的（5ファイル） | 4 MiB | 4 MiB | 合計558,625 B |
| UID応答（MiHoMo/Enka/原神/ZZZ） | 暫定4 MiB | — | 未測定（U-3） |
| GitHub OAuth（§5.5） | 1 MiB | — | — |

UIDの上限はU-3の実測後に「実測最大の4倍を2の冪へ切り上げた値、ただし1 MiB以上4 MiB以下」とする。実測最大が1 MiBを超えた場合は実装を止めて本書を改訂する。

**最悪時のメモリ予算**: 同時に読む本文の合計は、静的3bundleの合計上限24 MiBとUID 8枠×4 MiBで最大56 MiB。これに文字列化・JSON展開・mapコピー・既存LKGが加わる。受入は、本番ビルド相当のAPIプロセスを隔離環境で起動し、3bundleの同時cold取得と期限切れ更新（LKG保持中）とUID 8枠を、上限直前サイズの合成JSONで同時に発生させたときのpeak RSSが**384 MiB以下**（512 MBの75%）であること。超えた場合はUID上限→静的合計上限の順に下げて再測定し、採用値を本書へ反映する。

**上限超過時の扱い**（既存の失敗経路へ合わせ、新しいfallbackを足さない）:

| 超過した取得 | 扱い |
| --- | --- |
| MiHoMo UID | 既存どおり主取得の失敗としてEnkaへfallback |
| Enka UID（HSR） | 既存の上流失敗（`public.serviceUnavailable`系）。fallback内なので再fallbackしない |
| HSR静的 | 静的取得の失敗としてLKG/EMPTY＋再試行抑止 |
| 原神/ZZZ静的 | 既存loaderの失敗としてLKG＋再試行抑止 |
| 原神/ZZZ UID | 既存の`public.serviceUnavailable` |

クライアント切断の伝播とSQL実行期限は§3.2のとおり対象外。DB非待機は接続待ちを無くすだけでSQL実行時間を有限にしないため、「全待機時間が有限」とは扱わない。

### 5.3 C：CI権限と自動検出（SEC-05）

- `deploy-pages.yml`はworkflow全体を`contents: read`とし、`deploy` jobに`contents: read`・`pages: write`・`id-token: write`の3つを明記する（job単位で権限を書くと未指定の権限はnoneになるため、`contents: read`も再指定する）。build jobには権限を書かずworkflowの`contents: read`だけを使う。build jobに`ACTIONS_ID_TOKEN_REQUEST_URL`が無いこと（OIDC token取得不可）を確認するstepを入れる。公開後検査は公開HTTPとcheckout済みファイルだけを使うので追加の権限は不要。
- 3つのworkflowの外部Actionsを40桁のcommit SHAへ固定し、行末コメントに元のタグを残す。更新は既存のDependabot（github-actions、週次、グループ化）が担う。
- GitHub設定（U-1承認済み）: Code scanningのdefault setup（CodeQL、JavaScript/TypeScript）、Dependabot alertsとsecurity updatesを有効化する。publicリポジトリの無料範囲に限る。変更前後の状態をGET APIで取得して実装ログへ記録する。default setupがGitHub管理で実行するCodeQL job（`security-events: write`を持つ）は、本書の「write権限はdeploy jobだけ」の対象外とする。

### 5.4 D：Originの制約（SEC-07）

**許可Originの制約**: productionでは`CORS_ORIGINS`に`https://sitar-sitar.github.io`以外が含まれていれば、listen前に起動を拒否する（固定コード`cors_origin_not_allowed`、Phase 60 Cの起動前検証と同じ経路）。developmentは従来どおり追加できる（localhost開発用）。Pagesのlegacy/parallel/forward/rollbackはいずれも同じoriginのパス違いであり影響しない。

**状態変更のOrigin検証**: 判定はtRPCの共通`baseProcedure`のmiddlewareで行い、publicProcedureの`auth.logout`を含む全procedureに掛ける。

| 条件 | 扱い |
| --- | --- |
| `opts.type === "mutation"` かつ 要求に管理session Cookie（`COOKIE_NAME`）が**存在する**（有効・無効を問わない） | `Origin`ヘッダが許可Originと完全一致しなければ、resolverの前に`TRPCError(FORBIDDEN)`。Origin欠落・`null`も拒否 |
| mutationでsession Cookieが無い（Bearerだけ、未認証） | 検証しない |
| query（HTTP POSTで送るqueryを含む） | 検証しない（HTTP methodでは判定しない） |

- 判定はCookieの存在で行い、`Authorization`ヘッダの有無では免除しない。現行の認証順序（Cookieを先に使い、Cookieが無いときだけBearer。無効Cookie時にBearerへ再試行しない）は変更しない。これにより「Cookieで認証された要求に任意のBearerを併記して検証を逃れる」経路を作らない。
- `auth.logout`はCookieが存在すれば検証対象とする（無効・期限切れCookieの削除も外部サイトから強制させない）。Cookieが無いlogoutは従来どおり成功を返す。
- tRPC以外のPOSTは`/api/auth/github/exchange`だけ（2026-10-20に全文検索で確認）。これは短期・単回の交換コードで認証し、応答にCookieを使わないため対象外とする。今後tRPC以外のPOSTを追加する場合は、同じ規則をExpress側で固定403 JSONとして実装する。
- 拒否はbatch内の該当operationだけがtRPCエラーになり、同じbatchの他operationへ影響しない。

### 5.5 E：認証の残り（SEC-08）

- `requestGitHubJson`の本文読取を§5.2の`readBoundedText`（上限1 MiB）へ置き換える。超過は`oauth_upstream_failed`。
- **単体・統合テスト（DBはモック）**: JWTの署名改ざん・`alg: none`・期限切れ・issuer不一致・audience不一致・allowlistから外れた管理者で、管理resolverが呼ばれないこと。OAuth state不一致で403、state Cookieが消費されること。交換コードの期限切れ・使用済み・条件付きUPDATEが0行のときに拒否されること、発行されるSQL条件（`usedAt IS NULL`と期限）を確認する。
- **競合テスト（隔離MySQL、別ゲート）**: 本番ではないMySQL（ローカルまたは使い捨て環境、本番と同じschemaをmigrationで作成）に対し、別接続の2要求が同じ未使用コードをSELECTした後で同時にUPDATEする状況を同期させて作り、ちょうど1件成功・1件失敗になること。条件付きUPDATEの条件を外す変異で失敗すること。隔離MySQLを用意できない場合はNOT_TESTEDとしてAC-Eを未達のまま残し、モック結果を競合検証済みと読み替えない（§10 U-5）。

### 5.6 F：ログとCSP（SEC-09）

**秘匿ログ**: `server/_core/safeLog.ts`を新設する。

- `logFailure(area, code, error?)`の`area`と`code`はTypeScriptの列挙型（文字列リテラルのunion）で、呼出し側は固定値しか渡せない。
- 例外から出すのは、既知の値と完全一致した場合の`name`と`code`だけ。許可する値は列挙する（name: `TRPCError` `AbortError` `TimeoutError` `TypeError` `SyntaxError` `DatabaseConfigError` `OAuthRequestError`、code: TRPCのcode一覧、`ECONNREFUSED` `ECONNRESET` `ETIMEDOUT` `PROTOCOL_CONNECTION_LOST` `ER_DUP_ENTRY` `ER_LOCK_DEADLOCK` `ER_LOCK_WAIT_TIMEOUT`。mysql2の`No connections available.`は`pool_exhausted`へ変換）。それ以外は`unknown`。文字種の正規表現では許可しない。
- message・stack・SQL・パラメータ・URL・query・上流本文・任意オブジェクトはconsoleへ渡さない。出力は1行の文字列で、例外のプロパティ読取り（getterの例外等）で失敗してもlogger自体は例外を投げない。
- 置き換え対象: `server/db.ts`、`server/routers.ts`、`server/displaySettings.ts`、`server/_core/githubAdminAuth.ts`（exchange）、`server/_core/notification.ts`（上流本文の出力は削除）、`server/_core/sdk.ts`。Phase 60のOAuth callbackの固定理由コードは維持する。

**公開PagesのCSP**: Pages build（`vite.pages.config.ts`の`transformIndexHtml`）で、app本体の`index.html`の`<meta charset>`直後・他のリソース指定より前にmeta CSPを挿入する。

```
default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com 'unsafe-inline'; font-src https://fonts.gstatic.com; img-src 'self' data: https://enka.network https://raw.githubusercontent.com; connect-src 'self' <API origin>; base-uri 'self'; form-action 'self' <API origin>; object-src 'none'
```

- `<API origin>`はbuild時の`VITE_API_BASE_URL`から`new URL(...).origin`で作る。HTTPSでない、またはoriginへ正規化できない値ならbuildを失敗させる（既存の`scripts/pages.mjs` `apiUrl()`と同じ条件）。
- `style-src 'unsafe-inline'`は維持する（Reactのstyle属性が多数あり、今回外す根拠がない）。OAuthログインは画面遷移でありconnect-srcへGitHubを足さない。meta CSPでは`frame-ancestors`とreport-onlyが使えないため指定しない。
- SPAの直接アクセス用HTML（`scripts/pages.mjs`の`spaRoutes`が複製するルート別`index.html`と`404.html`）にも同じmetaが入ることを生成物で確認する。旧入口の転送ページは対象外（§3.2）。
- Chromeで3ゲームのUID照会（U-3の実UIDで外部画像の表示を含む）・図鑑・更新履歴・フィードバック・管理画面（OAuthログイン、表示/言語設定の読取）を操作し、consoleのCSP違反が0件であること。

### 5.7 G：PR必須化（SEC-10）

- 設定前に、運用ガイドへ「mainへの直接pushは不可。緊急時もPRを作りCI後にマージする」と書き、利用者のmain直push手順があればPRへ移す（リポジトリ内のworkflow・scriptsにmainへのpush経路は無いことを2026-10-20に確認済み。Dependabotは既にPR経由）。
- ruleset `22368117`へ`pull_request`ルール（必要承認数0、会話の解決は任意）を追加する。bypassは追加しない。
- 確認はGET APIでruleset（対象`refs/heads/main`、active、bypassなし、`pull_request`を含む）を照合し、次の通常PRのマージ成功で行う。設定確認のためだけにmainへ実際にpushする試験はしない。
