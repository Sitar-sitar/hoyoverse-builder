## 4. 設計方針

1. 解消済みの部分はレビューの記録を書き換えず、本書の照合表とレビューの対応状況追記で閉じる。
2. 依存は「使っていないものを消す」を先に行い、残りは互換範囲内の更新に限る。overrideで型やAPI互換性を飛ばさない。
3. 上限値はコード定数とし、実測値に十分な余裕を持たせて決める。環境変数での上書きは追加しない。
4. GitHubの設定変更（C・G）は利用者の承認を得てから行い、変更前後の値を記録する。
5. 拒否は既存の形式に合わせる（tRPCはTRPCError、Express経路は固定JSON）。ログは固定フィールドだけを出す。

## 5. 詳細仕様

### 5.1 A：依存の整理（SEC-03）

- `package.json`から`@aws-sdk/client-s3`、`@aws-sdk/s3-request-presigner`、`streamdown`、`recharts`を削除し、未使用の`client/src/components/ui/chart.tsx`を削除する。削除前に全文検索でimportが無いことを再確認し、型検査・Pages build・API buildで未参照を確認する。`.github/dependabot.yml`のグループから`recharts`・`@aws-sdk/*`の記載を除く。
- `express`を`^4.22.3`、`nanoid`を`^5.1.16`へ更新し、lockfileを再生成する。express 4系の挙動（Router、body parser設定、`trust proxy`未設定）を変えない。
- 本番依存の監査ゲートを`validate-api.yml`とdeploy-pagesのbuild jobへ追加する。新設`scripts/audit-gate.mjs`（Node標準のみ）が`pnpm audit --prod --json`の結果を読み、High以上の指摘が`security/audit-exceptions.json`に無い場合は失敗する。例外には`id`（GHSA）・`module`・`reason`（到達不能の根拠）・`expires`（最長90日）を必須とし、期限切れは失敗にする。audit APIの通信失敗は失敗扱いとし、成功へ読み替えない。
- 更新後にHigh以上が残る場合は、到達性の根拠と期限を例外へ記録したうえで受け入れるかを実装時に判断し、実装ログへ記録する。

### 5.2 B：上流取得の残り（SEC-04）

- `getStaticIndex`にsingle-flightを追加する。cold cache時の同時呼出しは1つの`loadStaticIndex()` Promiseを共有し、完了（成功・失敗）後に共有を解く。既存のTTL・LKG・再試行抑止（60秒）の順序は変えない。原神/ZZZの`createTimedLoader`は既存の共有を維持する。
- 上流応答本文をbyte上限付きで読む共通関数を`server/_core/boundedBody.ts`に新設し、`fetchJson`（原神/ZZZ）、`requestMihomo`、`requestEnka`系、HSR静的取得で使う。Content-Lengthが上限超なら読まずに拒否し、ストリーム読取中に上限を超えたら`reader.cancel()`して拒否する。拒否は既存の上流失敗と同じ分類（HSRはEnkaへのfallback、原神/ZZZは既存の`public.serviceUnavailable`）にする。
- 初期上限: 静的データは1ファイル16 MiB（実測最大2.54MBの約6倍）、UID応答は4 MiB（§10 U-3の実測で妥当性を確認し、必要なら本書を改訂）。

### 5.3 C：CI権限と自動検出（SEC-05）

- `deploy-pages.yml`のworkflow全体権限を`contents: read`だけにし、`deploy` jobにだけ`pages: write`と`id-token: write`を付ける。build jobで`ACTIONS_ID_TOKEN_REQUEST_URL`が無いこと（OIDC token取得不可）を確認するstepを入れる。
- 3つのworkflowの外部Actionsを40桁のcommit SHAへ固定し、行末コメントに元のタグを残す。更新は既存のDependabot（github-actions、週次）に任せる。
- GitHub設定（利用者承認後）: Code scanningのdefault setup（CodeQL、JavaScript/TypeScript）を有効化、Dependabot alertsとsecurity updatesを有効化する。publicリポジトリで無料の範囲に限る。変更前後の状態をAPIで取得して記録する。

### 5.4 D：Originの制約（SEC-07）

- productionでは`CORS_ORIGINS`に`https://sitar-sitar.github.io`以外が含まれていれば起動を拒否する（固定コード`cors_origin_not_allowed`）。developmentは従来どおり追加可能。Phase 60 Cと同じくlisten前に検証する。
- Cookieで認証された状態変更（tRPCのmutation、`/api/auth/github/exchange`を除くPOST）は、`Origin`ヘッダが許可Originと一致しない場合に403で拒否する。`Authorization: Bearer`で認証された要求、Originなしの要求でCookieを使わないもの（CLI等）、GETのOAuth callbackは対象外とする。判定はtRPC middlewareで行い、拒否はTRPCError（FORBIDDEN）とする。
- 管理画面の通常ログイン・保存（Bearer経路とCookie経路の両方）と、第三者Cookie遮断時のBearer経路を回帰確認する。

### 5.5 E：認証の残り（SEC-08）

- `requestGitHubJson`の本文読取を§5.2の上限付き関数へ置き換える（上限1 MiB）。超過は`oauth_upstream_failed`。
- 統合テストを追加する（DBは隔離したモックまたは疑似サーバー）。JWTの署名改ざん・`alg: none`・期限切れ・issuer/audience不一致・allowlistから外れた管理者で管理resolverが呼ばれないこと、OAuth state不一致で403・Cookieが消費されること、交換コードの期限切れ・再使用・同時消費（2要求同時でちょうど1件成功）を確認する。

### 5.6 F：ログとCSP（SEC-09）

- `server/_core/safeLog.ts`を新設し、`logFailure(area, code, error?)`は`area`・固定`code`・例外の`name`と`code`（文字列のallowlist形式に一致する場合のみ）だけを出す。SQL、パラメータ、URL、query、上流本文、例外messageとstackは出さない。§2の該当箇所（db/routers/displaySettings/githubAdminAuth exchange/notification/sdk）をこれへ置き換える。`notification.ts`の上流本文出力は削除する。
- 公開Pages（app本体の`index.html`）へmeta CSPを入れる。初期案:
  `default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com 'unsafe-inline'; font-src https://fonts.gstatic.com; img-src 'self' data: https://enka.network https://raw.githubusercontent.com; connect-src 'self' <API origin>; base-uri 'self'; form-action 'self' <API origin>; object-src 'none'`
  API originはPages build時の`VITE_API_BASE_URL`から生成する。`style-src 'unsafe-inline'`はUI部品が実行時に挿入するstyleの有無をChromeで棚卸しして、不要なら外す。meta CSPでは`frame-ancestors`とreport-onlyが使えないため指定しない。
- Chromeで3ゲームのUID照会・図鑑・更新履歴・フィードバック・管理画面（OAuthログインを含む）を操作し、CSP違反がconsoleに出ないことを確認する。

### 5.7 G：PR必須化（SEC-10）

- 利用者承認後、ruleset `22368117`へ`pull_request`ルール（必要承認数0、未解決の会話の解決は任意）を追加する。単独開発のため承認数は0とし、PR経由とCIを強制することを目的にする。bypassは追加しない。緊急時の手順（PRを作ってCI後にマージ）を運用ガイドへ書く。
