## 1. 依頼の内容

上記の修正設計書を、実装に入る前にレビューしてください。設計どおりに実装したときに、本番障害・既存機能の破壊・セキュリティ上の見落としが起きないか、また実装者が推測なしに着手できる粒度になっているかを判定してください。

判定は「Go / 条件付きGo / No-Go」のいずれかで出してください。条件付きGoの場合は、着手前に解消が必要な指摘を明示してください。

- 2026-10-06 のセキュリティ再確認レビュー（[ソースコードレビュー_セキュリティ再確認_2026-10-06.md](ソースコードレビュー_セキュリティ再確認_2026-10-06.md)）で SEC-01〜10 が挙がりました。P1 の SEC-01/02 は修正・本番反映済みです（[P1修正](修正設計書_P1セキュリティ修正_2026-10-06.md)）。
- 2026-10-19〜20 の Phase 60（[運用安定化](修正設計書_運用安定化と保守性改善_2026-10-19.md)）で、SEC-04/06/08/09 の一部を解消しました（新規UID照会の8枠、DBプール非待機、本番DB設定の起動前検証、OAuth通信の5秒期限、OAuth callback のログの固定コード化）。
- 今回の設計書は、残りを main `77e44f7` と GitHub 設定に照合し直し、SEC-06 を解消済みとして閉じ、残りを段階A〜Gに分けたものです。

## 3. 観点

既定の観点は「設計整合・実装安全性・回帰・残課題」です。加えて、次の点を確認してください。

1. **事実の正しさ**: 設計書§2の現状照合（各 SEC の現状、audit の発生源表、上流ファイルの実測サイズ、GitHub 設定の現状）がコードと設定に一致しているか。
2. **スコープ判断**: §3.2 OUT（UID照会のクライアント切断伝播、SQL実行期限、express 5、legacy 経路の削除、旧入口ページの CSP）を見送ってよいか。SEC-06 を、Job からの実接続確認が次回 migration まで未実施のまま「解消済み」として閉じてよいか。
3. **実装可能性**: 各段階の仕様が、実装者が推測せずに着手できる粒度か。受け入れ条件（§9）とテスト（§8）が対応しているか。
4. **本番への影響**: 段階ごとの公開で、ログイン不能・公開停止・誤拒否が起きないか。戻し方が成立するか。

## 4. 特に見てほしい論点

作成者自身が判断に自信を持てていない点です。指摘の有無にかかわらず、各項目に一言ずつ見解をください。

| # | 段階 | 論点 |
| --- | --- | --- |
| Q1 | A | 監査ゲートは audit API の通信失敗を「失敗」とする（fail closed）。npm 側の障害で PR と公開がすべて止まるが、それで運用できるか。代替（直近成功結果の再利用など）を設けるべきか |
| Q2 | A | express 4.21.2→4.22.3 で qs 6.16 系・body-parser 1.20.8 などへ上がる。tRPC の GET 入力解析、既存の 415/413 境界（P1修正の受入条件）に影響しないか |
| Q3 | B | 上限値（静的 1 ファイル 16 MiB、UID 応答 4 MiB）。8枠すべてが同時に上限近くの応答を読んだ場合の最悪メモリ（512 MB コンテナ）として妥当か。上限超過時に HSR を Enka へ fallback させる扱いでよいか |
| Q4 | B | HSR 静的データの single-flight を、既存の TTL・直近正常値（LKG）・60秒の再試行抑止とどう組み合わせると正しいか。失敗した共有 Promise を後続の呼出しが受け取らない順序になっているか |
| Q5 | C | deploy job だけに `pages: write` / `id-token: write` を付けた場合、公開後検査（`scripts/monitor-production.mjs`）に必要な checkout が `contents: read` で足りるか。Actions の SHA 固定と既存 Dependabot（github-actions、週次・グループ化）の組合せで更新が止まらないか |
| Q6 | D | 「Cookie で認証された状態変更」を tRPC middleware でどう判定するか。現行の `getSessionToken`（`server/_core/githubAdminAuth.ts`）は **Cookie を先に見て、無いときだけ Bearer** を使うため、両方を持つ要求は Cookie で認証される。設計書§5.4 の「Bearer で認証された要求は対象外」がこの順序と矛盾しないか。Safari/ITP 向けの exchange code 経路、`auth.logout`（publicProcedure の mutation）を対象に含めるべきか |
| Q7 | D | production で `CORS_ORIGINS` を正式 Pages origin だけに制限する。Pages の legacy/parallel/rollback モードや検証用 Pages で別 origin を使う運用が残っていないか |
| Q8 | E | 交換コードの「同時消費でちょうど1件成功」を、モック DB で検証できるか。条件付き UPDATE の競合を示すには隔離した実 MySQL が必要ではないか |
| Q9 | F | meta CSP の初期案（§5.6）で、Google Fonts、Enka/GitHub raw の画像、API への接続、OAuth ログインの遷移、ダーク表示など既存 variant が壊れないか。`style-src 'unsafe-inline'` を外せる見込みはあるか |
| Q10 | G | PR 必須（承認数0）を有効にした後も、既存の自動化（Dependabot、利用者の Codex 運用など）が main へ直接 push していないか。直接 push が拒否されて止まる経路がないか |

## 5. 参照してよい範囲と制約

- 読取専用で行ってください。コード・設計書・GitHub 設定・依存を変更しないでください（指摘の反映は作成者が行います）。
- 実行してよいもの: リポジトリ内の閲覧と検索、既存テストの実行、`pnpm audit --prod`、GitHub の設定を読むだけの API（`gh api` の GET）、公開 URL への通常の GET。
- 行わないこと: 本番への攻撃・負荷・大量要求、JWT の偽造送信、管理画面での設定保存、DB への接続、依存のインストール・更新、GitHub 設定の変更。
- 秘密情報（DB URL、password、CA 本文、token、GitHub App secret）や実 UID、個人データをレビュー文書に書かないでください。
- 外部資料を根拠にする場合は、リンクではなく出典名・ID・取得日・要点を書いてください（設計書管理ルール §4.1）。

## 6. 成果物の形式

既存の設計レビュー（例: [設計レビュー_運用安定化と保守性改善_2026-10-19.md](設計レビュー_運用安定化と保守性改善_2026-10-19.md)）と同じ構成でお願いします。

1. **ヘッダ**: 作成日、対象アプリ、種別（設計レビュー）、レビュー対象（設計書へのリンク）、前提コミット、観点、判定（Go / 条件付きGo / No-Go と一文の理由）、関連。
2. **事実確認の結果**: 設計書§2 の主張ごとに、照合箇所（ファイル:行、または実行したコマンド）と判定（正 / 誤 / 一部誤り）を表で。
3. **指摘**: `R-01` からの通し番号で、各指摘に「重大度（重大 / 中 / 低 / 参考）」「該当箇所（設計書の節、コードのファイル:行）」「指摘」「推奨対応」を書き、事実と提案を分けてください。重大 = 着手前に解消が必須、中 = 該当段階の着手前に反映、低 = 本文の誤記・補足。
4. **§4 の論点 Q1〜Q10 への見解**: 一問ずつ。指摘に回したものはその R 番号を書いてください。
5. **良い点**: 維持すべき判断があれば。
6. **反映先と状態**: R 番号ごとに、反映先の節と「未反映」を表で（反映は作成者が行います）。
7. **実施したこと・していないこと**: 実行したコマンド、確認できなかった事項。

## 7. 受け取り後の流れ

作成者がレビューを受け取り、設計書へ追記反映して設計書の§変更履歴にレビューへの参照を残します。判断が利用者に必要な指摘は、利用者に確認してから反映します。反映後に実装（段階A）へ進みます。
