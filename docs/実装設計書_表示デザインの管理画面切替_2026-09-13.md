## 1. 目的・背景

- 2026-09-13 に、見せ方の改修案6件（A〜F）を方向性メモとして提示した。いずれも既存の API 応答・ガイドデータだけで成立することを確認済み。メモは外部ページのためリンクせず、要旨を §4.4 へ転記する。
- 案は「デザイン決定後に実装可否を再判定する」段階で、見た目の細部は未確定。公開サイトへ一度に反映すると、見比べも撤回もできない。
- そこで各案を**現行表示と並存する表示バリアント**として実装し、管理者が次の3つを行えるようにする。
  1. 自分のブラウザだけでプレビューする。
  2. 公開する見せ方を選ぶ。
  3. 問題があれば即座に現行表示へ戻す。
- 狙いは「コードのデプロイ」と「公開する見せ方の決定」を分離すること。

## 3. 全体方針

### D1. 切替の単位は「案ごとの表示キー × バリアント」

- 表示キー1つにつき値は1つ。値 `legacy` は常に「現行表示」を指し、全キーの既定値とする。
- キーとバリアントは `shared/displayVariants.ts` の登録表（コード定数）を正本とする。**バリアントの追加はコード変更とデプロイ、公開する値の切替は管理画面**で行う。
- **未完成のバリアントは登録表に載せない**。管理画面に出る選択肢は、すべての対象画面で実装と検証が済んだものだけにする。

### D2. 各キーは互いに依存しない

- どのキーの組み合わせでも画面が成立するように作る。あるバリアントが別キーの状態を前提にしない。例として、F の3ゲームパネルは E-1 のアクセント色が無くても自前の色で描ける。
- 組み合わせを全部は検証しない。代わりにこの依存禁止を設計規約とし、検証を「全キー legacy」「各キー単独で新バリアント」「全キー新バリアント」の3構成に絞る（§8）。

### D3. 公開設定は MySQL の新テーブルに保存する（追加のみ）

- 管理画面から実行時に切り替えるには、デプロイと独立した保存先が必須である。次の代替案は採らない。
  - Railway 環境変数: 管理画面から変更できず、反映に再デプロイが要る。
  - リポジトリ内の JSON: 変更に commit と Pages 再ビルドが要り、管理画面で切り替える要件を満たさない。
- 既存テーブルは変更せず、新テーブルを1つ追加する（§4.1）。**追加はユーザー確認済み（2026-09-13、§10 Q1）。**

### D4. プレビューは管理者のブラウザ内だけで行い、下書きをサーバーに持たない

- 下書き用のテーブルや状態を作らない。プレビュー値は `sessionStorage` に置き、管理者としてログインしているタブでだけ公開値より優先する。
- この判定はクライアント側だけで行い、**セキュリティ境界ではない**。バリアントのコードは Pages で誰でも取得できる公開 JS であり、管理者専用データを一切扱わないことを規約とする。保存（公開）は `adminProcedure` で保護する。

### D5. 設定が取れないときは現行表示に倒す（fail-safe）

- DB 未接続、API 失敗、未知のキーや値、登録表から消えたバリアントは、すべて `legacy` として扱う。
- 表示設定の不調で公開サイトが表示できなくなる経路を作らない。

### D6. 現行表示のコードは移動しない

- 既存の JSX を別ファイルへ切り出さず、その場で `variant === "gauge" ? <新部品 /> : (既存JSX)` と分岐する。既存テストが守っている経路を動かさないため（KN-009）。
- 新バリアントは、既存ページ内で計算済みの値（`activeComparisons` など）を props で受け取り、**新しい計算ロジックを持ち込まない**。
- 新バリアントの部品は各ページ（遅延チャンク）から import し、`App.tsx`（entry）からは import しない。Pages コード分割設計の「同期 import を足すと entry が 500kB に寄る」を守るため。例外は §4.2 の Provider とプレビュー帯（小さい部品のみ）。
- 例外1（DR-05）: B の詳細シートは、ページ内で C・D の分岐を解決した詳細 JSX を変数へ一度だけ束ね、`CatalogShelf` へ children として渡す。詳細4セクションを複製しない。
- 例外2（U17）: 「計算を持ち込まない」は目標・推奨・比較の算出に限る。ゲージの座標や表示用の集計は部品内で計算してよい。

## 4. 詳細仕様

### 4.1 保存テーブル `site_display_settings`

| 列 | 型 | 制約 | 意味 |
| --- | --- | --- | --- |
| `settingKey` | varchar(64) | PK | 表示キー（例 `progressionStepper`） |
| `variant` | varchar(32) | NOT NULL | 公開中のバリアント ID |
| `updatedAt` | timestamp | NOT NULL, DEFAULT now, ON UPDATE now | 最終更新日時 |

- 行が無いキーは `legacy` とみなす。
- 値は enum にせず varchar とし、正当性は登録表で検証する。バリアント追加のたびにマイグレーションを起こさないため。
- 更新者と変更履歴は持たない（§7、§10 Q8）。個人データを保存しない。
- `drizzle/schema.ts` に定義し、`drizzle-kit generate` で `drizzle/0006_*.sql` を作る。本番へは Railway の `preDeployCommand`（`drizzle-kit migrate`）で適用される。
- **注意（既存のマイグレーション履歴）**: `0005_swift_exchange_code.sql` は手書きで、`drizzle/meta` に 0005 のスナップショットが無く、テーブルも `schema.ts` に定義されていない。generate は 0004 のスナップショットと比較するため、実装時に**生成 SQL が `site_display_settings` の CREATE だけであること**を目視確認する。0005 のテーブルを触る文が混ざったら採用しない。
- `drizzle.config.ts` は `DATABASE_URL` 未設定で例外を投げるため、generate 時はダミー値を与える（generate は接続しない）。

### 4.2 切替基盤

#### 4.2.1 登録表 `shared/displayVariants.ts`（定数と純関数のみ）

```ts
export type DisplayVariantDefinition = {
  key: string;                 // 表示キー
  proposal: "A" | "B" | "C" | "D" | "E-1" | "E-2" | "F";
  label: string;               // 管理画面の表示名（日本語）
  screens: string[];           // 影響する画面（管理画面の説明用）
  variants: Array<{ id: string; label: string; description: string }>; // 先頭は必ず legacy
  previewPath: string;         // プレビュー時に開く既定の画面（"/"、"/characters" など）
};

export const DISPLAY_VARIANTS: readonly DisplayVariantDefinition[];

export type PublishedState =
  | { status: "loading" }                                   // 初回取得中
  | { status: "success"; variants: Record<string, string> } // 取得成功（疎な公開スナップショット）
  | { status: "error" };                                    // 取得失敗

/** 全登録キーについて有効な値を返す。 */
export function resolveDisplayVariants(input: {
  published: PublishedState;
  cached: Record<string, string> | null;      // 期限内で検証済みの localStorage 前回公開値
  preview: Record<string, string> | null;     // 検証済みの sessionStorage プレビュー値
  isAdmin: boolean;
}): Record<string, string>;

/** 登録表に無いキー・値を落とす。 */
export function sanitizeDisplaySettings(raw: Record<string, string>): Record<string, string>;
```

- 公開値の決め方は、取得状態で分ける（DR-01）。
  - `success`: 公開スナップショットだけを使う。キーの欠落と無効値は `legacy`。**過去のキャッシュへは戻らない**。サーバーが `source: "default"` を返した場合も、空のスナップショットとして全キー `legacy`。
  - `loading`: 期限内の `cached` を使い、無ければ `legacy`。
  - `error`: 全キー `legacy`（D5）。
- その上で、`isAdmin` のときだけ `preview` の有効値をキー単位で優先する。プレビューは取得失敗中も維持する（U02）。
- キャッシュは `{ savedAt, variants }` の形で保存する。24時間を超えたもの、JSON の破損、オブジェクト以外、文字列以外の値は未保存として扱う（U03）。

| キー | 案 | 登録する Phase | バリアント |
| --- | --- | --- | --- |
| `progressionStepper` | D | Phase 1 | `legacy` / `stepper` |
| `statGauge` | A | Phase 2 | `legacy` / `gauge` |
| `partyFormation` | C | Phase 3 | `legacy` / `formation` |
| `topPortal` | F | Phase 4 | `legacy` / `portal` |
| `siteChrome` | E-1 | Phase 5 | `legacy` / `unified` |
| `catalogShelf` | B | Phase 6 | `legacy` / `shelf` |
| `colorTheme` | E-2 | Phase 7 | `legacy`（ライト固定）/ `switchable` |

- Phase の順はユーザー確認済み（2026-09-13、§10 Q3）。
- デザイン確定の結果、1つの案に新バリアントを2つ以上置く場合は、その Phase の追記で `variants` に足す（例: F の `portal-paper` / `portal-dark`）。

#### 4.2.2 API（`server/routers.ts` に `display` ルーターを追加）

| 手続き | 権限 | 入力 | 出力 |
| --- | --- | --- | --- |
| `display.settings` | public（query） | なし | `{ variants: Record<string, string>, source: "database" \| "default" }` |
| `display.adminSettings` | admin（query） | なし | `{ entries: Array<{ key, variant, updatedAt: string \| null }> }`（登録表の全キー） |
| `display.publish` | admin（mutation） | `{ changes: Array<{ key, variant }> }`（1件以上、登録キー数以下、キー重複なし） | `display.settings` と同じ形 |

- `display.settings` は**例外を投げない**。DB 未接続（`getDb()` が null）や取得失敗では `console.error` を出し、`{ variants: {}, source: "default" }` を返す（D5）。
- DB から読んだ値は `sanitizeDisplaySettings` を通す。`legacy` の行は応答から省く。
- `display.publish` は zod の `superRefine` で、登録表に無いキー・値と重複キーを `BAD_REQUEST` で拒否する。
- 複数キーは1トランザクションで upsert する。`legacy` も行として保存し、行削除はしない。
- 保存失敗は既存の手続きと同じく `INTERNAL_SERVER_ERROR`（`Unable to save display settings`）を返す。
- 公開値はプロセス内に 60 秒キャッシュし、`display.publish` の成功時に破棄する。破棄時に世代番号を進め、破棄より前に始まった読み取りの結果ではキャッシュを埋め直さない。取得失敗はキャッシュしない（U10）。
- 複数の管理者が同じキーを更新した場合は、最後の書き込みを優先する（U08）。
- 応答にユーザー情報と更新者を含めない。リクエストボディは数百バイトで、既存の 256kb 上限に収まる。
- DB 層は `server/db.ts` に `getDisplaySettingRows()` と `upsertDisplaySettings(changes)` を足す。既存関数と同じく DB 未接続時は例外を投げ、`display.settings` 側で握りつぶす。
- キャッシュ・sanitize・fail-safe の組み合わせは `server/displaySettings.ts` に置く。

#### 4.2.3 クライアントの設定解決

- `client/src/contexts/DisplaySettingsContext.tsx` に `DisplaySettingsProvider` と `useDisplayVariant(key)` を置く。状態は `useState` だけで持ち、グローバル状態ライブラリは使わない。
  - `trpc.display.settings.useQuery(undefined, { staleTime: 60_000, refetchInterval: 60_000, refetchIntervalInBackground: false, refetchOnWindowFocus: true, retry: 1 })` で公開値を取る。表示中のタブは60秒ごと、非表示から戻ったときに再取得する（DR-02）。
  - 取得に成功したら `localStorage["hb.displaySettings.v1"]` へ `{ savedAt, variants }` を保存する。保存するのは DB から読めた応答（`source: "database"`）のときだけとし、DB 障害時の空応答で直前の公開値を消さない。読み書きは try/catch で囲み、失敗しても表示は続ける。
  - プレビュー値は Provider の React 状態として持ち、`setPreview` / `clearPreview` で状態と `sessionStorage["hb.displayPreview.v1"]` を同時に更新する。storage イベントは待たない（U04）。
  - プレビューを適用するのは、`useAuth()` の取得が終わり `user.role === "admin"` のときだけ。取得が成功して管理者でないと確定したら、保存済みのプレビューを消す。取得中や通信失敗では消さない（U05）。
  - 値の決定は `resolveDisplayVariants` に任せる。
- **初回表示の待機（ちらつき防止を優先。2026-09-13 確定、§10 Q2）**
  - `localStorage` に前回値が無いときだけ、公開値の取得完了か **600ms 経過**の早い方まで、ルートを既存の `RouteFallback`（空の外枠）のまま待たせる。
  - 前回値があれば待たずに描画し、取得後に差分があれば1回だけ切り替える。
  - 取得に失敗したら待機を解いて `legacy` で描く。待機の解除は一度だけ行い、600ms 後に届いた成功応答はその時点で適用する。この場合だけ表示の切替が起きうるため、「ちらつきゼロ」とは謳わない（U11）。
  - 理由は、初回訪問で現行表示から新表示へ画面全体が入れ替わるちらつき（特に F）を避けるため。`auth.me` と同じバッチ要求に乗るため、往復は増えない見込み。待機する方式は確定とし、実測（§8 M3）は上限 600ms の調整にだけ使う。
- `App.tsx` では `LanguageProvider` の内側に `DisplaySettingsProvider` を置き、`/admin/display` を `lazy()` で追加する。
- 既存 `useAuth` の `localStorage.setItem("manus-runtime-user-info", …)` を try/catch で囲む。認証判定は従来どおりクエリ結果を使い、補助保存の失敗で描画が止まらないようにする（DR-04）。

#### 4.2.4 プレビュー

1. 管理画面でキーごとに値を選ぶ。フォームの状態は `useState` で持つ。
2. 「この組み合わせをプレビュー」を押すと、選択値を Provider の `setPreview` で設定し、選んだ画面（固定候補: UID照会 `/`、キャラ図鑑 `/characters`、更新履歴 `/updates`）へ、Wouter の base に沿って同じタブで遷移する。UID などの入力値は保存しない（U12）。
3. 管理者ログイン中のタブでは、公開画面の上端に `DisplayPreviewBanner` を出す。文言は「プレビュー表示中：公開中の見せ方と N 件異なります」で、「管理画面へ戻る」「プレビューを終了」を置く。差分が0件でも、プレビューが有効な間は帯と終了操作を出す（U12）。
4. 管理画面へ戻ると、フォームを `sessionStorage` のプレビュー値で初期化する。
5. 「プレビューを終了」または公開成功で、`clearPreview` によりプレビューを消す。

- プレビュー帯は管理者にしか出ない。非管理者が `sessionStorage` を手で書いても、解決時に無視される（D4）。
- プレビュー帯と管理画面の文言は日本語だけにする。既存の管理者ポータル `AdminHome` に合わせる（§10 Q7）。

#### 4.2.5 管理画面 `/admin/display`（`client/src/pages/DisplaySettingsAdmin.tsx`）

- 権限による表示分岐（読み込み中 / 非管理者 / 管理者）は `AdminHome` と同じにする。
- `AdminHome` の管理メニューに「表示デザイン」カードを1枚足す。
- 未ログイン時は既存の GitHub 認証でログインする。ログイン後の戻り先に `/admin/display` を許可する（クライアントの許可リスト。サーバーの `sanitizeAdminReturnPath` は `/admin/` 配下を許可済み）。
- キーごとの行に、案の記号・表示名・影響画面・公開中の値・最終更新日時（JST）・バリアントのラジオ（説明文付き）を並べる。
- フォームの「公開中の値」は `display.adminSettings` を基準にする。フォームは最初の取得時と公開成功時にだけ初期化し、編集中の選択を再取得で上書きしない（U06・U07）。
- `display.adminSettings` の取得に失敗したら、全キー現行と誤表示せずにエラーを出し、公開操作を無効にする（U07）。
- 操作は次の3つ。
  - **この組み合わせをプレビュー**: 開く画面を選べる。
  - **公開する**: 押した時点で `display.adminSettings` を再取得し、最新の公開値との差分を「現在 → 新」で確認ダイアログ（`alert-dialog`）に並べる（U08）。確定で `display.publish` を呼ぶ。成功したら応答で `display.settings` のキャッシュを更新し、プレビューを消して画面内に「公開しました。」を表示し、両方を再取得する。結果の表示は既存の管理画面（`FeedbackAdmin`）に合わせて画面内のメッセージとし、トーストは使わない。
  - **すべて現行に戻す**: 確認後、全キーを `legacy` にして `display.publish` を呼ぶ。
- 変更が無いときは「公開する」を無効にする。
- 保存に失敗したら「保存できませんでした。時間をおいて再度お試しください。」を表示し、選択状態は保持する。
- 保存は成功したが再取得に失敗した場合は、「公開しました。最新状態の取得に失敗したため、再読み込みしてください。」と分けて表示する。送信中は各ボタンを無効にし、二重送信しない（U09）。

### 4.3 全バリアント共通の規約

- **3言語**: 新しい文言は既存の `t()` 辞書（`LanguageContext.tsx`）または図鑑の `uiText` に、ja / en / zh-CN をそろえて足す。ガイド本文（推奨セットなど）は現行と同じく日本語のまま表示する。
- **URL**: `?game=` / `?uid=` / `?character=` の直リンクは、どのバリアントでも現行と同じ意味で動く。
- **自動照会の禁止**: 記憶済み UID は入力欄に入れるだけで、送信するまで照会しない（`Home.tsx` の現行の規約）。F でも守る。
- **データの形の揺れ**: 凸の `preparing`、目標の `targets: []`、`statsStatus: "unavailable"`、PT メンバー3人（ZZZ）と4人、Enka フォールバック表示、推奨PT 0件を、どのバリアントも現行と同じ意味で表示する。
- **色**: 新バリアントの強調色は `var(--game-accent, <現行の amber 系の色>)` で参照する。`--game-accent` を定義するのは E-1 だけにする（D2）。
- **動き**: アニメーションを入れる場合は `prefers-reduced-motion` で止める。
- **操作性**: クリックできる要素はボタンかリンクにし、キーボードで操作できるようにする。
- **旧クライアントとの互換**: 登録表に無いキーは、サーバーとクライアントの両方で除外する。古いクライアントの「すべて現行に戻す」は、そのクライアントが知るキーだけを戻す。公開操作の前に、Pages と Railway の両方が同じ版であることを確認する（U26）。

### 4.4 各案のバリアント仕様

各項の「デザイン確定ゲート」は、その Phase の着手前にユーザーと決め、§4.5 に記録する項目である。G-D 以外の表示仕様は候補であり、ゲートを確定して §4.5 に記録するまで実装しない（DR-06）。

#### A. `statGauge` = `gauge`（目標マトリクスの達成ゲージ化）

- **対象**: `Home.tsx` の「目標マトリクス」セクションと「次の強化」セクション。
- **表示**
  - サマリーに、目標達成数 / 比較対象数と、到達ティア（妥協未満 / 妥協 / 目標 / 厳選）を出す。`activeComparisons[].achieved` の集計だけで作る。
  - 1ステータスにつき1本のゲージを描く。左端は0、右端は `max(厳選, 現在値) × 1.1`。妥協・目標・厳選を目印線、現在値をマーカーで示す。`current === null` はマーカーを出さず「未取得」とする。
  - PT・凸で目標が変わったキーは、`selected.comparisons`（変更前）の目標を点線、`activeComparisons`（変更後）を実線で重ねる。
  - 「次の強化」は既存の `activeRecommendations`・`equipmentActions`・`actionReason` をそのまま使い、装備提案は開閉式にする。
  - `statsStatus === "unavailable"` と比較対象0件では、現行と同じ文言（`comparisonPending` / `allTargetsMet` / `noRegisteredTargets`）を出す。
  - モバイルはゲージを縦に積み、現行のモバイル用カードは出さない。
- **データ**: 既存のみ。
- **デザイン確定ゲート（G-A）**: ゲージの形（1本バー / 3分割セグメント / 円弧）、ティア名を出すかどうか。
- **着手前に採否を決める事項**: レビュー U15（到達ティアの定義、未取得を含むときの判定保留、0件を達成扱いにしない）、U16（ゲージ上限を旧新の全目印と現在値の最大×1.1にする）、U17（D6 例外2）。

#### B. `catalogShelf` = `shelf`（図鑑のカード棚と詳細シート）

- **対象**: `CharacterCatalog.tsx` の一覧（左リスト）と詳細の配置。
- **表示**
  - 一覧をカードの格子にする。カードにはキャラ名・ゲーム色の帯・精査状態（「精査済み B17」/「汎用プロファイル」）を出す。`entries[].name / status / batch` だけで作る。
  - 絞り込みは、ゲーム（現行）・名前検索（現行）・精査状態（すべて / 精査済み / 汎用）・バッチ（`entries` に現れる batch 値）。並び順は、カタログ順（現行）とバッチの新しい順。
  - 詳細は `sheet` で開く（デスクトップは右から、モバイルは全画面）。中身は現行の詳細4セクション（推奨ビルド → 推奨ステータス → 推奨PT → 凸）を同じ順で置き、上部に4セクションへのジャンプを固定する。
  - カードを開くと、現行と同じく `replaceState` で `?game=&character=` を書く。`character` 付きの直リンクは、シートを開いた状態で表示する。
  - **shelf では `character` が無いときに先頭キャラを自動選択しない**。現行の自動選択は legacy にだけ残す。シートを閉じたら `character` を URL から外す。
- **データ**: 既存のみ。ロール（運命・職業）での絞り込みは OUT（§10 Q4）。
- **デザイン確定ゲート（G-B）**: カードの密度（1行あたりの枚数）、ゲーム色の帯の表現、詳細をシートにするかページ内展開にするか。
- **着手前に採否を決める事項**: DR-05（D6 例外1。C・D を解決済みの詳細を children で渡す）、U23（URL の削除・不正な character・検索と開いた詳細の関係）、U24（並び順・batch なし・閉じたときのフォーカス）。B×C・B×D・B×両方・B×各 legacy を個別に確認する。

#### C. `partyFormation` = `formation`（推奨PTの隊列表示）

- **対象**: `Home.tsx` の「おすすめPT編成」セクションと、`CharacterCatalog.tsx` の「推奨PT」セクション。
- **表示**
  - PLAN 01〜03 の切替は現行どおり。選んだ案のメンバーを横一列の枠に並べ、枠数は `members.length` とする。モバイルは横スクロール。
  - 選択中キャラの枠を強調する。一致判定は `member.name.ja` と表示中キャラ名（UID照会は `selected.name`、図鑑は `reference.name`）の**完全一致だけ**とし、一致しなければ強調しない（推測で寄せない）。
  - ロール色帯は、`member.role.ja` に含まれる語で分類する定数表で決める（例: アタッカー / サポート・バッファー / デバッファー / 回復 / 耐久・シールド）。どれにも当たらないロールは無彩色にする。分類表はコンポーネント内の定数とする。
  - 目標変更は、`targetChanges` を「ステータス名 変更前 → 変更後」のチップで並べ、理由は開閉式にする。変更前の値は、UID照会では `selected.comparisons`、図鑑では `reference.guide.targets` の「目標」値。変更前が無いキーは「→ 変更後」だけを出す。
  - 参照元・確認日・SNS 照合は、現行の脚注をそのまま出す（情報源ポリシーに関わるため省略しない）。
- **データ**: 既存のみ。メンバー名から図鑑へのリンクは OUT（§10 Q5）。
- **デザイン確定ゲート（G-C）**: 枠の見た目（カード / 円形スロット）、ロール色の割り当て。
- **着手前に採否を決める事項**: U18（ロール語が重複したときの優先順位と、キャラ名の言語差）、U19（「変更前」を基礎目標と表記するか）。

#### D. `progressionStepper` = `stepper`（凸の6段ステッパー）

- **対象**: `Home.tsx` の「凸効果・目標補正」セクションと、`CharacterCatalog.tsx` の「凸・星魂・心象映画」セクション。
- **表示**
  - 1〜6 を**縦のタイムライン**で並べる。各段はゲーム別の記号・段番号・効果名を持ち、段どうしを縦線でつなぐ。`role="tablist"`（`aria-orientation="vertical"`）とし、上下キー・Home・End で移動する。選択中の段だけを tab 順に入れ（roving tabindex）、各段と詳細パネルを `aria-controls` で関連付ける（U13）。
  - **ゲーム別の記号**: HSR（星魂）は4本光の星、原神（命ノ星座）は点と線の星座、ZZZ（心象映画）はフィルム。公式アイコンは使わない。
  - UID照会は `acquiredRank` までを解放済みの塗りにし、図鑑は解放の概念が無いため全段を同じ塗りにする。`targetChanges` を持つ段には印を付ける。
  - デスクトップはタイムラインを左、選んだ段の詳細を右に置く。モバイルはタイムラインの下に詳細を置く。
  - UID照会の凸セクションは濃色の背景、図鑑は淡色の背景のため、部品は `tone`（`dark` / `light`）を受け取って配色を切り替える。
  - 選んだ段の詳細（効果名・説明・目標変更・注意）だけを出す。初期選択は、UID照会では「次に解放する段」（`acquiredRank + 1`、6段すべて解放済みなら6）、図鑑では1。表示中のキャラクターか `acquiredRank` が変わったら初期選択へ戻す（U13）。
  - 未解放の段を選んでも詳細を見るだけで、`acquiredRank` や比較の目標は変えない（U14）。
  - 選んだ段に目標変更があれば、「ステータス名 目標 N」を見出し級で出す。
  - 段の呼び名は `rankLabel`（星魂 / 命ノ星座 / 心象映画）を使う。
  - `dataStatus !== "curated"` では、タイムラインを無効色で描いて操作不可にし、現行の準備中文言を出す。高さは固定せず、文言が切れないようにする（U13）。
  - 対応バージョン・基準日・最終更新日・参照リンクは、現行の脚注をそのまま出す。
- **データ**: 既存のみ。
- **デザイン確定ゲート（G-D）**: **確定**。並べ方は縦のタイムライン、記号はゲームごとに変える（2026-09-13、ユーザー決定）。レビューの推奨（横一列・記号なし）は採らない。
- 規模が最小のため、Phase 1 で切替基盤と同時に実装し、基盤の試金石にする。

#### E-1. `siteChrome` = `unified`（共通ヘッダーとゲーム別アクセント）

- **対象**: 公開画面4本（`Home` / `CharacterCatalog` / `GuideHistory` / `TranslationFeedback`）のヘッダーと、`App.tsx` の `PublicCatalogShortcut`（左下の固定ボタン）。
- **表示**
  - 共通ヘッダー `SiteHeader` に、サイト名 / UID照会 / キャラ図鑑 / 更新履歴 / 翻訳フィードバック / 言語切替 / 管理者を並べ、現在地を示す。モバイルは折りたたみメニューにする。
  - `unified` のときは `PublicCatalogShortcut` を出さない。
  - UID照会と図鑑のページ外枠に `data-game="hsr|genshin|zzz"` を付け、`index.css` で `--game-accent` を定義する。色の値はデザイン確定ゲートで決める。
  - 新ヘッダーと新バリアント部品のラベルは最小 11px にする。**legacy 部分の文字サイズは変えない**。
- **データ**: 既存のみ。
- **デザイン確定ゲート（G-E1）**: 全体のトーン（現行の紙面調を保つ / ゲーム UI 寄りの濃色）、3ゲームのアクセント色。
- **着手前に採否を決める事項**: U22（管理者導線は既存のログインと戻り先を再利用、モバイルメニューの開閉名・Escape・フォーカス復帰）。

#### E-2. `colorTheme` = `switchable`（ダークテーマの切替を利用者へ開放）

- **対象**: 公開画面4本と、その時点で登録済みの全バリアント部品。
- **表示**: `ThemeProvider` を `switchable` にし、言語切替の隣にテーマ切替を出す。ヘッダーが legacy でも unified でも出す。`legacy` のときは現行どおりライト固定で、切替も出さない。
- **実装方針**: 既存の色クラスは置き換えず、`dark:` クラスを**追加**する。ライト表示の見た目と既存クラスを変えないため。ダーク用のトークンは `index.css` の `.dark` に定義する。
- **登録条件**: 公開画面4本と、その時点で登録済みの全バリアントがダークで破綻しないことを確認してから、登録表に載せる（D1）。
- **デザイン確定ゲート（G-E2）**: ダーク配色、既定値（ライト / OS 設定に従う）。
- **DR-03 の反映**: `DisplaySettingsProvider` を `ThemeProvider` より外側に置き、有効テーマを「`switchable` なら利用者の好み、そうでなければ light」で決める。好みの保存と有効テーマを分け、管理ルートはライト固定にする。storage の値は light / dark に検証し、例外は吸収する。アプリ全体の再マウントで切り替えない。
- **着手前に採否を決める事項**: U25（保存キー、管理画面、解除後の好みの扱い）。dark→legacy、プレビュー終了、ログアウト、管理ルート往復、storage 拒否、再度の switchable 化で期待どおりのテーマになることを受入条件にする。

#### F. `topPortal` = `portal`（トップを3ゲームの入口にする）

- **対象**: `Home.tsx` の先頭（ヒーロー見出し・UID 照会フォーム・「利用手順」）。照会結果より後のセクションは対象外。
- **表示**
  - 見出しを「HoYoverse Builder」と「崩壊：スターレイル / 原神 / ゼンレスゾーンゼロ のビルド支援」にする（3言語の文言を追加）。英字の「Build with Intention.」は出さない。
  - 3ゲームのパネルに、ゲーム名、装備の呼び名（既存の `t()` の遺物・聖遺物・ドライバディスクなど）、図鑑の収録数、「UIDで照会」「図鑑を見る」（`/characters?game=<id>`）を置く。
  - 収録数は `trpc.build.referenceCatalog`（既存・公開）の `games[id].length` を使い、`staleTime` は図鑑と同じ10分にする。取得中と失敗時は「—」。**Home が新たにこの API を呼ぶ**点だけが通信上の変化になる（§7）。
  - パネルを選ぶと、そのパネル内に UID 入力欄と送信ボタンが開く。状態と処理は既存の `game` / `uid` / `validUid` / `handleSubmit` / `selectGame` を使い、新しい照会ロジックを作らない。
  - 照会後（`lookupUid` あり）は、選択中ゲームのパネルを細い帯に縮め、他の2ゲームをタブとして並べる。タブを押すと、既存の `selectGame` と同じく照会結果を消してそのゲームの入力へ戻る。
  - 「公開プロフィールのみ参照」「UID はこの端末に保存」「第三者サービス」の注記は文言を変えずに出す。「利用手順」は既存の文言のまま、パネルの下へ移す。
  - ゲームらしさは CSS の図形・線・色だけで表す（例: HSR は星軌の細線、原神は7色の円環、ZZZ は黒と黄のストライプ）。**公式ロゴ・キービジュアル・画像は使わない**（§10 Q6）。
- **データ**: 既存のみ（図鑑収録数も既存 API）。
- **デザイン確定ゲート（G-F）**: パネルの並び（3枚横並び / 中央1枚と左右 / 縦積み）、トーン（紙面調 / 濃色フルブリード）。
- **着手前に採否を決める事項**: U20（照会エラー中の再入力）、U21（図鑑収録数の取得を portal のときだけにし、legacy の通信0件を確かめる）。

## 5. 既存機能の非破壊（チェックリスト）

- [ ] 全キー `legacy` で、公開画面の表示が前提コミット時点と同じ（既存テストが無変更で通り、Chrome の目視でも同じ）。

- [ ] ブラウザ保存領域の読み書きが例外になる環境でも、公開画面が表示できる（DR-04）。

- [ ] 既存の管理画面（`/admin`・`/admin/feedback`）の挙動が変わらない。

## 7. リスクと割り切り

- **二重保守**: 採用が決まるまで、legacy と新バリアントの両方を保守する。キャラクター追加（データ側）は表示に依存しないため影響しないが、表示部品の修正は両方に要る。**採用が確定したキーは、legacy と分岐を撤去する修正設計書を別途起こす**（本書の範囲外）。
- **組み合わせの検証漏れ**: D2 の依存禁止と、3構成の検証で抑える。画面の同じ領域を共有する組み合わせ（B×C、B×D、E-2×legacy ヘッダーなど）は、該当 Phase で個別に確認する（DR-05・U30）。依存がどうしても必要になった案は、キーを統合して本書へ追記する。
- **初回訪問の待機**: 前回値の無い初回訪問だけ、最大 600ms の描画待ちが増える。ちらつき防止を優先することはユーザー確認済み（§10 Q2）。M3 で待機が常に上限まで伸びる場合は上限値を見直し、待機する方式自体は変えない。
- **デプロイ順**: Pages と Railway は別デプロイで、Pages が先に新クライアントを公開すると、未実装の `display.settings` を呼ぶ。D5 により `legacy` で表示されるため害は無い。管理画面での公開操作は、Railway の反映を確認してから行う。
- **マイグレーション失敗**: Railway の `preDeployCommand` が失敗するとデプロイ自体が止まり、旧 API が動き続ける（安全側）。ローカルに MySQL が無いため、隔離 DB での upgrade 検証（U27）は実施できない。生成 SQL の目視と、既存 0005 の journal・SQL を変えないことで代替し、未実施として実装ログに記録する。
- **反映の遅れ**: 表示中のタブへの反映は、通常の通信状態でサーバーのキャッシュ60秒＋クライアントの再取得間隔60秒＋通信時間が目安（DR-02）。非表示のタブとオフラインでは上限を保証せず、表示に戻った時点で再取得する。すぐ反映されるのは公開した管理者自身だけ。DB の行を直接消した場合も、サーバーのキャッシュ60秒は残る。
- **再取得の通信量**: 表示中のタブが60秒ごとに `display.settings` を呼ぶ。応答は数十バイトで、サーバーはプロセス内キャッシュから返す。
- **F の通信増**: `topPortal=portal` のとき、Home が `build.referenceCatalog`（圧縮後は小さい応答）を追加で呼ぶ。`legacy` では呼ばない。
- **変更履歴を持たない**: いつ変えたかは `updatedAt` しか残らない。管理者が少数である前提で割り切る（§10 Q8）。
- **ロールバック**
  - 見せ方: 管理画面の「すべて現行に戻す」。
  - 管理画面に入れない場合: Railway の DB で `site_display_settings` の行を削除すれば、全キーが legacy に戻る。
  - コード: PR の revert。
